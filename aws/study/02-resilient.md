## Task 2.1: Design scalable and loosely coupled architectures

### Achieving loose coupling with SQS, SNS pub/sub, and API Gateway

Tight coupling is what happens when one component calls another directly and synchronously, so a slowdown or outage in the callee immediately becomes a slowdown or outage in the caller; loose coupling breaks that direct dependency by putting a buffer between components so each side can fail, scale, or deploy on its own schedule. Amazon SQS is the standard buffer for point-to-point work: a producer drops a message on a queue and moves on, and one or more consumers pull messages off whenever they're ready, so a burst of incoming work piles up in the queue instead of overwhelming or crashing whatever processes it, and a consumer that's temporarily down just means messages wait a little longer rather than getting lost. Amazon SNS extends the same idea into a publish-subscribe pattern: one published notification fans out to many subscribers at once (queues, functions, HTTP endpoints, email, and more), so a producer never needs to know how many downstream listeners exist, and pairing SNS with SQS is a common way to make sure a fanned-out event still lands durably even if a particular subscriber is briefly unavailable. Amazon API Gateway plays a related but different role as the entry point for an API: it terminates client connections, enforces authentication, throttling, and request validation, and routes accepted calls on to backend targets such as Lambda functions or private VPC resources, keeping all of that client-facing traffic management separate from whatever compute is actually doing the work.

### Event-driven architectures and workflow orchestration with Step Functions

An event-driven design reacts to things happening — a file landing in a bucket, an order being placed, a message hitting a queue — instead of running on a fixed schedule or waiting for a client to ask for work, and that reaction model tends to produce systems that are both more loosely coupled and more elastic, since each event producer and consumer only has to agree on what the event looks like, not on when or how the other side gets around to handling it. AWS Lambda functions are frequently the compute behind that reaction, since Lambda ships with built-in triggers for S3, SQS, DynamoDB Streams, and hundreds of other AWS services, letting you wire a response to an event without standing up a server that sits there polling. Once a single event needs to kick off more than one step — a sequence with branching logic, retries, or a blend of quick calls and long-running jobs — AWS Step Functions is the purpose-built way to coordinate it: you model the process as a state machine, and Step Functions manages the handoffs and error handling between Lambda invocations, ECS or Fargate tasks, and a long list of other integrated services, rather than that orchestration logic being scattered through application code. Step Functions gives you two workflow flavors to pick from depending on the job: one type keeps a complete execution history and guarantees each step runs once, well suited to long-running, auditable business processes, while the other favors very high throughput and short-lived runs, which fits bursty, high-volume event processing where a step might occasionally run more than once.

### Scaling strategies: horizontal vs. vertical scaling, caching, and CDNs

Vertical scaling means moving a workload onto a bigger instance — more vCPU, memory, or IOPS on the same box — which is straightforward but runs into a hard ceiling (the largest instance type that exists) and usually forces a restart, making it a poor fit for a highly available design that needs to absorb unpredictable spikes. Horizontal scaling instead adds more instances running the same workload behind a load balancer; there's no practical ceiling, it can happen automatically as load changes through Auto Scaling, and because the work is now spread across many hosts, fault tolerance improves as a side effect, since losing any single host only removes a small slice of total capacity rather than the whole service. Caching cuts down how much there is to scale for in the first place: an in-memory cache in front of a database, or a cache built into API Gateway itself, serves repeated requests for the same data without re-hitting the origin every time, lowering both latency and the read load the backend has to absorb. Amazon CloudFront pushes that same caching idea out to the network edge, keeping copies of static and some dynamic content at locations physically close to end users worldwide, so most requests never have to travel back to the origin Region at all — speeding up delivery for users while shielding the origin from having to scale for every individual request directly.

### Multi-tier architectures, microservices, and load balancing with ALB

A multi-tier architecture separates an application into layers — typically presentation, application logic, and data — each of which can be scaled, secured, and released on its own, and that separation predates microservices as the standard way to structure an application. Microservices carry the idea further by splitting the application layer itself into many small, independently deployable services, usually each with its own data store, so teams can ship and scale one service without coordinating a release of the whole system. A decision that comes up inside any of these layers is whether a given piece is stateless or stateful: a stateless component, like a typical web or API server, keeps no session data of its own, so any running instance can serve any incoming request and an Application Load Balancer can freely add, remove, or swap instances behind it and spread traffic across all of them; a stateful component, such as a database or a server holding session data in memory, needs more careful handling — either moving that state out to a shared store like a managed cache or a database so the layer above it can stay stateless, or falling back to sticky sessions and more deliberate failover when statefulness genuinely can't be avoided. Good scalability design generally pushes as much of a system as it can toward the stateless side of that line, because stateless tiers are exactly the ones a load balancer and an Auto Scaling group can treat as interchangeable.

### Containers vs. serverless compute: ECS, EKS, Fargate, and Lambda

Amazon ECS and Amazon EKS are both container orchestrators — they place containers on compute, restart the ones that fail, and handle service discovery and scaling — but they speak different languages: ECS uses AWS's own task, service, and cluster model, which is quicker to pick up if a team has no existing Kubernetes tooling or expertise, while EKS runs an upstream-compatible, fully managed Kubernetes control plane, the natural choice when an organization already has Kubernetes manifests, operators, or skills it wants to bring along. Either orchestrator can place its containers on a fleet of EC2 instances you manage yourself, or on AWS Fargate, which takes server management out of the picture entirely — you declare the CPU and memory a container needs and Fargate runs it on infrastructure you never patch, size, or see. Deciding between containers (ECS or EKS, with or without Fargate) and Lambda functions mostly comes down to the shape of the work: Lambda is built for short-lived units of work triggered by an event that need to scale from zero with no standing infrastructure, while containers suit long-running processes, steady traffic, or applications that need a full OS environment, a particular runtime version, or bulky local dependencies that don't map cleanly onto Lambda's execution model. Migrating an existing application into containers is also a common first modernization step for legacy or on-premises workloads, since packaging the app and its dependencies into a container image makes it portable across ECS, EKS, or Fargate without first breaking it apart into individual functions — usually a smaller, lower-risk move than jumping straight to a serverless rewrite.

### Storage types, read replicas, and purpose-built managed services (Transfer Family, Secrets Manager)

Picking the right storage type is a foundational scalability decision: object storage (Amazon S3) holds independent files reached over an HTTP API and scales to effectively unlimited capacity and request volume, which fits static assets, backups, and data lakes but not something a server expects to mount as a filesystem; file storage (Amazon EFS or FSx) gives you a shared, POSIX- or SMB-style filesystem that many instances or containers can mount and use at the same time, the choice when an application expects ordinary file-and-directory access shared across a fleet; and block storage (Amazon EBS) provides low-latency volumes attached to one instance at a time, the natural fit for a database's own data files or a boot volume. On the database side, read replicas scale read throughput horizontally: a relational database asynchronously streams changes from its primary instance out to one or more replicas, and an application can send read-only work — reporting queries, dashboards, browse traffic — to those replicas instead of piling it all onto the primary, which is a far cheaper way to add read capacity than resizing the primary vertically. Beyond compute and storage, AWS also offers purpose-built managed services that take undifferentiated heavy lifting out of a scalable design rather than leaving it for you to build: AWS Transfer Family stands up a fully managed SFTP, FTPS, FTP, or AS2 endpoint in front of S3 or EFS so you're not running and scaling your own file-transfer server fleet for partner or customer data exchange, and AWS Secrets Manager centralizes (and can automatically rotate) database credentials and API keys, so scaling an application out to many instances doesn't also mean distributing and babysitting long-lived secrets across every one of them.

## Task 2.2: Design highly available and/or fault-tolerant architectures

### AWS global infrastructure: Regions, Availability Zones, and Route 53 failover

AWS organizes its footprint into Regions — separate geographic areas — each made up of multiple Availability Zones (AZs): distinct facilities with their own power, cooling, and networking, linked to each other by low-latency connections. A resilient design spreads a workload's compute and data across at least two AZs in a Region so the loss of one facility doesn't take the whole application with it, and for workloads that need to survive the loss of an entire Region, that same principle extends outward to operating across two or more Regions at once. Amazon Route 53 sits in front of this topology as the DNS layer: beyond turning domain names into IP addresses, it can run health checks against your endpoints and stop sending traffic to any that fail, and its routing policies — failover, weighted, latency-based, geoproximity — let an architect decide exactly how traffic should redistribute the moment an AZ or Region goes unhealthy. Choosing which AWS services to build on for high availability and fault tolerance largely comes down to favoring ones that are natively Multi-AZ or multi-Region aware — a load balancer spanning AZs, a database with a Multi-AZ standby, a globally replicated data store — over a design that treats resilience as something bolted on after the fact to a single-location resource.

### Eliminating single points of failure: route tables, Application Load Balancer, and RDS Proxy

A route table decides where traffic leaving a subnet goes next, and getting it wrong is a surprisingly easy way to introduce a hidden single point of failure — pointing every private subnet at one NAT gateway that lives in a single AZ means that AZ's outage cuts off outbound connectivity for every subnet depending on it, so a resilient design gives each AZ its own NAT gateway and a route table that matches. An Application Load Balancer removes a different single point of failure: rather than clients connecting straight to one server, the ALB spreads incoming requests across healthy targets registered in multiple AZs and stops sending traffic to any target that fails its health check, so one bad instance, or one bad AZ, doesn't take the whole service down with it. Amazon RDS Proxy addresses yet another failure mode, one common with serverless or auto-scaled fleets: a burst of application instances can open far more database connections than the database can comfortably handle, so the proxy pools and reuses a fixed set of connections on the application's behalf, and because it holds its own connection to the database, it can switch over to a standby instance in seconds while the client-side connections stay intact — a particularly valuable safety net for older applications that were never written with connection pooling or graceful reconnects in mind.

### Choosing a disaster recovery strategy: backup/restore, pilot light, warm standby, and active-active

Every disaster recovery strategy trades cost against how fast and how completely you can recover, and AWS groups the common options into four tiers of increasing readiness (and expense). Backup and restore is the cheapest tier: data is snapshotted periodically, infrastructure is captured as code so it can be rebuilt on demand, and nothing actually runs in the recovery Region until a disaster is declared — which also makes it the slowest to recover. Pilot light keeps only the data tier continuously replicated and running live in the recovery Region, while the rest of the stack sits deployed but powered down, ready to be switched on and scaled up when needed. Warm standby raises the bar again: the entire stack already runs in the recovery Region around the clock, just at reduced size, so recovering is purely a matter of scaling capacity up rather than starting anything cold. Multi-site active-active runs full capacity in more than one Region at the same time and actually serves live traffic from each of them, getting closest to zero downtime but at the highest cost and operational complexity of the four. Two numbers decide which tier a given workload actually needs: recovery point objective (RPO), the maximum amount of data loss the business can tolerate, expressed as a span of time, and recovery time objective (RTO), how long the business can be down before the outage is unacceptable — a tight RPO pushes a design toward continuous replication, and a tight RTO pushes it toward a warm or active-active posture instead of cold backups.

### Data durability and replication across storage services

Durability and availability are easy to conflate but answer different questions: durability is the likelihood that a piece of data survives over time without being lost or silently corrupted, while availability is whether you can reach and use that data right now. Amazon S3 reaches extremely high durability by automatically storing multiple copies of every object across multiple devices and multiple Availability Zones within a Region, and S3 Cross-Region Replication extends that same protection outward to a second Region for workloads that need to survive losing an entire Region, not just one facility. Amazon EBS volumes, by contrast, live inside a single Availability Zone by default, which is exactly why it's standard practice to snapshot them to S3 (itself Regional and multi-AZ) so a volume can still be recovered after an AZ-level failure. Managed databases build replication in as a core feature too: an RDS Multi-AZ deployment keeps a synchronously updated standby in a second AZ purely to fail over to, read replicas provide an asynchronously updated copy that can also absorb read traffic, and promoting a read replica running in another Region is itself a legitimate way to recover from a Regional outage. Knowing which storage and database options already replicate data on your behalf — and which ones leave replication to you — is central to designing for data durability and availability.

### Immutable infrastructure and automation for reliable, self-healing deployments

Immutable infrastructure means you never patch or reconfigure a running server in place; instead you bake a new machine or container image with the change, deploy fresh instances from it, and retire the old ones, rather than logging into a live fleet and editing configuration by hand. This matters for reliability because a server that's never been touched after launch behaves identically to every sibling built from the same image, which removes an entire category of outages caused by configuration drift — a fix applied to one box but never carried over to the rest. Pairing this with automation (Auto Scaling groups, infrastructure-as-code templates, a pipeline that redeploys on failure) produces infrastructure that repairs itself: when an instance fails a health check, the group terminates it and launches a replacement from the same known-good image without anyone needing to step in. The same pattern is how architects gradually raise the reliability of an older, non-cloud-native application without rewriting it from scratch — placing the existing app inside an Auto Scaling group behind a load balancer, moving its state out to a managed database or shared filesystem so any single instance can be replaced without losing data, and letting automated recovery take over from the manual server-babysitting the application used to depend on. Distributed-systems thinking adds a further layer of protection: designing as though any one component can fail at any time — retrying transient errors, isolating a failing part of the system with patterns like bulkheads or circuit breakers so trouble doesn't cascade, and decoupling components through queues — tends to degrade gracefully under stress instead of failing outright.

### Service quotas, throttling, workload visibility with X-Ray, and managed AI services as a resilience pattern

Every AWS account runs under service quotas — caps on how many of a given resource you can create, or how fast you can call a particular API — and hitting one unexpectedly, whether it's a concurrency ceiling on Lambda, an instance limit on EC2, or a throttled API call, looks exactly like an outage to your users even though nothing in the infrastructure actually broke. Designing for resilience means estimating which quotas a workload's peak traffic could realistically bump into, requesting increases well ahead of time through Service Quotas rather than mid-incident, and writing application code that handles a throttling response with retry-and-backoff logic instead of simply failing the request outright. AWS X-Ray provides the visibility to catch these problems, along with latency spikes and error patterns, before customers notice them: it follows a request as it hops between your services and their downstream calls, and its service-map view makes it easy to spot which link in a distributed chain is slow, erroring, or bumping against a limit. Reaching for a managed service instead of a self-hosted equivalent is itself a resilience strategy — Amazon Comprehend (natural-language processing such as sentiment scoring and entity extraction) and Amazon Polly (text-to-speech) are good examples of capabilities you'd otherwise have to run and scale yourself on EC2, most likely as a single point of failure, but which AWS instead operates as highly available, auto-scaling APIs you simply call, moving the burden of keeping that capability running onto AWS.
