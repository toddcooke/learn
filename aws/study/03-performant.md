## Task 3.1: Determine high-performing and/or scalable storage solutions

### Object storage with Amazon S3: buckets, keys, and storage classes

Amazon S3 stores data as objects — a file plus its metadata — inside containers called buckets, and every object is reached through the combination of a bucket name and a unique key rather than a filesystem path, which is why applications talk to it over an HTTP API instead of mounting it like a drive. Because there's no fixed capacity to provision, a bucket can absorb effectively unlimited objects and request volume, making S3 the default choice for data lakes, backups, static web assets, and archives — anything that doesn't need to look like a shared directory to a running server. Picking the right storage class is the main performance-and-cost lever inside S3 itself: S3 Standard suits data accessed often, S3 Express One Zone trades multi-AZ redundancy for single-digit-millisecond latency by keeping data in one Availability Zone next to compute, Intelligent-Tiering automatically shifts objects between tiers as access patterns change, and the Glacier tiers push rarely touched data to the cheapest possible storage at the cost of retrieval speed. S3 also guarantees strongly consistent reads immediately after a write or overwrite completes, so an application never has to guess whether a just-uploaded object is visible yet.

### File storage with Amazon EFS: elastic, shared, POSIX-style file systems

Amazon EFS gives you a network file system that many compute resources — EC2 instances, ECS tasks, EKS pods, Lambda functions, and Fargate — can mount and use at the same time over NFS, which is the option to reach for whenever an application expects ordinary shared file-and-directory access rather than an API call or a single attached disk. Capacity isn't something you provision ahead of time: EFS grows and shrinks on its own as files are added or removed, scaling toward petabytes without any resizing step, and the newer Elastic throughput mode adjusts bandwidth automatically to match whatever a workload is doing at that moment instead of requiring you to set a baseline rate in advance. For availability planning, a Regional file system spreads its data across several Availability Zones in a Region so it keeps serving even if one AZ has a problem, while a One Zone file system keeps everything in a single AZ, accepting a lower resilience bar in exchange for a lower price — a tradeoff worth naming explicitly for any workload where a shared filesystem is the plan.

### Block storage with Amazon EBS: volume types sized for performance

Amazon EBS hands out durable block volumes that attach to a single EC2 instance and behave like a local disk the instance can format and use directly, which makes it the natural fit for a database's own data files or a boot volume that needs consistently low latency rather than shared, filesystem-style access. Each volume lives inside one Availability Zone, and EBS offers two broad families of volume to match different access patterns: SSD-backed types tuned for transactional, IOPS-heavy work such as a busy database, and HDD-backed types tuned for large, mostly sequential reads and writes where sustained throughput matters more than per-operation latency. Elastic Volumes let a team raise capacity or switch performance tier on a live volume with no downtime, so a design doesn't need to guess the exact final size on day one — it can start modest and grow as real usage data comes in. EBS snapshots copy a volume's data into S3 for durability and give you a way to restore a fresh volume, or move one across an Availability Zone, Region, or account, independent of the original volume's lifecycle.

### Matching workload shape to object, file, and block storage

A recurring exam skill is recognizing which storage category a described workload actually needs: object storage fits independently addressed files reached over HTTP at effectively unlimited scale, such as a data lake, media library, or backup target; file storage fits any scenario where several compute nodes need to see and modify the exact same directory tree concurrently, like a shared content-management or rendering workload; and block storage fits a single instance that needs a private, low-latency volume it can treat as its own disk, most obviously a database's storage layer. Looking past the initial choice toward future scale changes the calculus slightly — S3 and EFS both absorb growth automatically with no capacity step to plan for, while an EBS volume needs someone (or an automated process) to explicitly grow it or move to a different volume type as demand increases, so a design that expects heavy, unpredictable growth on a block-storage-backed component should build that resizing step into its operational plan rather than assuming it away.

### Bridging on-premises and AWS storage: hybrid patterns with Storage Gateway and DataSync

AWS Storage Gateway puts an appliance on-premises that speaks the file and block protocols local applications already use — an S3 File Gateway exposes an NFS or SMB share that's actually backed by S3 objects, and Volume Gateway exposes iSCSI block volumes in cached or stored modes — so an existing workload keeps its familiar local access pattern while its data lands durably in AWS storage behind the scenes, which is the standard answer whenever a scenario calls for ongoing hybrid access rather than a one-time move. AWS DataSync instead specializes in moving large datasets: it connects to on-premises NFS, SMB, HDFS, or generic object storage, and AWS storage such as S3, EFS, or FSx (or even between two AWS storage services), using a purpose-built, multi-threaded transfer engine that includes end-to-end encryption and automatic integrity checks, and it can reach AWS storage through a VPC endpoint so the transfer never has to cross the public internet. The practical distinction for a design is durability of the access pattern: reach for Storage Gateway when an application needs to keep working against a local-looking file or volume share indefinitely, and reach for DataSync when the job is a scheduled or one-time bulk migration or sync into AWS.

## Task 3.2: Design high-performing and elastic compute solutions

### Choosing EC2 instance families, sizes, and processor options for the workload

EC2 groups its hardware offerings into instance families by the resource profile they're built for — general purpose, compute optimized, memory optimized, storage optimized, and accelerated computing for GPU or ML-chip workloads — and every size within a family scales vCPU count, memory, and network or storage bandwidth together, so moving up or down a size changes all of those dimensions at once rather than letting you tune just one. Because EC2 bills by the second, AWS's own recommendation is to launch a candidate type, benchmark it against the actual application rather than a synthetic guess, and change type later if it turns out mis-sized, which is a far cheaper way to land on the right instance than trying to calculate it perfectly up front. Beyond the traditional Intel and AMD processor lineup, Graviton (Arm-based) instances aim at the best price-performance ratio for workloads that support the architecture, and the burstable T-family trades a capped baseline CPU allocation for a lower price on spiky, non-sustained traffic. Getting this initial hardware match right — before any scaling policy is layered on top — is the foundation of a high-performing compute design.

### Scaling compute automatically: EC2 Auto Scaling, AWS Auto Scaling, and the right metric

An EC2 Auto Scaling group keeps a fleet between a minimum, maximum, and desired instance count, replacing any instance that fails its health check and balancing the fleet evenly across whichever Availability Zones you've configured so no single AZ ends up carrying a disproportionate share of capacity. A scaling policy decides when the group actually changes size — target tracking holds a chosen metric near a set point, step scaling reacts to CloudWatch alarm thresholds in defined increments, and scheduled scaling handles predictable time-of-day patterns — and picking the right metric for a given tier matters: a web tier scales cleanly on its load balancer's request count per target or on the fleet's own average CPU utilization, a queue-backed worker fleet scales better against the queue's backlog depth than against CPU, and DynamoDB scales its own provisioned throughput against consumed capacity. AWS Auto Scaling sits a level above any single group: instead of tuning one EC2 Auto Scaling group in isolation, it lets you define one scaling plan that coordinates capacity across several resource types together — EC2 Auto Scaling groups, ECS services, DynamoDB tables, and Aurora replicas among them — which is the tool to reach for when multiple tiers of an application need to grow and shrink in a coordinated way rather than being tuned one at a time.

### Serverless compute: right-sizing Lambda memory and running containers on Fargate

AWS Lambda removes server provisioning entirely and bills per invocation and per unit of execution time, with the memory setting as the one capacity dial available — allocating more memory to a function also increases the CPU and network bandwidth it gets, proportionally, so an under-provisioned CPU-bound function can quietly run slower (and sometimes end up costing more once total run time is counted) while an over-provisioned one just wastes budget on capacity it never touches. Testing a function's actual duration and cost across a small range of memory settings, rather than picking one number and moving on, is the standard way to land on a genuinely efficient configuration. AWS Fargate extends the same server-free idea to containers: rather than sizing, patching, and scaling a fleet of EC2 hosts underneath an ECS or EKS cluster, you declare the CPU and memory a task needs and Fargate places it on infrastructure it fully owns and operates, which fits any team that wants container packaging without also taking on host-level capacity planning.

### Container orchestration with ECS and EKS, on EC2 or Fargate

Amazon ECS and Amazon EKS both place containers onto compute, restart ones that fail, and plug into load balancers and service discovery, but they lead with different control-plane models: ECS relies on AWS's own task, service, and cluster constructs, which tends to be the faster on-ramp for a team without existing Kubernetes tooling, while EKS runs a Kubernetes-conformant control plane so an organization already invested in Kubernetes manifests, operators, and community tooling can bring all of that along unchanged. That orchestrator choice is separate from the compute-placement choice underneath it — both ECS and EKS can schedule work onto self-managed EC2 capacity when a team wants direct control over instance type, OS patching, or specialized hardware, or onto Fargate when the goal is to skip host management altogether. Deciding between containers and Lambda for a given piece of compute usually comes down to run duration and how much state or custom runtime a workload carries: short, event-triggered bursts that benefit from scaling to zero point toward Lambda, while long-running processes, heavyweight dependencies, or a need for a full OS environment point toward ECS or EKS instead.

### Distributed and batch processing at scale: AWS Batch and Amazon EMR

AWS Batch takes a queue of jobs and provisions a right-sized compute environment (backed by EC2 or Fargate) to run them, which removes the need to build a custom job scheduler or babysit cluster capacity for workloads that arrive in bursts rather than a steady stream — nightly ETL runs, scientific simulations, or media-rendering jobs are typical fits. Amazon EMR approaches distributed computing from a different angle, running managed clusters of open-source big-data frameworks — chiefly Apache Spark and Hadoop — so a dataset too large for any single machine gets split across many nodes and processed in parallel; an EMR cluster can pull input straight from S3 or a Kinesis stream, and its size can flex to match the data volume of a given run instead of sitting provisioned at peak capacity around the clock. Both services exist to spread large or unpredictable compute jobs across many machines automatically, sparing a solutions architect from hand-building and coordinating a fixed cluster for work that doesn't arrive on a constant schedule.

### Decoupling compute tiers with pub/sub so each layer scales independently

Inserting a buffer between two compute tiers — Amazon SQS for one-to-one work handoff, Amazon SNS for one-to-many fan-out to several subscribers at once — means a spike hitting the producer side doesn't force the consumer side to scale in lockstep, and the reverse holds too: the consumer fleet can size itself against its own backlog metric on its own timetable, and a consumer that's briefly unavailable just means work waits in the buffer instead of the producer stalling out. That separation is what lets a design apply the scaling approach and even the compute type that best fits each tier on its own terms — for instance, Lambda behind an SQS queue to absorb bursty, unpredictable spikes, paired with a steadily sized EC2 Auto Scaling group for a tier with more constant throughput — rather than sizing an entire pipeline around whichever stage happens to be hardest to scale.

## Task 3.3: Determine high-performing database solutions

### Relational, non-relational, and in-memory databases: matching engine type to the access pattern

A relational database (Amazon RDS or Aurora) organizes data into tables with a fixed schema and supports joins and multi-table transactions, which suits workloads with complex, interrelated queries and a need for strong consistency across those relationships. A non-relational database like DynamoDB instead stores flexible key-value or document items without a rigid schema or join support, and in exchange it delivers consistent single-digit-millisecond performance whether a table holds a handful of items or spans hundreds of terabytes, which is why it fits workloads with simple, well-known access patterns — a shopping cart, a session store, a leaderboard — that need to scale smoothly without capacity planning around joins. In-memory data stores such as those built on ElastiCache sit apart from both: they trade persistence and query richness for microsecond-to-millisecond latency, so they're the layer you put in front of a relational or non-relational database to absorb read-heavy or latency-sensitive traffic rather than a system of record on their own. Recognizing which of these three shapes a described workload actually needs — relational, non-relational, or purely in-memory — is the starting point before comparing specific services.

### Scaling reads and preserving availability with Aurora and RDS read replicas

Amazon Aurora is a relational engine, compatible with MySQL and PostgreSQL, that separates compute from a fast, auto-growing distributed storage layer shared across an entire cluster, letting it reach several times the throughput of stock MySQL or PostgreSQL on comparable hardware while handling failover, backup, and storage growth largely on its own. Read replicas — supported by both Aurora and standard RDS engines — give a read-heavy workload somewhere to send query traffic besides the primary: RDS copies changes from the primary out to one or more replicas asynchronously, an application routes reporting or browse-only traffic to those replicas instead of piling it onto the primary, and because a replica can also be promoted to a standalone instance, it doubles as a disaster-recovery option if the primary is lost. A read replica differs from a Multi-AZ standby, which replicates synchronously purely to fail over to and never serves read traffic on its own; a design that needs both extra read capacity and a dedicated failover target typically runs a Multi-AZ standby alongside one or more separate read replicas. For standard RDS engines, adding or removing read replicas as demand shifts is a step you (or an external automation script) take deliberately rather than something RDS does on its own; Aurora is the exception, since its Aurora Auto Scaling feature can add and remove Aurora Replicas for a cluster automatically against a target metric such as average CPU or connection count.

### Database capacity planning: DynamoDB capacity units and provisioned IOPS storage

DynamoDB offers two ways to pay for and provision read and write throughput: on-demand capacity mode bills per request and adjusts instantly to traffic with no capacity to plan ahead of time, which suits workloads with spiky or hard-to-predict demand, while provisioned capacity mode has you set a target amount of read and write capacity units up front (optionally paired with auto scaling of that provisioned amount) at a lower cost per unit for traffic that's steadier and easier to forecast. Because DynamoDB was purpose-built to skip the operational tuning a relational database needs at scale — no joins to optimize, no index maintenance beyond the secondary indexes you explicitly create — capacity planning here is mostly about picking the billing mode that matches how predictable a table's traffic actually is, then layering global tables on top for a workload that needs multi-Region, multi-active reads and writes with no single primary to fail over. On the relational side, the equivalent capacity-planning lever is storage performance rather than a request-based unit: RDS and Aurora let you provision a target IOPS rate for the underlying storage volume so a write- or read-heavy database gets a guaranteed, consistent number of operations per second instead of the variable performance a general-purpose volume delivers, which matters most for transactional workloads with a steady, predictable I/O rate. Getting either capacity model right avoids the two failure modes at either extreme: under-provisioned capacity causing throttled requests or storage-bound latency, or over-provisioned capacity paying for throughput that never gets used.

### Offloading read-intensive traffic with ElastiCache and DynamoDB Accelerator (DAX)

Amazon ElastiCache runs a managed in-memory data store or cache — built on the Valkey, Memcached, or Redis OSS engines — that sits in front of a primary database and answers repeated reads straight from memory instead of hitting the database on every request, which is the standard way to cut both latency and read-side load once a workload's traffic skews heavily toward the same hot data. It's available as a serverless cache that scales its own memory, compute, and bandwidth without any node sizing, or as a node-based cluster when a team wants direct control over node type, count, and Availability Zone placement, including choosing cluster mode for horizontal scaling versus a simpler single-node setup for vertical scaling. Amazon DynamoDB Accelerator (DAX) is a purpose-built variant of the same idea specifically for DynamoDB: it's a managed, highly available in-memory cache that can cut read response times from milliseconds down to microseconds even under millions of requests per second, handling cache population and invalidation for you so an application doesn't need custom caching logic in front of its DynamoDB calls. Deciding whether to add a caching layer at all generally comes down to how skewed and read-heavy the access pattern is — a cache adds the most value when a small slice of data accounts for a large share of total reads.

### Managing database connections at scale with Amazon RDS Proxy

A burst of application instances — common with Lambda functions or an auto-scaled fleet — can open far more connections to a relational database than it can comfortably sustain, since each connection consumes memory and CPU on the database itself regardless of how much work it's actually doing. Amazon RDS Proxy sits between the application and the database, pooling and reusing a bounded set of real database connections while serving many more client-side connections against that pool, queuing or shedding load gracefully when incoming requests exceed the limits you've set rather than letting the database itself become overwhelmed. Because RDS Proxy keeps its own connection to the database, it can switch over to a standby in seconds during a failover while every application-side connection stays intact, which is a meaningful reliability win for older applications that were never written with connection pooling or reconnect logic in mind. It also centralizes authentication, letting clients connect using IAM credentials while the proxy itself authenticates to the database with IAM or with credentials stored in Secrets Manager, which keeps long-lived database passwords out of application code.

### Choosing and migrating database engines: Aurora vs. DynamoDB, and homogeneous vs. heterogeneous migration

Choosing between Aurora and DynamoDB for a new workload comes down to the same relational-versus-non-relational question from a migration angle: pick Aurora when the application already thinks in SQL, needs multi-table transactions or ad-hoc joins, or is being lifted from an existing MySQL or PostgreSQL database with minimal rework, and pick DynamoDB when the access patterns are simple, well-defined key lookups that need to scale to a very large size with predictable, low latency and little schema maintenance. When a database migration is homogeneous — the source and target run the same engine, such as on-premises MySQL moving to RDS or Aurora MySQL — the schema and application code typically carry over untouched, so the migration mostly involves moving data. A heterogeneous migration — moving between different engines, such as a commercial database to Aurora PostgreSQL — usually requires converting the schema and any embedded procedural code first, commonly with the AWS Schema Conversion Tool, before AWS Database Migration Service handles the actual data movement and, where needed, ongoing replication during the cutover window. Recognizing which category a described migration falls into determines how much schema-conversion work has to happen before data migration can even start.

## Task 3.4: Determine high-performing and/or scalable network architectures

### Accelerating content and global traffic with CloudFront and Global Accelerator

Amazon CloudFront caches HTTP and HTTPS content — web pages, images, video, API responses — at edge locations spread around the world, so a viewer's request is answered from whichever nearby edge already holds a copy instead of always traveling back to the origin (an S3 bucket or a custom HTTP server); when content isn't cached yet, CloudFront fetches it from the origin over the AWS backbone and caches it for the next request, cutting both the number of networks a request has to cross and the latency users experience. AWS Global Accelerator solves a related but distinct problem for traffic that isn't necessarily HTTP: it hands out static anycast IP addresses and steers connections onto the AWS global network toward the closest healthy regional endpoint — an Application Load Balancer, Network Load Balancer, EC2 instance, or Elastic IP — re-routing within seconds if health checks detect a problem with an endpoint or an entire Region. The practical distinction for a design is what's being optimized: CloudFront caches and speeds up content delivery for web-style traffic, while Global Accelerator improves the routing path and failover behavior for TCP or UDP traffic terminating on load balancers or instances across one or more Regions.

### Designing subnet tiers, routing, and IP addressing for a scalable VPC

A subnet is a slice of a VPC's IP address range confined to a single Availability Zone, and a scalable network design typically lays out one subnet per tier per AZ — a public tier with a route to an internet gateway for load balancers, and one or more private tiers with no such route for application servers and databases — so each tier can be sized, secured, and scaled on its own terms. Route tables attached to each subnet decide where outbound traffic actually goes, and getting the routing right (a NAT gateway per AZ rather than one shared NAT gateway, for instance) avoids turning a single routing choice into a hidden bottleneck or single point of failure as traffic grows. Planning IP addressing ahead of time matters more than it first appears: choosing CIDR ranges with enough headroom for future subnets and instances avoids a disruptive re-addressing exercise later, and adopting IPv6 alongside or instead of IPv4 sidesteps the practical limits and cost of public IPv4 address space as a fleet scales into the thousands of instances. VPC endpoints round out the picture by letting resources in a private subnet reach AWS services like S3 or DynamoDB over the AWS network directly, without adding a NAT gateway or internet gateway hop to that traffic path.

### Distributing traffic with load balancers: choosing among ALB, NLB, and GWLB

Elastic Load Balancing offers several load balancer types tuned for different jobs, and picking the right one is a recurring high-performing-network decision. An Application Load Balancer operates at the application layer, evaluating listener rules that send HTTP and HTTPS traffic toward whichever target group matches the request's path, host header, or other content — the right choice whenever routing decisions need to look inside the request, such as sending traffic for different microservices to different backends from one load balancer. A Network Load Balancer instead operates at the transport layer, built for extreme throughput, very low latency, and static IP addresses, which fits protocols other than HTTP or workloads where every microsecond of added latency matters. A Gateway Load Balancer works at the network layer to transparently insert third-party virtual appliances — firewalls, intrusion-detection systems — into a traffic path without the rest of the architecture needing to know they're there. Because a load balancer automatically spreads registered targets across multiple Availability Zones and stops sending traffic to any target that fails its health check, choosing the right type is as much about eliminating a single point of failure as it is about raw throughput.

### Private connectivity options: VPN, Direct Connect, and VPC endpoints

AWS Site-to-Site VPN encrypts traffic between an on-premises network and a VPC over the public internet using IPsec tunnels, and because it needs no special physical infrastructure, it can typically be stood up in minutes to hours, making it the fast, low-commitment option for hybrid connectivity or as a backup path. AWS Direct Connect instead runs a dedicated fiber connection from an on-premises router into an AWS Direct Connect location, and from there you provision virtual interfaces — a private virtual interface to reach a VPC, a public virtual interface to reach public AWS services, or a transit virtual interface to reach multiple VPCs through a transit gateway — bypassing the public internet entirely for more consistent bandwidth and lower, more predictable latency, at the cost of a longer physical setup process; a common pattern pairs Direct Connect as the primary path with a Site-to-Site VPN as an encrypted backup. For traffic that never needs to leave AWS's own network in the first place, a VPC endpoint lets resources in a subnet reach an AWS service like S3 or DynamoDB, or a service exposed through AWS PrivateLink, using private IP addresses instead of routing out through an internet gateway or NAT device — removing an unnecessary hop from the path and the NAT gateway's throughput ceiling from the picture entirely.

### Placing resources and shaping network topology for performance and future scale

Where resources sit relative to each other and to end users is itself a performance lever: keeping tightly coupled tiers within the same Availability Zone reduces the cross-AZ latency and data-transfer cost that would otherwise be paid on every internal call, while still spreading redundant copies of each tier across multiple AZs so no single facility's failure removes the whole service — the two goals are reconciled by replicating the same multi-AZ pattern per tier rather than scattering unrelated tiers across zones at random. EC2 cluster placement groups take this further for tightly coupled, latency-sensitive workloads such as high-performance computing by packing instances physically close together within one Availability Zone for the lowest possible network latency between them. As a topology grows past a handful of VPCs connected by point-to-point peering, a transit gateway acting as a central routing hub keeps the design manageable, connecting many VPCs, VPN connections, and Direct Connect links through one place instead of an ever-growing mesh of individual connections. Planning subnet and address space with room to add capacity, and choosing a topology that scales by replicating a pattern rather than by adding one-off exceptions, is what keeps a network design able to absorb future growth instead of needing a redesign at the next order of magnitude.

## Task 3.5: Determine high-performing data ingestion and transformation solutions

### Real-time streaming ingestion with Kinesis Data Streams

Amazon Kinesis Data Streams takes in continuous, high-volume data — application logs, clickstreams, IoT telemetry, market feeds — as a steady flow of records rather than periodic batches, and a consuming application typically sees a new record available for processing in well under a second after it's written, which is what makes it the right fit whenever a design calls for reacting to data as it arrives instead of waiting for the next scheduled load. Because a stream is elastic, you can add shards to raise its throughput ceiling as ingestion volume grows, and because the data itself persists in the stream for a configurable window, more than one consumer application can read the same stream independently at the same time — one computing rolling aggregates into a database while a separate one archives raw records to S3, for example — without those consumers competing with each other or needing to coordinate. That combination of low end-to-end delay and support for multiple independent readers is the main signal that a workload calling for continuous ingestion and immediate downstream processing should be built on Kinesis rather than a periodic batch job.

### Moving data into AWS: DataSync and Storage Gateway for ingestion pipelines

When source data lives on premises and needs to land in a data lake, AWS DataSync provides a secure, managed transfer path from on-premises NFS, SMB, HDFS, or object storage straight into S3 (or EFS or FSx), using a parallel, multi-threaded protocol that's substantially faster than generic copy tools and that validates data integrity automatically along the way; scheduling DataSync tasks to run periodically is a common pattern for feeding a lake with recurring batches rather than a single one-time load. Reaching AWS storage through a VPC endpoint rather than the public internet keeps that transfer path private, which addresses the access-security half of an ingestion design alongside IAM roles scoped narrowly to the specific buckets or file systems a transfer job needs to touch. AWS Storage Gateway serves a complementary role when an existing application needs to keep writing through a local-looking file or volume share even as that same data becomes available for analytics in S3 behind the scenes — useful for feeding a lake continuously from a legacy system without redesigning how that system writes its data in the first place.

### Cataloging and securing a data lake with AWS Glue and Lake Formation

A data lake built on S3 only becomes queryable once something describes what schema lives in which files, and the AWS Glue Data Catalog fills that role: Glue crawlers scan data sources, infer table and column structure automatically, and register the result in a central catalog that Athena, Amazon Redshift Spectrum, and EMR can all query against directly, which avoids hand-maintaining schema definitions in every tool that touches the lake separately. AWS Lake Formation builds on top of that shared catalog as a dedicated authorization layer, letting a team define fine-grained access — down to specific tables, columns, or rows — once, centrally, rather than replicating a patchwork of individual bucket policies across every service and team that needs to read the lake. Together, cataloging and centralized authorization are what let a data lake scale to many datasets and many consuming teams without turning access control into an unmanageable, per-bucket exercise, which is the core of designing secure access into an ingestion pipeline from the start rather than bolting it on afterward.

### Transforming data formats and pipelines with AWS Glue ETL

AWS Glue runs serverless extract-transform-load jobs on a managed Apache Spark engine, so cleaning, reshaping, or joining datasets at scale doesn't require standing up or sizing a Spark cluster yourself — Glue Studio's visual job canvas generates the underlying code for common transformations, while more complex logic can still be hand-written and run the same way. An especially common transformation in an analytics pipeline is converting row-oriented formats such as CSV or JSON into a columnar format like Parquet: columnar storage lets query engines such as Athena read only the columns a query actually needs and compress similar values more effectively, which cuts both the data scanned per query and its cost. Glue jobs can run on a fixed schedule, on demand, or in response to an event such as a new file landing in a bucket, and multiple jobs and crawlers can be chained into a workflow so that, for example, a crawler refreshes the catalog automatically right after a transformation job finishes writing new output.

### Querying and visualizing a data lake with Athena

Amazon Athena runs standard SQL directly against data sitting in S3 without requiring any database to be loaded or any infrastructure provisioned ahead of time — point it at a location cataloged by Glue, and it starts returning results in seconds, executing queries in parallel across the underlying files so that performance holds up even against large datasets and complex joins. Billing follows the amount of data a query actually scans, which is precisely why upstream choices like partitioning data by date and converting it to a columnar format such as Parquet pay off twice over: they make individual queries faster and measurably cheaper at the same time. Athena is typically the query layer underneath a business-intelligence tool such as Amazon QuickSight, which connects to Athena to turn ad-hoc SQL results into interactive dashboards and visualizations for end users who never write a query themselves — the combination of a serverless query engine feeding a visualization layer is the standard answer whenever a design needs to expose data-lake content to analysts without operating a traditional data warehouse.

### Choosing EMR versus serverless analytics, and matching ingestion frequency to the job

Amazon EMR is the right tool when a transformation genuinely needs a distributed compute cluster — custom Spark or Hadoop code, machine-learning training over large datasets, or processing that depends on a specific open-source big-data tool that Athena or Glue don't expose directly — and an EMR cluster's size can be matched to a particular job's data volume rather than left running at a fixed capacity. For lighter or more intermittent transformation and query needs, the serverless combination of Glue for transformation and Athena for querying avoids managing a cluster at all, which is usually the simpler and cheaper choice unless a workload's scale or tooling requirements specifically call for EMR. Ingestion frequency should drive the same kind of choice on the intake side of the pipeline: data that must be reflected in the lake within seconds calls for a streaming path built on Kinesis feeding Lambda or a Glue streaming job, while data that only needs to be current within hours or a day fits comfortably on a scheduled batch pattern using DataSync or a periodic Glue job — building a continuous streaming pipeline for data that only needs a daily refresh adds operational cost without a matching benefit.
