## Task 4.1: Design cost-optimized storage solutions

### S3 storage classes and Lifecycle rules for tiering data down as it ages

Every object placed in S3 lands in S3 Standard unless told otherwise, which is the right home for data that's read often, but a meaningful share of most datasets cools off with time and keeps costing full price while sitting untouched. S3 Standard-IA and One Zone-IA hold the same millisecond retrieval speed as Standard at a lower storage rate in trade for a fee charged on every gigabyte actually pulled back out, which suits backups or older records that must stay quickly reachable but aren't read often — restoring a large volume of IA data at once can erase the storage savings if that access-frequency assumption turns out wrong; One Zone-IA drops the price further by keeping only a single copy in one Availability Zone, a fair trade for data that's easy to regenerate. When an access pattern is unpredictable rather than simply aging, S3 Intelligent-Tiering watches each object and slides it between frequent, infrequent, and archive tiers automatically for a small monitoring fee, with no retrieval charge at all. For data that just needs to be kept and rarely, if ever, touched, the Glacier tiers push cost down further still in exchange for minutes-to-hours retrieval times. An S3 Lifecycle configuration is what actually drives all of this without a person moving objects by hand: rules can transition objects from Standard to IA to Glacier on a schedule tied to their age, and separately expire objects outright once they pass a defined retention point, so a bucket's average cost per gigabyte falls automatically as the data inside it ages.

### EBS volume types: matching SSD and HDD performance to workload cost

Amazon EBS offers several volume families that trade IOPS, throughput, and price against each other, and picking the wrong one either overpays for performance nobody needs or starves a workload that needed more. General Purpose SSD (gp3) is the default starting point for boot volumes and most transactional workloads, and unlike its predecessor gp2 it lets you dial in IOPS and throughput independently of the volume's size for a flat price, rather than having size alone determine the performance ceiling. Provisioned IOPS SSD (io1 and io2, including the higher-end io2 Block Express) exists for the workloads gp3 can't satisfy — large, latency-sensitive database engines that need a guaranteed, sustained IOPS number well above what gp3 tops out at — and that guarantee is what you're paying the premium for. On the other end, the two HDD families skip IOPS entirely and price themselves around throughput: Throughput Optimized HDD (st1) suits big-data processing, log ingestion, and data-warehouse scans that stream large sequential reads, while Cold HDD (sc1) trades away even more performance for the lowest per-gigabyte price EBS offers, fitting data that's accessed rarely but still needs to sit on an attached volume rather than in object storage. Neither HDD type can serve as a boot volume, which is itself a useful exam signal for recognizing when a described workload has picked the wrong family. Sizing any of these volumes correctly is a separate step from picking the family: a gp3 volume billed at a flat rate regardless of size gains nothing from being provisioned larger than the dataset and its growth headroom actually require, and an io1 or io2 volume provisioned for an IOPS number well above what the workload's measured I/O ever reaches is paying for guaranteed performance that never gets used — the right approach is watching actual utilized IOPS, throughput, and free space over time and adjusting the volume to match, rather than sizing once at launch and leaving it fixed indefinitely.

### Choosing among S3, EFS, and FSx by storage type and workload fit

Before comparing specific services, a cost-optimized storage design starts by recognizing which of the three storage shapes a workload actually needs. Object storage (Amazon S3) holds whole files addressed by key rather than a byte-range, scales to any size at the lowest cost per gigabyte of the three, and fits static assets, backups, data-lake content, and anything an application reads and writes as complete objects over HTTP. File storage (Amazon EFS) presents a shared, POSIX-compliant NFS mount that many EC2 instances, containers, or Lambda functions can attach to at once and grows or shrinks its billed capacity automatically as files are added or removed, which fits shared home directories, content-management systems, and container workloads that need a common filesystem without anyone provisioning capacity ahead of time. Amazon FSx wraps a handful of purpose-built, fully managed third-party file systems — FSx for Windows File Server for SMB shares serving Windows workloads, FSx for Lustre for high-throughput HPC and machine-learning training, FSx for NetApp ONTAP and FSx for OpenZFS for teams standardized on those platforms — and is the right call specifically when an application depends on native compatibility with one of those systems rather than a generic NFS mount. Reaching for FSx or EFS for data that's really just files an application could read as S3 objects means paying for filesystem semantics a workload never uses.

### Moving data into AWS storage at the lowest cost: DataSync, Transfer Family, and Storage Gateway

Getting existing data into AWS storage cheaply is a separate design question from picking the target storage service, and the right transfer tool depends on how the source system already talks to data. AWS DataSync suits a one-time or recurring bulk move from an on-premises NFS, SMB, or HDFS share (or another cloud's object storage) into S3, EFS, or FSx: it parallelizes the copy well beyond what a generic script achieves and checksums the data automatically, so a scheduled nightly DataSync task is typically the cheapest and most reliable way to keep a data lake fed from an on-premises source. AWS Transfer Family instead fits when external partners or internal tools need to keep pushing files over SFTP, FTPS, FTP, or AS2 exactly as they do today; it terminates those managed endpoints and drops the files straight into S3 or EFS, avoiding the cost and operational burden of running and patching a fleet of file-transfer servers. AWS Storage Gateway solves a third case — an existing application that can't be rewritten to call S3 directly but still needs its data to end up there — by presenting a local-looking NFS/SMB share, iSCSI volume, or virtual tape library that's actually backed by S3 (and EBS snapshots or Glacier) behind the scenes. For a large one-time migration, batching uploads rather than sending objects one at a time cuts per-request charges and transfer time alike, which is why bulk tools like these usually beat hand-rolled, per-object copy loops on cost.

### Designing backup and archival strategies around retention and access frequency

A cost-aware backup design starts from how long data must be kept and how likely it is to actually be restored, not from backing everything up the same way by default. AWS Backup centralizes this by letting you define a backup plan once — a schedule, a retention window, and a lifecycle rule that moves older recovery points into cold storage automatically — and apply that single plan across EBS volumes, RDS and Aurora databases, DynamoDB tables, EFS file systems, and more, rather than hand-configuring snapshot schedules service by service. Recovery points that must satisfy a compliance retention period but are almost never restored are exactly what the lifecycle-to-cold-storage transition exists for: keeping them on standard backup storage past the point anyone expects to touch them just pays a higher rate for the same durability. The archival side of the same question is answered by the S3 Glacier storage classes for anything that isn't a structured database snapshot in the first place — raw files, exports, or media kept purely to satisfy a retention requirement belong there rather than in S3 Standard. Picking the right combination — how often a recovery point is taken, how long each one is kept before it either expires or drops to colder storage, and whether the underlying data even needs backup-service semantics versus plain archival storage — is what keeps a backup strategy's cost proportional to the risk it actually covers.

### Cost visibility and governance: Requester Pays, tags, consolidated billing, and the AWS cost tools

Several storage-adjacent settings exist purely to control who pays and how spending gets tracked, separate from which storage service is chosen. Turning on Requester Pays for an S3 bucket shifts data-transfer and request charges from the bucket owner onto whoever downloads the objects, which is the standard pattern for a team distributing a large public or shared dataset without absorbing everyone else's download costs. Cost allocation tags let every resource carry a project, team, or environment label that AWS Cost Explorer and the Cost and Usage Report can then group and filter by, turning a single combined bill into a per-team or per-workload breakdown; AWS Organizations' consolidated billing extends the same idea across a multi-account setup, rolling linked accounts' usage into one bill so volume pricing tiers and shared Reserved Instance or Savings Plans discounts apply across the whole organization instead of resetting per account. Cost Explorer itself is the day-to-day tool for visualizing spend trends and getting Reserved Instance or Savings Plans purchase recommendations, AWS Budgets adds proactive alerts (and optional automated actions) when spend or usage crosses a threshold you set, and the Cost and Usage Report provides the most granular, line-item export for teams that need to pipe billing data into their own analysis. Knowing when a storage tier needs auto scaling versus a fixed size matters here too: S3 and EFS bill for exactly what's stored with no capacity to plan ahead of time, while an EBS volume's provisioned size and IOPS are fixed until someone (or an automated process) resizes them.

## Task 4.2: Design cost-optimized compute solutions

### EC2 purchasing options: On-Demand, Reserved Instances, Savings Plans, and Spot

On-Demand pricing — billed by the second with no upfront commitment — is the right default for a workload whose size or duration isn't yet known, but it's also the most expensive way to run anything that's actually steady and predictable. Once a baseline level of usage is well understood, committing to it unlocks a substantial discount: Reserved Instances lock in a specific instance family, size, and Region for a one- or three-year term, while Savings Plans instead commit to a dollar-per-hour amount of compute spend and apply that discount automatically across whichever instance family, size, OS, or Region the usage actually lands in, and even extend to Fargate and Lambda usage — which makes Savings Plans the more flexible of the two for a workload whose shape might shift over the commitment term. Spot Instances take the opposite approach entirely, requesting spare EC2 capacity for a discount that can reach roughly 90% off On-Demand in exchange for accepting a two-minute interruption warning whenever AWS needs that capacity back, which fits fault-tolerant, flexible workloads like batch processing, CI pipelines, or stateless horizontal fleets far better than anything holding session state or serving synchronous requests. A mature cost design typically blends layers — a Savings Plan or Reserved Instance baseline sized to the workload's floor, topped up with On-Demand or Spot for the variable portion above that floor — rather than committing everything to one purchasing model. AWS Cost Explorer generates Reserved Instance and Savings Plans purchase recommendations straight from historical usage, AWS Budgets can raise an alert the moment RI or Savings Plans utilization or coverage slips below a target, and tagging compute resources by team or environment feeds those same purchases into the cost allocation and Cost and Usage Report breakdowns a finance team relies on; AWS Organizations' consolidated billing then pools every linked account's usage against one shared set of commitment discounts instead of forcing each account to buy its own.

### Right-sizing: instance families and sizes for the workload's dominant resource

EC2 instance types group into families built around a dominant resource — general purpose for a balanced mix, compute optimized for CPU-bound work like batch processing or gaming servers, memory optimized for in-memory databases and caching layers, storage optimized for workloads driven by local disk throughput, and accelerated computing for GPU or specialized-hardware needs — and picking the family that matches a workload's actual bottleneck avoids paying for capacity in a dimension that was never going to be used. Within a chosen family, sizes scale vCPU count, memory, and price together in roughly linear steps, so the exercise of right-sizing is really about matching observed CPU and memory utilization to the smallest size that still leaves comfortable headroom, rather than defaulting to a larger size out of caution. Oversizing shows up on the bill directly as unused, paid-for capacity, while undersizing shows up as throttling or degraded performance that eventually forces a resize anyway — both point to the same conclusion, that ongoing utilization monitoring (not a one-time launch-day guess) is what keeps instance sizing matched to a workload's real footprint as that workload's traffic evolves over its lifetime. The same instance family and size can also carry a different On-Demand price from one AWS Region to the next, so a workload without a hard latency or data-residency reason to sit in a specific Region can sometimes cut cost simply by running in a cheaper one; within a Region, spreading a fleet's baseline size across multiple Availability Zones for redundancy is a cost tradeoff too, since each additional AZ's worth of standby capacity is instance-hours paid for whether or not a failure ever calls on it.

### Optimizing compute utilization with containers, serverless, and microservices

A monolithic application sized for its own peak load leaves a lot of paid-for capacity idle outside that peak, and the main way to cut that waste is to shrink the unit of compute that has to be provisioned in the first place. Splitting a monolith into microservices lets each service scale to its own demand curve independently, so a rarely called component doesn't force the whole application to run at the size its busiest component needs. Running those services in containers on ECS or EKS improves the density of a given EC2 fleet by packing multiple tasks onto shared instances, while placing those same containers on Fargate removes host management and bills per task rather than per whole instance, which suits workloads whose per-service resource needs don't cleanly divide into fixed EC2 sizes. AWS Lambda pushes the same idea furthest: it bills per invocation and per millisecond of execution with nothing to pay when a function isn't running, which makes it the cheapest option for event-driven or bursty work with meaningful idle time between invocations, though a function that runs near-continuously at high volume can end up costing more than an equivalently sized EC2 or Fargate task running the same workload steadily. The right point on that spectrum — Lambda, Fargate, or EC2 — comes down to how continuous the workload's traffic actually is.

### Scaling strategies for cost: Auto Scaling, horizontal vs. vertical scaling, and hibernation

EC2 Auto Scaling keeps a fleet's size tracking real demand rather than a fixed guess, using target-tracking policies that add or remove instances against a metric like average CPU, scheduled policies for predictable daily or weekly traffic patterns, and predictive scaling that provisions ahead of an anticipated spike instead of reacting after it starts — all of which keeps a fleet from sitting oversized during quiet periods just to be ready for a peak. Scaling horizontally, by changing the number of instances in a fleet, generally beats scaling vertically, by resizing a single larger instance, for cost-sensitive elastic workloads: a horizontal fleet can shrink back down to a small baseline the moment demand drops, while a vertically sized instance keeps paying for its larger size until someone manually resizes it back down. EC2 hibernation offers a middle path for workloads that don't need to be running continuously but also can't tolerate a slow cold start: hibernating an instance saves its in-memory state to the attached EBS volume and stops it, so you stop paying for compute entirely while it's hibernated, and resuming it restores that saved memory state far faster than booting and reinitializing the application from scratch — a good fit for infrequently used development or specialized workstation instances with a heavyweight startup process.

### Selecting a load balancer type and sizing availability to the workload's tier

Elastic Load Balancing's three types map to different cost and routing needs. An Application Load Balancer (Layer 7) is the natural fit whenever routing decisions depend on the content of the request itself — host headers or URL paths — because a single ALB can route to many backend services through separate target groups, which is more cost-efficient than standing up a dedicated load balancer per microservice. A Network Load Balancer (Layer 4) is built for extremely high throughput and the lowest possible latency at the connection level, which fits non-HTTP protocols or workloads where every microsecond matters more than content-based routing. A Gateway Load Balancer sits apart from both, transparently inserting third-party security or inspection appliances into a traffic path. Separate from load balancer choice, matching a workload's availability tier to its actual business importance is itself a major cost lever: a production workload generally justifies multiple Availability Zones, redundant instances, and a Reserved Instance or Savings Plan baseline, while a non-production workload — development, test, or staging — can often run in a single Availability Zone, on Spot Instances, at a smaller instance size, and even be scheduled to stop outside business hours, since the cost of an outage there is far lower than in production and doesn't justify paying for production-grade redundancy.

### Hybrid and edge compute: AWS Outposts and distributed processing

Not every workload can move fully into an AWS Region — some need to keep processing physically on-premises for latency reasons, local data-residency requirements, or dependence on on-site equipment — and AWS Outposts addresses that by delivering AWS-managed compute and storage racks into a customer's own data center, extending the same APIs, instance types, and tooling used in the cloud to hardware that sits on-site. The cost case for Outposts specifically applies to a workload that would otherwise force a choice between running everything on general-purpose on-premises infrastructure (with its own procurement and operations overhead) or accepting a latency penalty from placing it fully in a distant Region; it's a poor fit for anything that could run in a standard Region without a real latency or residency constraint, since it carries its own subscription cost on top of that constraint. Distributed and edge processing options — Lambda@Edge and CloudFront Functions running code at CloudFront edge locations, AWS IoT Greengrass running logic on local devices — solve a related but smaller-scale problem by pushing computation close to end users or devices, which cuts both the data volume that has to travel back to a central Region and the size of the central compute fleet needed to process it there.

## Task 4.3: Design cost-optimized database solutions

### Relational vs. non-relational selection, and choosing between engines

The relational-versus-non-relational decision has a direct cost dimension on top of its access-pattern one: a relational engine on RDS or Aurora keeps an instance running continuously and bills for that instance's size regardless of query volume, while DynamoDB has no per-instance cost at all — it bills for the throughput and storage actually consumed, which suits workloads with simple key-based access patterns and avoids paying for idle database capacity during quiet periods. Within the relational world, the choice between engines like MySQL and PostgreSQL on RDS or Aurora often comes down to which one the application and its ecosystem of drivers, extensions, or existing procedural code already assume, since moving between them (or from a commercial engine to either one) means a heterogeneous migration rather than a like-for-like copy. That distinction matters directly for cost: MySQL and PostgreSQL are open-source engines with no per-vCPU licensing fee, while commercial engines carry License Included pricing on top of the instance cost, so migrating a workload that doesn't depend on a commercial engine's proprietary features onto an open-source engine is one of the more direct ways to cut a database's baseline cost. Determining the appropriate engine is therefore as much about existing licensing exposure as it is about SQL dialect compatibility.

### Database capacity planning and serverless options for variable demand

DynamoDB's two capacity modes trade planning effort for cost in opposite directions: on-demand mode bills per request with nothing to configure ahead of time, which fits workloads with spiky or hard-to-forecast traffic, while provisioned mode has you set target read and write capacity units up front — optionally paired with auto scaling of that provisioned target — at a lower per-unit rate that pays off once traffic is steady enough to forecast accurately; guessing wrong on provisioned capacity means either paying for unused throughput or getting throttled, so the mode choice itself is a cost decision, not just an operational one. Aurora Serverless v2 answers the equivalent question on the relational side by scaling a database's capacity, measured in Aurora Capacity Units, up and down automatically to track actual load in fine-grained increments, which removes the need to provision a fixed instance size for a workload whose demand varies through the day or across environments (a dev database that sits idle most of the time being a common case). Cost allocation tags and consolidated billing apply here just as they do elsewhere: tagging database resources by team or project lets Cost Explorer and the Cost and Usage Report break out exactly how much of the bill each database is responsible for, and a multi-account setup shares Reserved Instance and Savings Plans discounts on database instance usage across every linked account rather than resetting per account.

### Cutting database cost with a caching layer: ElastiCache and DAX

Adding a cache in front of a database is one of the highest-leverage cost moves available once an access pattern skews toward a relatively small set of hot data being read repeatedly, because every read a cache absorbs is a read the underlying database never has to serve — which means a smaller, cheaper database instance (or a lower DynamoDB provisioned capacity) can support the same overall traffic. Amazon ElastiCache runs a managed in-memory store in front of a relational or non-relational database and is available as a serverless cache that scales memory and bandwidth on its own, or as node-based clusters when a team wants direct control over node type and count. Amazon DynamoDB Accelerator (DAX) offers the DynamoDB-specific version of the same pattern, cutting response times from milliseconds to microseconds while handling cache population and invalidation automatically. Whether a caching layer is worth its own added cost depends entirely on how concentrated the read traffic actually is — a workload where a small slice of records accounts for most reads sees a large drop in database load per dollar spent on cache, while a workload with uniformly spread-out reads gains far less from the same investment.

### Managing connections cost-effectively with Amazon RDS Proxy

A relational database instance has to hold open every connection made to it, and each open connection consumes memory and CPU whether or not it's actively doing work, which means a burst of short-lived connections from Lambda functions or an auto-scaled application fleet can force a team into a larger, pricier instance size purely to survive the connection overhead rather than the actual query load. Amazon RDS Proxy sits between the application and the database, pooling and reusing a bounded set of real database connections while serving a much larger number of client-side connections against that pool, which lets a smaller database instance handle a connection-heavy workload that would otherwise have forced an upsize. Because the proxy also queues or sheds excess connection attempts instead of letting them overwhelm the database directly, it avoids a failure mode where connection pressure alone (independent of query volume) is what drives the perceived need for more expensive database capacity. RDS Proxy is billed separately per vCPU-hour of the underlying database it proxies, so the decision to use it is a straightforward comparison between that added proxy cost and the cost of the larger database instance it lets you avoid.

### Read replicas and replication as a cheaper alternative to scaling up

When a relational database's bottleneck is read traffic rather than write traffic, adding one or more read replicas is typically cheaper than resizing the primary instance to a larger class, because a read-heavy load can be spread across several smaller, less expensive replica instances instead of concentrating it on one larger instance sized to handle everything. RDS and Aurora both support read replicas, with Aurora additionally offering Aurora Auto Scaling to add and remove Aurora Replicas automatically against a target metric like CPU or connection count, which keeps the replica fleet — and its cost — tracking actual read demand rather than sitting fixed at a peak size. A replica also does double duty as a lower-cost disaster-recovery option, since it can be promoted to a standalone primary if the original instance is lost, though a design that specifically needs a dedicated failover target as well as extra read capacity typically pairs a Multi-AZ standby (kept purely for failover, never serving reads) with separate read replicas rather than relying on replicas alone for both jobs. Recognizing that read replicas solve a read-scaling and cost problem, distinct from what a Multi-AZ standby solves, is what keeps a design from either overpaying for a standby it doesn't need or underprovisioning read capacity it does.

### Backup and retention policy design, and cost-effective engine types for analytics

A backup and retention policy has direct cost consequences through two levers: how often a snapshot is taken, and how long each one is kept before it's deleted. RDS and Aurora support automated backups with a configurable retention window (up to 35 days) plus on-demand manual snapshots that persist until explicitly removed, while DynamoDB offers point-in-time recovery over a rolling 35-day window alongside on-demand backups that likewise persist indefinitely until deleted — in both cases, a retention policy longer than what compliance or recovery objectives actually require is paying for storage that no restore is ever likely to use. Migrating a database's schema and data — whether between Regions, between accounts, or to a different engine entirely — follows the same homogeneous-versus-heterogeneous distinction covered above: a homogeneous move (same engine, different location) is mostly a data-movement exercise with AWS Database Migration Service, while a heterogeneous move (different engine) needs schema conversion first, commonly through the AWS Schema Conversion Tool. On the analytics side, matching the database type to the query shape carries its own cost weight: a columnar engine like Amazon Redshift reads only the columns a query touches and compresses similar values well, which cuts the compute needed for large analytical scans compared with a row-oriented relational database, while a purpose-built time-series database such as Amazon Timestream automatically tiers older data to cheaper storage and prices itself around ingested and queried data volume rather than a fixed always-on instance, which fits time-stamped metrics or IoT data far more cheaply than forcing that same data into a general-purpose relational table.

## Task 4.4: Design cost-optimized network architectures

### NAT gateway cost models: shared vs. per-AZ, and NAT gateway vs. NAT instance

A NAT gateway lets instances in a private subnet reach the internet or other networks without accepting unsolicited inbound connections, and it bills on two dimensions at once — an hourly charge for the gateway itself, plus a per-gigabyte charge for every byte it processes — which makes its placement a real cost decision, not just a redundancy one. A single NAT gateway shared by every private subnet across all Availability Zones in a VPC is the cheapest configuration in hourly terms, but it concentrates all outbound traffic through one AZ, which means instances in other AZs pay cross-AZ data transfer charges on top of the NAT processing charge just to reach it, and it becomes a single point of failure if that AZ has a problem. Deploying one NAT gateway per Availability Zone instead removes both of those costs — no cross-AZ hop for outbound traffic, and no single AZ failure taking down egress for the whole VPC — at the price of paying the hourly charge multiple times over. Running a self-managed NAT instance on EC2 is the older alternative: it avoids the per-gigabyte NAT processing charge entirely, but replaces it with the ongoing cost and operational burden of an EC2 instance that you have to size, patch, and scale yourself, which rarely wins on total cost once the operational overhead is counted honestly.

### Choosing private connectivity: Direct Connect, VPN, and the public internet

Reaching AWS from an on-premises network over the plain internet costs nothing extra for the connection itself but leaves performance and reliability to normal internet conditions, so it's rarely the right choice once a workload needs consistent throughput or latency. AWS Site-to-Site VPN encrypts traffic over that same public internet path through IPsec tunnels, billed per connection-hour plus data processed, and can typically be stood up in hours rather than weeks, which makes it the fast, low-commitment option for moderate or variable traffic volumes, or as an encrypted backup path alongside something more dedicated. AWS Direct Connect instead runs a dedicated physical connection from an on-premises router into an AWS Direct Connect location, bypassing the internet entirely for steadier bandwidth and materially lower per-gigabyte data transfer rates than internet-based paths — the tradeoff is a longer physical provisioning lead time and a higher fixed cost, which only pays for itself once sustained transfer volume is large enough to amortize that fixed cost below what the same volume would cost over a VPN or the internet. Bandwidth allocation follows the same logic: Direct Connect is offered at a range of port speeds from hosted connections in the tens of megabits up through dedicated connections at 100 Gbps, and choosing a single large connection versus several smaller ones (or a single VPN versus multiple) trades some redundancy for a simpler, usually cheaper bill — a pattern commonly rounded out by running Direct Connect as the primary path with a Site-to-Site VPN as its low-cost, encrypted failover.

### Network routing, topology, and peering: VPC peering vs. Transit Gateway

A VPC peering connection is free to create and carries no charge at all for traffic that stays within a single Availability Zone, which makes it a genuinely no-cost way to connect a small number of VPCs directly — but a peering connection is never transitive, so connecting many VPCs to each other this way requires a full mesh of individual connections that grows quadratically and quickly becomes unmanageable as the VPC count rises, on top of cross-AZ or cross-Region peered traffic still being billed as data transfer. AWS Transit Gateway solves the topology problem by acting as a central routing hub that every VPC, VPN connection, and Direct Connect link attaches to once, replacing that ever-growing mesh with a single hub-and-spoke design and a shared route table — at the cost of an hourly charge per attachment plus a per-gigabyte charge for data it processes, on top of what peering would have cost for the same traffic. For a handful of VPCs, plain peering is close to free and simpler to reason about; past roughly half a dozen VPCs needing to talk to each other and to on-premises networks, a transit gateway's per-attachment cost is usually offset by no longer having to manage (or later untangle) a dense mesh of point-to-point connections, which is the crossover a cost-optimized network design is really weighing.

### Minimizing data transfer costs across Regions, Availability Zones, and network paths

AWS prices data transfer differently depending on the path it travels, and a cost-optimized network design is largely about steering traffic onto the cheapest available path for a given hop. Traffic that stays within the same Availability Zone over private IP addresses is free, traffic crossing Availability Zones within a Region is billed but at a lower rate than traffic crossing Regions entirely, and traffic that leaves AWS to the public internet is generally the most expensive tier of all — which is why placing tightly coupled, high-volume tiers of an application in the same AZ, and keeping AWS-to-AWS traffic on private paths instead of routing it out to the internet and back, are both direct cost levers rather than just performance ones. VPC endpoints put that principle into practice for traffic to AWS services: a Gateway endpoint reaches S3 or DynamoDB over private IP addresses at no charge at all, avoiding both the NAT gateway processing fee and any internet-path data transfer charge that traffic would otherwise incur, while an Interface endpoint (built on AWS PrivateLink) does the same for a much broader set of services at an hourly and per-gigabyte rate that's still typically cheaper than routing the equivalent traffic through a NAT gateway. AWS Global Accelerator takes a different angle on the same routing decision: it keeps traffic on the AWS global network from the point it enters rather than letting it cross the public internet toward a distant Region, which is a genuine latency and failover win, but it layers its own premium data-transfer rate and hourly accelerator charge on top of standard pricing — so it earns its cost on reliability and routing control for latency-sensitive, multi-Region traffic rather than on shrinking the data-transfer bill itself. Reviewing an existing workload's traffic flows against this pricing structure — which hops cross an AZ or Region boundary, which ones touch the public internet unnecessarily — is usually how these savings get found in the first place. Tagging the resources on each side of an expensive path (a NAT gateway, a Transit Gateway attachment, a cross-Region link) lets AWS Cost Explorer and the Cost and Usage Report attribute data-transfer spend to the specific workload or team generating it, AWS Budgets can flag a tagged workload's transfer costs the moment they climb past a set threshold, and consolidated billing across an AWS Organizations setup means every linked account's data-transfer volume counts toward the same discount tiers instead of each account being billed as if it stood alone.

### CDN and edge caching strategy with CloudFront, and DNS routing with Route 53

Amazon CloudFront caches content at edge locations distributed globally, so repeat requests for the same content are answered from a nearby edge instead of traveling back to the origin every time, which cuts data-transfer cost on two fronts at once: the origin (an S3 bucket or an application server) sees far fewer requests and serves far less data directly, and content delivered out of a CloudFront edge is generally priced lower than the same volume served straight out of an origin like EC2 or an Application Load Balancer. Deciding whether a workload needs a CDN in front of it comes down to how cacheable its content actually is and how geographically spread its users are — a workload serving the same static or semi-static content to a wide, distributed audience benefits heavily, while content that's unique per request and never cacheable gains little beyond CloudFront's connection reuse and edge termination. Amazon Route 53 handles the DNS side of the same goal: routing policies such as latency-based or geolocation routing send users to whichever regional endpoint serves them fastest, and health checks tied to those policies redirect traffic away from an unhealthy endpoint automatically, at a cost (billed per hosted zone, per query, and per health check) that's typically a small fraction of the data-transfer and compute savings a well-designed routing and caching strategy delivers elsewhere in the architecture.

### Throttling strategy and bandwidth allocation as protection against runaway cost

Without a throttling strategy, an API or ingestion pipeline has to be sized (and paid for) against its worst-case burst rather than its typical load, since nothing stops a traffic spike, a retry storm, or an abusive client from driving backend compute or database capacity far past what normal usage requires. API Gateway usage plans apply per-client rate and burst limits, rejecting excess requests before they ever reach backend compute, which lets that backend be sized for its expected load instead of an unbounded worst case. The same principle extends to how load balancer types are matched to a workload: an Application Load Balancer's content-based routing consolidates many backend services behind one load balancer at Layer 7, which is more cost-efficient than provisioning a dedicated load balancer per service, while workloads that route on relatively static traffic patterns can lean on Auto Scaling instead of a fixed overprovisioned fleet to absorb load spikes. Bandwidth allocation decisions carry the same logic on the connectivity side discussed earlier — choosing a single sufficiently sized VPN or Direct Connect connection instead of several smaller, redundant ones (or the reverse, when redundancy matters more than unit cost) is fundamentally about not paying for network capacity that a workload's actual traffic pattern will never use.
