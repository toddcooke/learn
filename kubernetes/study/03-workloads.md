## Deployments, rolling updates, and rollbacks

### How a Deployment reconciles Pods through the ReplicaSets it owns

A Deployment doesn't manage Pods directly — it describes a desired Pod template and replica count, and the Deployment controller drives the cluster toward that state by creating and owning ReplicaSets that in turn create the actual Pods. Applying a Deployment for the first time makes the controller create one ReplicaSet, named by appending a hash of the Pod template to the Deployment's name, and scale it up to the requested replica count. That hash is stamped onto every child ReplicaSet and Pod through a dedicated pod-template-hash label, which is how the controller distinguishes a Deployment's own ReplicaSets from one another and keeps them from fighting over the same Pods; hand-editing that value is explicitly discouraged. Because a Deployment only ever talks to the API server about ReplicaSets and leaves individual Pods to the ReplicaSet controller, day-to-day Deployment work — scaling, updating an image, checking rollout status — never requires touching a ReplicaSet object directly, and doing so anyway is generally discouraged.

### What actually triggers a new rollout

A Deployment's revision history only grows, and a rollout only starts, when its Pod template (.spec.template) changes — updating a container's image or the Pod template's own labels are the two most common triggers. Purely operational changes such as scaling the replica count up or down, by contrast, create no new revision and start no rollout; the existing ReplicaSet is simply resized in place. This split matters for two practical reasons: it lets you scale a Deployment manually, or hand scaling off to a HorizontalPodAutoscaler, without accidentally kicking off an unrelated image rollout, and it's why rolling a Deployment back to some prior point in its history reverts only the Pod template portion of its spec — a manual scaling change made in between is left untouched by that rollback.

### Controlling the pace of a rolling update with maxUnavailable and maxSurge

The default RollingUpdate strategy replaces Pods gradually instead of all at once, and two fields under .spec.strategy.rollingUpdate govern how aggressively it does so. maxUnavailable caps how many of the desired Pods can be missing at any point during the rollout, and maxSurge caps how many extra Pods beyond the desired count can exist temporarily; both default to 25%, both accept an absolute number or a percentage, and maxUnavailable rounds its percentage down while maxSurge rounds its up. Neither field can be set to zero while the other is also zero, since that would leave no room to replace anything at all. If a Deployment is scaled — manually or by an autoscaler — while a rollout is already underway, the controller doesn't dump every new replica into the newest ReplicaSet; proportional scaling spreads the additional replicas across all currently active ReplicaSets, weighted toward whichever already holds more Pods, so the rollout keeps converging on the new template rather than stalling.

### Recreate vs RollingUpdate, and catching a stalled rollout

Setting .spec.strategy.type to Recreate abandons gradual replacement entirely: every existing Pod is terminated first, and only once all of them are gone does the Deployment begin creating Pods from the new template, which guarantees old and new versions never run side by side but does mean a window with no Pods running at all. RollingUpdate, the default, avoids that gap but can still get stuck — a rollout that can't make progress because of a bad image, a failing readiness probe, or exhausted quota is caught by .spec.progressDeadlineSeconds, 600 seconds by default. Once that deadline elapses with no progress, the controller sets a Progressing condition to status False with reason ProgressDeadlineExceeded, and checking the rollout with kubectl rollout status reports failure through its exit status; deliberately pausing a Deployment suspends that deadline check entirely, so a paused rollout is never flagged as stalled no matter how long it sits.

### Rolling back to an earlier revision

Every retained Deployment revision's configuration lives inside the ReplicaSet that revision created, which is why .spec.revisionHistoryLimit — 10 by default — matters in practice: once an old ReplicaSet is garbage-collected past that limit, rolling back to the revision it represented is no longer possible, and setting the limit to 0 disables rollback for that Deployment altogether. kubectl rollout history deployment/`<name>` lists the revisions still on hand, each optionally tagged with a change-cause message set through the kubernetes.io/change-cause annotation, and kubectl rollout undo reverts to the immediately preceding revision or, with --to-revision, to a specific one further back. A rollback is implemented the same way any forward rollout is — the controller scales the target revision's ReplicaSet back up while scaling the current one down — and a Deployment that is currently paused cannot be rolled back until it has first been resumed.

### Pausing rollouts, and why the label selector is locked after creation

kubectl rollout pause lets several edits accumulate on a Deployment's Pod template — a new image, revised resource requests, and so on — without each one separately triggering a rollout; nothing new rolls out until kubectl rollout resume is run, at which point one new ReplicaSet picks up every accumulated change at once. Separately, .spec.selector becomes immutable the moment a Deployment is created under apps/v1, and none of the usual update paths — kubectl's patch, edit, or apply subcommands, nor a Helm upgrade — are able to change it; selecting a different set of Pods means tearing the Deployment down and standing up a fresh one in its place. The rationale traces back to the pre-apps/v1 API versions that still permitted selector updates: removing a label key was a safe, overlapping change that simply let the existing ReplicaSet keep matching what it already matched, but adding a key or changing an existing key's value was a non-overlapping change that orphaned the old ReplicaSet and its Pods and forced a brand-new ReplicaSet into existence — exactly the kind of silent orphaning apps/v1's immutability rule now rules out entirely.

## Configuring applications with ConfigMaps and Secrets

### ConfigMap's role and data model

A ConfigMap holds non-confidential configuration as key-value pairs, letting an environment-specific setting — say, a database hostname that's localhost in development and a Service name once deployed — live outside the container image, so the exact same image runs unmodified everywhere. Unlike most Kubernetes objects, a ConfigMap has no spec section at all; its payload sits directly under a data field for UTF-8 string values and an optional binaryData field for base64-encoded binary values, and one ConfigMap can freely mix short property-style entries with longer, file-like blocks. The API caps a ConfigMap at 1 MiB total specifically to discourage using it as a stand-in for a real file store or database, and a ConfigMap can only configure Pods sitting in its own namespace, with the one exception being application code that reads it straight through the Kubernetes API rather than through the kubelet's normal Pod-launch machinery.

### Four ways to feed ConfigMap data into a container, and how updates propagate

A Pod can pull ConfigMap values into a container's command-line arguments, into individual environment variables through configMapKeyRef, into every key at once through envFrom's configMapRef, or as files inside a mounted read-only volume where each key becomes its own filename — or a chosen subset of them, if the volume's items list narrows things down. A less common fifth path is application code calling the Kubernetes API directly, which is also the only route that lets a workload watch for live changes or read a ConfigMap sitting in a different namespace. These paths differ sharply in how current they stay: the kubelet keeps a periodically-refreshed local cache of mounted ConfigMaps, so a volume's files do eventually catch up to an edit, with the exact lag depending on the sync period plus whichever cache strategy — watch, TTL, or direct polling — the kubelet is configured with, but a ConfigMap value consumed as an environment variable is captured once at container start and never updates without restarting the Pod, and a ConfigMap mounted through subPath doesn't receive live updates at all.

### Secret's built-in types and the move away from long-lived tokens

A Secret is structurally almost identical to a ConfigMap but is meant specifically for sensitive values such as passwords, tokens, and keys, and beyond the generic, default Opaque type, Kubernetes ships several built-in types to standardize common cases: kubernetes.io/tls for a certificate-and-key pair, kubernetes.io/dockerconfigjson for registry credentials, kubernetes.io/basic-auth and kubernetes.io/ssh-auth for those authentication schemes, and kubernetes.io/service-account-token for a ServiceAccount's own credential. That last type is explicitly flagged as a legacy mechanism now: since v1.22, the recommended way to obtain a ServiceAccount credential is a short-lived, automatically-rotating token from the TokenRequest API — through kubectl create token or a projected volume — rather than a persisted, non-expiring Secret, and the docs advise reaching for the Secret-based token only when TokenRequest genuinely isn't an option. Each built-in type carries its own validation, such as a dockerconfigjson Secret needing to parse as valid JSON or a tls Secret needing both tls.crt and tls.key present, but Kubernetes never inspects whether an Opaque Secret's contents are actually sensitive.

### What Kubernetes does — and does not — do to protect Secret data

Secrets get protections a ConfigMap doesn't: the kubelet stores mounted Secret data only in tmpfs on the node rather than on durable disk, it deletes its local copy once no Pod on that node still needs the Secret, and only nodes actually running a Pod that references a given Secret ever receive a copy of it in the first place. The documentation is nonetheless blunt about the limits of that protection: Secrets are stored unencrypted in etcd by default, so anyone with API server or etcd access can read them, and because Kubernetes has no data-level access control finer than the object itself, anyone authorized to create a Pod — or anything that creates Pods on their behalf, like a Deployment — in a namespace can get at every Secret that namespace holds simply by mounting each one into a Pod they control. Granting list or watch on Secrets is equally broad, exposing the namespace's whole Secret collection rather than just the ones a workload explicitly references, and a container that a node lets run in privileged mode can likewise read every Secret used anywhere on that node, regardless of which Pod it belongs to. The documented mitigations are encryption at rest, least-privilege RBAC, and restricting exactly which containers can reach a given Secret.

### Immutable ConfigMaps and Secrets

Setting immutable: true on a ConfigMap or Secret is a one-way switch: once flipped, its data or binaryData can never be edited again, only deleted and recreated, and the immutability itself cannot be reverted either. The payoff is concentrated in clusters that mount huge numbers of these objects — the documentation frames the benefit around clusters with, at minimum, tens of thousands of individual ConfigMap-to-Pod or Secret-to-Pod mount points — because the kubelet no longer has to keep an open watch on anything marked immutable, which measurably cuts load on the API server, on top of the everyday benefit of making it impossible to accidentally push a bad edit into a config object that many running Pods already depend on. Because existing Pods keep their mount point pointing at the deleted object even after a delete-and-recreate cycle, the guidance is to recreate those Pods too rather than assume they'll automatically pick up the replacement.

### Operational edges: static Pods, optional references, and image pull Secrets

Static Pods — the manifest-file-based Pods a kubelet runs without talking to the API server — categorically cannot reference a ConfigMap or a Secret, since resolving either one requires an API call the static-Pod mechanism never makes. For ordinary Pods, marking a referenced Secret or ConfigMap as optional: true tells Kubernetes to simply proceed without it if it doesn't exist, overriding the default behavior of blocking every container in the Pod from starting until all of its non-optional Secrets and ConfigMaps are available; if a Pod instead asks for one specific key inside a Secret that exists but is missing that key, the Pod still fails to start regardless of the optional setting. A separate mechanism, imagePullSecrets, is how a Pod hands the kubelet a registry-credential Secret so it can pull a private image, and rather than repeating that reference on every Pod, it can be attached once to a ServiceAccount so that every Pod created under that ServiceAccount inherits it automatically.

## Self-healing workload primitives: ReplicaSet, StatefulSet, DaemonSet, and Job

### ReplicaSet: the reconciliation loop underneath a Deployment

A ReplicaSet's entire job is to keep a specified number of Pods matching its selector running at all times, creating new ones the moment the count falls short and deleting the extras the moment it's over, and it identifies which Pods belong to it not by name but by a matching label selector plus an ownerReferences entry on the Pod pointing back at the ReplicaSet. That acquisition mechanism cuts both ways: a bare Pod created with no owner reference of its own, if its labels happen to match a ReplicaSet's selector, gets silently adopted by that ReplicaSet and immediately becomes eligible to be scaled down if keeping it would exceed the desired count — exactly why hand-created Pods are warned against ever sharing labels with a ReplicaSet's selector. Kubernetes explicitly recommends against creating or manipulating ReplicaSets directly except in the rare case of needing custom update orchestration, since a ReplicaSet has no native concept of a rolling update at all — that orchestration is precisely what a Deployment layers on top.

### StatefulSet: giving each Pod a durable identity instead of treating them as interchangeable

Where a Deployment's Pods are meant to be indistinguishable from one another, a StatefulSet's Pods each keep a persistent identity — an ordinal index running from 0 through N-1, a stable hostname of the form `<statefulset-name>`-`<ordinal>`, and, when volumeClaimTemplates are defined, a PersistentVolumeClaim dedicated to that specific ordinal — that follows the Pod across any rescheduling instead of being handed off to whichever replacement Pod happens to come up next. The stable-hostname piece depends entirely on a Headless Service, created with clusterIP: None, that the StatefulSet's own spec.serviceName field points at; a StatefulSet never creates that Service on its own, so supplying it is left to the cluster operator. Because the PersistentVolumeClaims generated from volumeClaimTemplates are deliberately left alone when their Pod or the whole StatefulSet is deleted — a data-safety decision rather than an oversight — reclaiming or fully tearing down that storage always requires a separate, manual cleanup step afterward.

### StatefulSet's ordering guarantees, pod management policies, and partitioned rollouts

Under the default OrderedReady pod management policy, a StatefulSet with N replicas creates its Pods one at a time in order from 0 to N-1, waiting for each one to become Running and Ready before starting the next, and tears them down in the exact reverse order, waiting for each successor to fully terminate before touching its predecessor. The Parallel policy discards that sequencing for both scaling and, above a configured maxUnavailable, rolling updates as well, trading strict ordering for faster convergence. A RollingUpdate on a StatefulSet always proceeds from the highest ordinal down to the lowest, and it can be scoped with .spec.updateStrategy.rollingUpdate.partition: any Pod whose ordinal sits below that partition value is left on the old template even if it happens to be deleted and recreated, which is the documented technique for staging a canary or a phased rollout across a StatefulSet's replicas. If an update ever lands a broken Pod template that never becomes Ready, the rollout stalls and, due to a known limitation, won't even attempt to revert to the previous working template until the broken Pod has been deleted by hand first.

### DaemonSet: guaranteeing one Pod per matching node

A DaemonSet exists to run exactly one copy of a Pod on every node that matches its constraints — or on every node in the cluster if no nodeSelector or node affinity is set at all — automatically adding a Pod as new nodes join and garbage-collecting the corresponding Pod once a node leaves. Under the hood, the DaemonSet controller creates each Pod carrying a node affinity term pinned to that one specific node's name, then, in the ordinary case, lets the default scheduler take over and bind it just as it would any other Pod. To let critical, node-level DaemonSet workloads such as a CNI plugin start even on a node that isn't fully healthy yet, the controller automatically attaches a standard set of tolerations covering conditions like not-ready, unreachable, disk-pressure, and unschedulable — sidestepping the chicken-and-egg problem where a node can never become Ready without its networking Pod running, and that Pod can never schedule onto a node that isn't yet Ready.

### Job: running Pods to completion, in one of three parallelism patterns

A Job is built for workloads meant to finish rather than run forever, retrying Pod creation until it has accumulated the number of successful Pod completions it was told to reach, then stopping for good; its Pod template must set restartPolicy to Never or OnFailure, since Always — the default everywhere else in Kubernetes — isn't a valid choice for something designed to terminate. Three shapes are documented for how a Job's work can be structured: a non-parallel Job that runs a single Pod to completion, leaving completions and parallelism both unset in the spec so each falls back to 1; a fixed-completion-count Job whose spec pins completions at however many successful Pods are required, optionally in Indexed completion mode so each Pod is handed a stable 0-based index it can read from a Pod annotation, a Pod label, its own hostname, or the JOB_COMPLETION_INDEX environment variable; and a work-queue Job that leaves .spec.completions unset entirely and instead relies on its Pods coordinating over an external queue to work out, on their own, when the overall task is finished.

### Job failure handling, deadlines, and cleanup

Failed Pods are retried automatically with a doubling backoff delay between attempts, topping out at a six-minute ceiling, until .spec.backoffLimit, 6 by default, is exceeded, at which point the whole Job gets marked as having failed; a .spec.podFailurePolicy can override that default counting by matching specific container exit codes or Pod conditions to one of the actions FailJob, Ignore, Count, or, for indexed Jobs, FailIndex, which is how a Job can be set up to fail fast on a genuine bug while shrugging off Pod failures caused by preemption or eviction instead. Separately, .spec.activeDeadlineSeconds bounds a Job's total wall-clock runtime no matter how many Pods it has created along the way, and it takes precedence over backoffLimit — once the deadline is hit, every running Pod is terminated and the Job is marked Failed with reason DeadlineExceeded, with no automatic restart of the Job afterward. Because finished Jobs and their Pods otherwise stick around indefinitely by default — handy for reading logs, costly for API server load at scale — .spec.ttlSecondsAfterFinished is the documented way to have a TTL controller cascade-delete a finished Job and its Pods automatically once that many seconds have elapsed.

## Workload autoscaling and Pod scheduling admission

### HorizontalPodAutoscaler: what it watches and what it can target

A HorizontalPodAutoscaler doesn't scale Pods directly; it periodically adjusts the replica count of a target workload resource — a Deployment, ReplicaSet, or StatefulSet — through that resource's scale subresource, on an interval set by --horizontal-pod-autoscaler-sync-period (15 seconds by default) rather than continuously. On each sync, the controller resolves the HPA's scaleTargetRef to find its target, uses that target's own .spec.selector to find the Pods currently backing it, and pulls metrics for those Pods from one of three aggregated APIs: metrics.k8s.io for the built-in resource metrics — CPU and memory usage on a per-Pod basis — which is usually served by the Metrics Server add-on, or, for anything outside that built-in set, the separate custom-metrics and external-metrics aggregated API groups, both served via a vendor-supplied adapter. A DaemonSet is explicitly called out as a workload the HPA cannot scale, since a DaemonSet's replica count isn't something anyone sets directly — it's dictated entirely by how many nodes currently match its own constraints.

### How the HPA turns metrics into a replica count

At its core, the algorithm is a simple ratio: desiredReplicas equals currentReplicas multiplied by currentMetricValue divided by desiredMetricValue, rounded up — so Pods averaging 200m against a 100m target double the replica count, and Pods averaging 50m against the same target halve it. Before applying that ratio, the controller filters out Pods that would skew the result: Pods carrying a deletion timestamp and any failed Pods are dropped from per-Pod resource-metric calculations, and Pods that haven't been Ready for long enough — governed by --horizontal-pod-autoscaler-initial-readiness-delay, 30 seconds by default, and --horizontal-pod-autoscaler-cpu-initialization-period, 5 minutes by default — are set aside so a container still warming up doesn't get mistaken for a CPU spike demanding more replicas. A ratio close enough to parity — inside a tolerance band that defaults to 10% and can be adjusted — is treated as noise and produces no scaling action at all, which is the main defense against the HPA thrashing the replica count back and forth over marginal metric fluctuations.

### Tuning HPA behavior, and why it conflicts with a fixed spec.replicas

The autoscaling/v2 behavior field lets scaleUp and scaleDown be configured independently, each combining one or more rate-limiting policies — a maximum number of Pods, or a maximum percentage of current replicas, per time window — with a stabilizationWindowSeconds that smooths out flapping by looking back over recent scaling recommendations and picking whichever one would keep the most replicas running, rather than reacting to only the single latest data point; selectPolicy can be set to Max, Min, or Disabled to control which of several matching policies wins, or to switch off scaling in a given direction entirely. Whatever HorizontalPodAutoscaler gets attached to a Deployment or StatefulSet, the documentation is explicit that .spec.replicas should then be removed from that workload's own manifest — reapplying a manifest that still specifies replicas silently overwrites whatever count the autoscaler had converged on, reintroducing exactly the thrashing behavior the HPA's own smoothing exists to prevent.

### Resource requests and limits: two different enforcement mechanisms

A container's resource request is what the kube-scheduler consults at placement time — it will only bind a Pod to a node if that node's remaining allocatable capacity can cover every container's requests, even when actual usage on the node is currently low, precisely so there is still headroom left for real usage spikes later on. A limit, by contrast, is enforced locally on the node by the kubelet together with the kernel's cgroups, and CPU and memory limits are enforced in fundamentally different ways: a CPU limit works as a hard ceiling that throttling enforces, so a container simply cannot use more CPU time than its limit allows no matter how much capacity is free, while a memory limit is enforced reactively through the kernel's out-of-memory killer, meaning a container can transiently exceed its memory limit right up until the instant the kernel decides to kill it. Setting a limit but leaving the request unset, with nothing else defaulting one, makes Kubernetes copy the limit value and use it as the request too.

### Steering placement with node affinity, and letting Pods attract or repel each other

nodeAffinity generalizes the older, simpler nodeSelector field: a requiredDuringSchedulingIgnoredDuringExecution rule behaves like nodeSelector but with a richer expression language — operators In, NotIn, Exists, and DoesNotExist, plus Gt and Lt for node affinity specifically — while a preferredDuringSchedulingIgnoredDuringExecution rule is a soft preference the scheduler tries to honor, weighted from 1 to 100 and folded into that node's overall placement score, but never one that blocks scheduling outright. When both nodeSelector and nodeAffinity are set on the same Pod, both have to be satisfied at once; across multiple nodeSelectorTerms the terms are OR'd together, while multiple matchExpressions inside a single term are AND'd. A parallel mechanism for affinity and anti-affinity between Pods themselves reuses that same requiredDuringScheduling / preferredDuringScheduling vocabulary to constrain placement relative to Pods already running in a topology domain — expressing rules such as co-locating with Pods labeled security=S1, or never sharing a node with another Pod carrying app=web-store — though the documentation cautions that required anti-affinity rules depend on every node consistently carrying the relevant topologyKey label, and that the feature isn't recommended for clusters larger than a few hundred nodes because of the scheduling overhead it adds.

### ResourceQuota: namespace-wide caps on aggregate consumption

A ResourceQuota constrains total resource consumption across an entire namespace — compute resources such as requests.cpu and limits.memory, storage requests either overall or scoped to a particular StorageClass, and raw object counts such as count/pods or count/secrets — and any request that would push a namespace past one of its quota's hard limits is rejected outright with a 403 Forbidden response. The consequence that trips people up in practice: once a namespace carries a ResourceQuota covering cpu or memory, every new Pod created in that namespace must specify a request or limit for that resource or the API server refuses to admit it, and a LimitRange can be layered in to supply a default automatically so users aren't required to remember to set one themselves. A quota can be narrowed further with scopeSelector to match only a subset of Pods — BestEffort versus Guaranteed/Burstable QoS class, Terminating versus NotTerminating Pods, or Pods tied to a specific PriorityClass — letting an administrator, for instance, cap how much a namespace's low-priority Pods can consume without constraining its high-priority ones at all.
