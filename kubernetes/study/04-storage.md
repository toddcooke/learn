## Implement storage classes and dynamic volume provisioning

### StorageClass objects: naming a storage profile administrators offer

A StorageClass is how a cluster administrator describes one flavor of storage it can hand out — say, a fast tier versus a cheap one, or one with a particular backup arrangement — without Kubernetes itself caring what the distinction actually means; unlike most API kinds, it has no separate spec block, so provisioner, parameters, and reclaimPolicy sit directly on the object. provisioner is mandatory and names which volume plugin actually creates storage for the class; parameters are free-form and interpreted however that provisioner sees fit, capped at 512 entries and 256 KiB total specifically so the field can't be abused as a data store of its own; reclaimPolicy sets what happens to any PV the class dynamically produces once its claim goes away, defaulting to Delete whenever the field is left out entirely. The object's own name is what users reference when requesting that class, so administrators are free to pick names that communicate intent — low-latency, archival, and so on — to the people consuming them.

### Marking a default StorageClass and how PVCs inherit it

Tagging one StorageClass with a storageclass.kubernetes.io/is-default-class value of true means any PersistentVolumeClaim created afterward with no storageClassName field at all automatically falls back to that class; if an administrator carelessly marks more than one class default at the same time, whichever was created most recently wins, though the guidance is to keep exactly one default and treat the multi-default allowance purely as a way to migrate from one default to another without a gap. A PVC can still be created with no storageClassName even when no default exists yet in the cluster — it simply sits with that field unset rather than failing outright. Once a default StorageClass later appears, a stable feature retroactively walks every existing PVC that has no storageClassName set at all and backfills it to point at the new default, but a PVC whose storageClassName was deliberately set to the empty string is left alone by that backfill so it keeps matching only classless PersistentVolumes.

### Internal versus external provisioners, and the shift to CSI

Some provisioners ship as part of Kubernetes itself, historically identified by a kubernetes.io/ prefix, while external provisioners are separate programs, written by anyone, that speak a documented provisioning protocol and can be run and versioned completely independently of the Kubernetes release cycle. NFS is a case where Kubernetes never included a built-in provisioner at all — an external one has always been required. For cloud block storage the trend runs the other direction: the in-tree AWS EBS driver was deprecated in the 1.19 release and stripped out of the codebase entirely by 1.27, and a StorageClass targeting AWS EBS today names the out-of-tree ebs.csi.aws.com CSI driver as its provisioner instead, taking parameters like volume type, IOPS, and encryption that are specific to that driver rather than to Kubernetes. A CSIMigration mechanism keeps this transition mostly invisible to existing configuration — requests aimed at a legacy in-tree plugin name get quietly redirected to the matching CSI driver so StorageClasses, PVs, and PVCs written against the old plugin keep working without being rewritten.

### Controlling when binding happens with volumeBindingMode

volumeBindingMode decides the moment a PersistentVolume actually gets tied to, or created for, a PVC, and Immediate — the default when the field is left unset — does that the instant the PVC is created, before anyone knows which node the consuming Pod will land on; for storage that's only reachable from certain nodes or zones, that early binding can strand a Pod that can never be scheduled next to the volume it was handed. WaitForFirstConsumer instead holds off until a Pod actually references the PVC, letting the scheduler's full view of that Pod's constraints — resource requests, node selectors, affinity and anti-affinity rules, taints and tolerations — steer where the volume ends up. A documented trap: if a Pod pins itself to a node with nodeName rather than a selector while relying on WaitForFirstConsumer, the scheduler is bypassed entirely and the PVC is left pending forever, so a kubernetes.io/hostname nodeSelector is the recommended substitute. allowedTopologies can additionally pin dynamic provisioning to specific zones when that finer control is still needed, though WaitForFirstConsumer alone is usually enough on its own.

### Volume expansion and StorageClass-level mount options

Setting allowVolumeExpansion to true on a StorageClass is what lets a user later request more space for a PVC drawn from that class simply by editing the claim's requested size — the feature only ever grows a volume, never shrinks one, and support depends on the underlying plugin (CSI, plus the deprecated FlexVolume and Portworx types). A class can also carry mountOptions that get applied to every volume it dynamically provisions, but those options are never validated against the class or the PV up front — an invalid one only surfaces later as a failed mount attempt. Local volumes are a special case worth remembering: they can't be dynamically provisioned at all, yet the documentation still recommends creating a StorageClass for them anyway — one using the kubernetes.io/no-provisioner marker — purely so its volumeBindingMode can be set to WaitForFirstConsumer and delay binding decisions until a Pod's full scheduling picture is known.

## Configure volume types, access modes and reclaim policies

### Ephemeral versus persistent volumes, and why bare containers fall short

A container's own writable layer disappears the moment it crashes — the kubelet simply restarts it from a clean image state — which breaks any application that needs to survive that restart or share files with another container in the same Pod; Kubernetes' volume abstraction solves both problems by attaching a directory to the Pod itself, declared under .spec.volumes and mounted into one or more containers through their own volumeMounts entries, with data in any volume type surviving a container restart even though volumes can't be nested inside one another. Ephemeral volume types are scoped to the Pod that defines them and Kubernetes tears them down the moment that Pod goes away, whereas persistent volumes are built to outlive any one Pod that happens to be using them at a given moment, which is the dividing line that determines whether a workload can safely be rescheduled without losing its data.

### emptyDir: throwaway working space that lives and dies with the Pod

An emptyDir volume starts out with nothing in it the moment its Pod is placed on a node, and every container in that Pod can read and write into it, whether they all mount it at the same path or different ones; the volume, and everything in it, is wiped for good only once the Pod itself leaves the node — a container merely crashing doesn't touch it, since the kubelet just restarts the container in place. The medium field decides what backs the volume: leaving it unset stores files on whatever the node's own storage happens to be, while setting it to Memory instead mounts a RAM-backed tmpfs that's much faster to read and write but counts anything written there against the writing container's own memory limit. sizeLimit caps how much of the node's ephemeral storage the volume can consume; without one, a memory-backed emptyDir is instead capped by the node's allocatable memory. Typical uses include scratch space for something like an external merge sort, checkpointing a long-running computation, and handing files from a content-fetching sidecar off to the container actually serving them.

### hostPath: a useful escape hatch with real security tradeoffs

A hostPath volume reaches straight into a file or directory that already exists on the node's own filesystem, which is occasionally exactly what's needed — reading node-level logs, or feeding a static Pod a config file it can't get from a ConfigMap since static Pods can't talk to the API server — but the documentation is blunt that it should be avoided whenever a real alternative like a local PersistentVolume exists. The risk is concrete: a hostPath mount can expose sensitive host material such as kubelet credentials or the container runtime's own socket, opening a path to escaping the container entirely, and a Pod template that behaves fine on one node can behave differently on another purely because the two nodes' local filesystems don't match. The type field lets an administrator require something specific already be there — Directory, File, Socket, CharDevice, BlockDevice — or ask Kubernetes to create a DirectoryOrCreate or FileOrCreate path if nothing exists yet, rather than the default empty-string behavior that skips every check before mounting. hostPath usage also isn't tracked as ephemeral storage the way emptyDir is, so nothing warns an operator when it quietly fills up a node's disk.

### CSI: the out-of-tree standard that most storage now plugs into

The Container Storage Interface gives storage vendors a documented way to ship a driver that Kubernetes can call into without that vendor's code ever being merged into the Kubernetes source tree — the same out-of-tree idea FlexVolume also tried, though FlexVolume is now deprecated in CSI's favor. That matters because the old in-tree model tied support for any new storage backend to Kubernetes' own release schedule; CSI and its predecessor both let a driver be built, released, and upgraded on its own timeline instead. A Pod can consume a csi-backed volume three different ways: through an ordinary PersistentVolumeClaim, as a generic ephemeral volume tied to the Pod's own lifetime, or, if the specific driver supports it, as a CSI ephemeral volume configured directly in the Pod spec. CSI also has stable support for raw block volumes, exposing a device to the Pod with no filesystem layered on top at all for the lowest possible overhead, provided the application inside the container is written to talk to a block device directly rather than expecting an ordinary mounted directory.

### Access modes describe what a volume can do, not what it will enforce

ReadWriteOnce lets one node mount a volume read-write, though that single node can still run several Pods that all reach the volume at once — anyone needing to guarantee just one Pod in the whole cluster gets access should reach for ReadWriteOncePod instead, stable since the 1.29 release and, as of the current docs, limited to CSI volumes. ReadOnlyMany allows many nodes to mount read-only, and ReadWriteMany allows many nodes to mount read-write; the CLI shorthand for the four modes is RWO, ROX, RWX, and RWOP. Only one access mode can actually be in effect for a given mount even when the underlying volume plugin lists support for several, and — this is the part that catches people out — declaring a volume ReadOnlyMany doesn't by itself stop a write from being attempted; access modes describe compatibility for matching a PVC to a PV rather than acting as an enforced permission, with ReadWriteOncePod being the one mode that Kubernetes actually constrains at the mounting level. Which modes are even available depends entirely on the volume plugin backing a particular PV — HostPath only ever supports ReadWriteOnce, for instance, while NFS supports all three of the non-single-Pod modes.

### Reclaim policies: Retain, Delete, and the deprecated Recycle

A PersistentVolume's reclaim policy governs what happens to it once the claim that was using it gets deleted. Retain leaves both the PV object and its underlying storage asset in place, moving the PV to a released — not yet reusable — status, since whatever data the previous claim wrote is still sitting there; getting that capacity back for a new claim is a manual sequence of deleting the old PV, cleaning up the data on the storage asset by hand, and either deleting that asset too or standing up a fresh PV that reuses it. Delete instead removes the PV object and the real storage behind it together, and it's what any dynamically provisioned volume inherits from its StorageClass unless that class was configured otherwise, making it the default reclaim behavior for provisioner-created storage even though a manually created PV without a class defaults to nothing in particular until an administrator sets one explicitly. Recycle, now deprecated in favor of just using dynamic provisioning instead, used to run a bare filesystem scrub against the volume so it could be handed to a new claim, but it only ever worked for the nfs and hostPath plugin types. A PV created by hand keeps whatever reclaim policy it was given at creation regardless of which StorageClass name it carries, so changing that behavior later always means editing or patching the live PV object directly.

## Manage persistent volumes and persistent volume claims

### PersistentVolume and PersistentVolumeClaim: separating supply from demand

A PersistentVolume is a cluster-scoped piece of real storage — the storage equivalent of what a Node represents for compute capacity — that an administrator either creates directly or that gets created on demand through dynamic provisioning, and it carries whatever implementation detail is needed to actually back the storage, whether that's an NFS export, an iSCSI target, or a cloud block device. A PersistentVolumeClaim plays the role for storage that a Pod's own resource requests play for CPU and memory: it's a user's request for some amount of space at some access mode, deliberately left ignorant of how that storage gets fulfilled underneath. Because users often need storage that differs in more than raw size and access pattern — performance characteristics being the obvious example — the StorageClass resource sits above both of them, letting an administrator publish several such offerings without the PVC author needing to understand what backs any one of them.

### The provisioning, binding, using, and reclaiming lifecycle

Provisioning happens one of two ways: statically, where an administrator has already created PV objects ahead of time describing existing storage, or dynamically, where the cluster creates a brand-new PV on the fly because no existing static PV satisfies an incoming PVC, driven entirely by whichever StorageClass the PVC names — a PVC that explicitly requests the empty-string class opts out of dynamic provisioning altogether, and turning dynamic provisioning on for defaulted PVCs additionally requires the DefaultStorageClass admission controller to be enabled on the API server. Binding is handled by a control loop that watches for unbound claims and looks for a matching volume — a dynamically provisioned PV is always bound straight to the PVC that caused its creation, while a statically provisioned match is guaranteed to meet or exceed what the PVC asked for, and either way the resulting PVC-to-PV pairing is an exclusive one-to-one relationship recorded through a bidirectional ClaimRef, so a PVC with no match anywhere simply stays unbound until a suitable PV shows up. Using a bound claim just means listing it under a Pod's persistentVolumeClaim volume entry, at which point the cluster resolves it to the underlying PV and mounts that volume for the Pod. Reclaiming kicks in once a user deletes the PVC, at which point whatever reclaim policy the bound PV carries determines the storage's fate.

### What actually has to match before a claim gets bound to a volume

Binding isn't purely about whether a PV is big enough — a PVC's storageClassName has to line up exactly with a candidate PV's storageClassName, with both left empty counting as a valid match for storage carrying no class at all, while a PVC that leaves storageClassName unset entirely follows a separate code path: its fate then depends on whether that cluster's admission chain currently has the DefaultStorageClass plugin turned on, and it can even be updated automatically later once a default class becomes available (a PVC carrying a label selector, however, is explicitly excluded from ever receiving a dynamically provisioned volume). When a selector is present, its matchLabels and matchExpressions entries are all combined with AND logic, so a PV has to satisfy every listed requirement at once to qualify. To reserve one specific PV for one specific PVC rather than leaving the match to the control loop, a claim can set its volumeName field to name that PV directly, and the PV itself can list that claim under its own claimRef to shut out every other PVC from taking it first — the standard way to reattach to a Retained volume that still holds data worth keeping.

### Storage Object in Use Protection: finalizers that block a premature delete

Deleting a PVC that some running Pod is still actively using doesn't remove it right away — the object instead moves into a Terminating state and stays there, held by a kubernetes.io/pvc-protection finalizer, until no Pod references it any longer, which exists specifically to stop an in-flight delete from yanking storage out from under a workload that's still writing to it. The same protection applies symmetrically to a PV that's currently bound to a PVC, held in place by a kubernetes.io/pv-protection finalizer until the binding itself is gone. A related but separate set of finalizers — external-provisioner.volume.kubernetes.io/finalizer for CSI-backed volumes, and kubernetes.io/pv-controller for dynamically provisioned in-tree ones — keeps a PV whose reclaim policy is Delete from disappearing from the API until its backing storage asset has actually been torn down in the external system, which guarantees that outcome no matter what order an administrator happens to delete the PV and PVC objects in.

### Growing a PVC after it is already in use

Expanding a PVC's storage after the fact is enabled by default, but only works against a StorageClass that has allowVolumeExpansion explicitly set to true, and it can only make a volume bigger — there's no supported way to shrink one back down. The mechanic is simply editing the PVC's own requested storage size; the control plane resizes the volume that's already backing the claim rather than swapping in a brand-new PV to replace it. If the volume holds a filesystem, that filesystem only actually grows once some Pod is mounting the PVC in read-write mode — either the moment that Pod starts up, or, for filesystems capable of resizing while mounted, at any point while it's already running. One documented pitfall worth remembering: manually editing a PV's own recorded capacity to match a PVC's newly requested size tricks the control plane into believing nothing needs to happen, since it only compares the two objects' declared sizes rather than confirming the real storage grew, so that shortcut silently skips the actual resize.

### Filesystem versus Block volume mode, and how that affects binding

volumeMode defaults to Filesystem, under which Kubernetes formats a filesystem onto an empty block device the first time it's mounted and hands a Pod what looks like an ordinary directory; setting it to Block instead presents the volume as a bare device with no filesystem layer at all, trading the convenience of a mounted directory for the lowest possible latency, at the cost of pushing device management onto the application itself. Only a handful of plugins support that raw mode — CSI, Fibre Channel, iSCSI, and local volumes among them. Binding rules get stricter once volumeMode enters the picture: an unspecified PV happily binds to a PVC that also leaves the field unspecified or asks for Filesystem, but a PV explicitly set to Block only ever binds to a PVC that also explicitly asks for Block, and any Filesystem-to-Block or Block-to-Filesystem mismatch between the two is rejected outright rather than silently coerced one way or the other.
