## Troubleshoot clusters and nodes

### Reading node health: conditions, the NotReady timeline, and automatic taints

kubectl get nodes is the starting point for any cluster-level investigation — it shows whether every node an administrator expects to see is present and sitting in the Ready state — and kubectl describe node or kubectl get node -o yaml pull the fuller picture for any node that looks wrong. When a node genuinely goes down — it loses network connectivity entirely, or its kubelet crashes and never comes back — the MemoryPressure, DiskPressure, PIDPressure, and Ready conditions all flip from their normal values to Unknown, each carrying a NodeStatusUnknown reason and a message noting that the kubelet stopped posting status. Kubernetes also stamps that node with an unreachable taint carrying both NoExecute and NoSchedule effects. Because ordinary Pods tolerate the matching NoExecute taint for a bounded window — 300 seconds by default — a downed node's Pods keep showing as running for about five minutes before they're evicted, which is why a freshly-unreachable node and a long-unreachable one can look different in kubectl get pods even though the node's own status hasn't changed.

### Triaging Pod-level failure states: Pending, Waiting, and stuck Terminating

kubectl describe pod is the first move for any misbehaving Pod, since its Events section usually names the actual blocker. A Pod stuck Pending can't be scheduled at all — most often because no node has enough free CPU or memory to satisfy its requests, which calls for trimming requests, freeing capacity, or adding nodes, or because it demands a hostPort that only a limited number of nodes can offer, in which case a Service is almost always the better fix than hostPort in the first place. A Pod stuck Waiting has been scheduled but can't start on its node, overwhelmingly because its image can't be pulled — worth checking the image name for typos, whether it was actually pushed to the registry, and whether pulling it manually from that node succeeds. A Pod stuck Terminating means a deletion was issued but a finalizer is still attached, and something — typically a validating or mutating admission webhook intercepting Pod UPDATE operations — is preventing the control plane from clearing that finalizer; checking for a ValidatingWebhookConfiguration or MutatingWebhookConfiguration targeting Pods is the way to confirm that theory. Because events are namespaced, kubectl get events only returns something useful when pointed at the right namespace (or run with --all-namespaces).

### Getting a shell into the trouble: exec, ephemeral containers, and copy-to-debug

kubectl exec `<pod>` -c `<container>` -- `<command>` is the first tool to reach for when a container's own image already ships a shell and basic utilities. It falls short the moment a container has crashed already, or its image is deliberately minimal (a distroless image, for instance) and has no shell to exec into at all — that's exactly the gap ephemeral debug containers close: kubectl debug -it `<pod>` --image=`<debug-image>` --target=`<container>` attaches a throwaway container to the already-running Pod and, through --target, shares the target container's process namespace so tools like ps actually show its processes (assuming the container runtime supports that sharing). When even attaching isn't enough — say, the Pod's own configuration is what's getting in the way of debugging it — kubectl debug --copy-to=`<name>` stands up a full copy of the Pod with a deliberate change applied instead of touching the original: adding a new container for extra tooling (--share-processes to let it see the other containers), replacing one container's command entirely with an interactive shell, or swapping every container's image at once via --set-image=*=`<image>`. A --profile flag (general, baseline, restricted, netadmin, sysadmin, or the legacy default) tunes the security context the debug container gets — sysadmin grants full capabilities for genuinely privileged work — and every one of these debugging Pods or containers should be deleted once the investigation wraps up.

### kubectl debug node: an SSH-free shell on a Node

kubectl debug node/`<name>` -it --image=`<image>` deploys a Pod onto the named node and drops into an interactive shell there, which matters most when direct SSH access to nodes isn't available — it just needs permission to create Pods, pin them to a specific node, and mount host filesystems. The node's own root filesystem shows up inside that debugging Pod at /host, and on a typical Linux node the files worth checking under there include /host/var/log/kubelet.log, kube-proxy.log, containerd.log, syslog, and kern.log. The debugging Pod runs inside the node's IPC, network, and PID namespaces, but it isn't privileged by default, so some operations — chroot /host among them — fail until a privileged profile (--profile=sysadmin) or a manually-built privileged Pod is used instead. The one hard limit worth remembering: this technique doesn't work at all against a node that's genuinely unreachable, since there's no kubelet left on it to run the debugging Pod — at that point reading its status and events from the API side, through kubectl describe node or a raw kubectl get node -o yaml, is the only option left.

### Capturing packets on a Node or Pod during a privileged debug session

For connectivity or DNS problems that need an actual packet trace, kubectl debug --profile=sysadmin node/`<name>` -it --image=ubuntu:latest opens a privileged shell on the node where a tool like tcpdump can be installed on the spot (apt-get install tcpdump) and pointed at the node's interfaces (tcpdump -i any -n). The same flag works against a specific workload instead of the whole node — running kubectl debug with --profile=sysadmin against pod/`<name>` in the right namespace, with an interactive Ubuntu-based debug image, captures traffic from that one Pod's own network namespace instead, which is the better choice when the suspect traffic is scoped to a single application rather than everything passing through a node. As with any kubectl debug invocation, the created debugging Pod (typically named something like node-debugger-`<node>`-`<suffix>`) has to be deleted by hand once the capture is done, or it lingers around in a Completed state.

### What actually breaks when a cluster component fails, and how HA mitigates it

Losing the API server — a crash or a VM shutdown — stops any new create, update, or scale operation cold, but Pods and Services that were already running keep working unless they specifically need to call the API themselves. Losing the storage behind the API server is worse: the apiserver can't come back healthy again until that state is manually recovered, though kubelets keep running whatever Pods they'd already been assigned and keep proxying traffic in the meantime. Because the scheduler and controller-manager are typically co-located with the apiserver and carry no persistent state of their own, their failure modes track the apiserver's closely. A single node shutting down just drops the Pods scheduled to it; a network partition splits the cluster's own view of itself, with each side believing the other is the one that's down; a crashing kubelet stops new Pods from starting on its node and gets that node marked unhealthy so a controller reschedules the affected workload elsewhere. The documented mitigations map straight onto these failure modes: automatic VM restart at the infrastructure layer, durable and replicated storage under the apiserver and etcd, a highly-available control-plane layout able to tolerate losing one or more nodes or components at once, periodic snapshots of that backing storage, and building workloads around replication — a Deployment or ReplicaSet, a Service in front of it, containers written to tolerate an unexpected restart — so that no single node or kubelet failure takes an application down.

## Troubleshoot cluster components: control plane and kubelet

### Where control-plane and node component logs actually live

On a control-plane node provisioned by kubeadm, the kube-apiserver, kube-scheduler, and kube-controller-manager all run as static Pods, so journalctl won't show them directly — reading their output means going through the same Pod-log mechanism any other container uses, while an installation that runs those components as plain host processes instead keeps their logs as flat files at paths like /var/log/kube-apiserver.log. Worker nodes are more straightforward: /var/log/kubelet.log and /var/log/kube-proxy.log (or their journalctl -u kubelet / journalctl -u kube-proxy equivalents on a systemd host) are the first places to check when a node itself is misbehaving. The kubelet and the container runtime are the two components that never run inside a container at all, so they're the ones that genuinely do write straight to the systemd journal (or to flat files via a helper like kube-log-runner if no journal exists) — every other Kubernetes component's logs are, ultimately, container logs. etcd, almost always deployed as a static Pod too, follows that same Pod-log path, with etcd's own documentation the right place for interpreting what's actually in those logs.

### Confirming kubectl itself can reach the cluster before blaming the cluster

kubectl version prints both the client and server version in one shot; getting a connection-timeout error back in place of a server version means the problem is reachability, not cluster health, and is worth ruling out before assuming anything is actually broken on the cluster side. The kubeconfig file kubectl reads — by default ~/.kube/config, or a control-plane node's own /etc/kubernetes/admin.conf when nothing else has been set up yet — has to exist and be valid, and either the $KUBECONFIG environment variable or the --kubeconfig flag can silently point kubectl at the wrong file if a different one was expected. Because one kubeconfig can define several clusters and contexts at once, kubectl config get-contexts followed by kubectl config use-context `<name>` is how to confirm which one is actually active, rather than assuming a failing command is a cluster problem when it's really a stale context. A dropped VPN session produces symptoms that are indistinguishable from a genuinely unreachable API server, so reconnecting it is worth trying early, alongside a basic reachability check — pinging the API server's host, or the load balancer sitting in front of several control-plane nodes if one exists.

### Diagnosing TLS and authentication failures against the API server

An error along the lines of 'certificate signed by unknown authority' on an otherwise healthy-looking cluster almost always means a kubeconfig pointing at the wrong CA, or holding a client certificate that's simply expired. Both the client-certificate-data and certificate-authority-data fields inside a kubeconfig are base64-encoded, so decoding one with base64 -d and piping the result into openssl x509 -noout -dates is the quickest way to read off its notBefore/notAfter window and confirm whether expiry is actually the cause. A stale $KUBECONFIG environment variable left pointing at an old file is a common self-inflicted version of this problem; unsetting it, or explicitly exporting it to the control plane's /etc/kubernetes/admin.conf, forces kubectl back onto a known-good file, and as a last resort overwriting ~/.kube/config with a fresh copy of that admin.conf clears out a corrupted local configuration entirely. Authorization failures are a distinct category worth not conflating with these: a credential that authenticates cleanly but still gets a request rejected means RBAC doesn't grant that identity the verb or resource being requested, not that the certificate itself is bad.

### kubeadm-specific control-plane failure patterns

kubeadm init hanging indefinitely right after printing that it's waiting for the control plane to become ready traces to one of three usual causes: no network connectivity between the machines involved, a mismatch between the container runtime's configured cgroup driver and the kubelet's own, or the control-plane containers themselves crash-looping — checked by inspecting each one's logs through whatever tooling matches the runtime in use (crictl for a CRI-compliant runtime). kubeadm reset can get stuck removing Kubernetes-managed containers if the container runtime itself has stopped responding; restarting the runtime and re-running the reset is the documented fix, with crictl again useful for inspecting runtime state directly. Missing preflight utilities such as ebtables or ethtool surface only as warnings during kubeadm init rather than hard failures, but installing them anyway is worth doing since networking add-ons frequently depend on them. A version-skew gotcha worth knowing: a kubeadm v1.18-or-newer node joining a cluster originally bootstrapped by kubeadm v1.17 can fail because the newer kubeadm needs RBAC permission to read Node objects — added specifically to stop a node from joining under a name that's already taken — that the older cluster's bootstrap-token group was never granted; running kubeadm init phase bootstrap-token from a current control-plane node, or applying the missing ClusterRole and ClusterRoleBinding directly, resolves it.

### Kubelet client certificate rotation failing on a node

kubeadm configures every kubelet to rotate its own client certificate automatically through a symlink at /var/lib/kubelet/pki/kubelet-client-current.pem, referenced from /etc/kubernetes/kubelet.conf; when that rotation breaks, the telltale symptom shows up as x509 certificate-expiry errors in the kube-apiserver's own logs rather than anywhere obvious on the affected node itself. Recovery starts with backing up and removing the broken kubelet.conf and kubelet-client* files on that node, then generating a replacement kubeconfig from a control-plane node that still holds the cluster's CA key, using something like kubeadm kubeconfig user --org system:nodes --client-name system:node:`<node-name>` and adjusting the cluster name and API server address inside the result as needed. After copying that file back to /etc/kubernetes/kubelet.conf and restarting the kubelet, the client-certificate-current.pem symlink should reappear on its own; a final edit points kubelet.conf's client-certificate and client-key fields at that symlink rather than at embedded certificate data, followed by one more kubelet restart, after which the node should return to Ready.

### CoreDNS as a signal of control-plane and add-on health

CoreDNS sitting in Pending immediately after kubeadm init is expected rather than a symptom of anything wrong: kubeadm is deliberately network-provider-agnostic and installs no Pod network add-on on its own, so CoreDNS simply can't schedule until an administrator applies one — the same networking dependency that shows up elsewhere as 'no CNI plugin, no working cluster DNS.' CoreDNS actively crash-looping once a network add-on is already in place points at something different: on nodes running SELinux together with an older container runtime, CoreDNS's container can fail to start until the runtime is upgraded, SELinux is turned off (a real security tradeoff), or the coredns Deployment has allowPrivilegeEscalation flipped to true as a workaround. A second, unrelated cause of the same CrashLoopBackOff symptom is CoreDNS detecting a genuine DNS forwarding loop and exiting on purpose rather than looping forever, for which documented workarounds exist so Kubernetes stops endlessly restarting it every time the loop check fires. Because any Pod sitting in RunContainerError, CrashLoopBackOff, or Error state immediately after a bare kubeadm init — before any add-on has even been applied — is not expected at all, seeing that pattern that early is a stronger signal than CoreDNS's ordinary Pending phase and is worth treating as a potential kubeadm issue rather than routine startup noise.

## Monitor cluster and application resource usage

### The resource metrics pipeline: cAdvisor, the kubelet, and metrics-server

Resource metrics flow through a short, fixed chain: cAdvisor, bundled inside the kubelet, collects and aggregates per-container CPU and memory figures straight from the container runtime; the kubelet then exposes a per-node summary of that data through its own /metrics/resource endpoint (or the older /stats/summary endpoint, for older metrics-server versions); metrics-server, a separate cluster add-on rather than something built into Kubernetes itself, polls every kubelet's endpoint in turn and aggregates the results cluster-wide. metrics-server is what actually implements and serves the Metrics API under metrics.k8s.io, and nothing downstream of it works — kubectl top included — until it, or an equivalent implementation, has actually been deployed into the cluster. The Metrics API's consumers sit at the top of that chain: the kube-apiserver serves the API itself to whoever queries it, and both the HorizontalPodAutoscaler and VerticalPodAutoscaler read from it to make their scaling decisions, alongside kubectl top for a quick human-readable view. A runtime that isolates workloads through something other than ordinary Linux cgroups has to separately implement the CRI Container Metrics interface, or the kubelet has no way to surface its metrics into this pipeline at all.

### What CPU and memory actually mean in the Metrics API

CPU usage is reported as an average number of cpu units — one cpu equating to one vCPU or core on a cloud provider, or one hyperthread on bare-metal Intel hardware — calculated from how fast a cumulative CPU counter the kernel maintains has been climbing across whatever window the API's window field reports, rather than an instantaneous snapshot of activity. Memory usage is reported as the container's working set in bytes at the exact instant it was sampled: the portion of in-use memory that can't be reclaimed under pressure, though the precise calculation is host-OS-dependent, leans on heuristics, and typically folds in some reclaimable file-backed cache alongside genuinely anonymous memory. Both figures live behind a real, directly-queryable API object (NodeMetrics or PodMetrics under metrics.k8s.io/v1beta1), reachable with something like kubectl get --raw against the appropriate path — handy for confirming the pipeline independently of kubectl top or for scripting against it. The Metrics API is deliberately scoped to just these two signals for autoscaling purposes; anything beyond CPU and memory needs a second, separate pipeline built on the custom-metrics or external-metrics API groups, served through a vendor-specific adapter rather than metrics-server.

### kubectl top as the everyday resource-usage check

kubectl top nodes and kubectl top pods read straight from the Metrics API that metrics-server populates, giving an immediate view of CPU and memory consumption without hand-querying the raw API; when metrics-server isn't deployed or isn't healthy, both commands fail outright instead of returning stale or zeroed-out numbers. Because the figures behind kubectl top are the exact ones an attached HorizontalPodAutoscaler evaluates on its own sync interval, a workload's kubectl top output is a reasonable stand-in for what that HPA currently sees, which makes it a natural first check whenever an HPA doesn't seem to be scaling the way it's expected to. kubectl describe node surfaces a related but genuinely different view — allocated resources, based on what Pods have requested and limited — which answers a different question (how much capacity is already committed) than kubectl top's answer (how much is actually being used right now); mixing the two up is a common source of confusion when a node looks saturated on one command but shows headroom on the other.

### Diagnosing a broken or missing metrics pipeline

The most common cause behind kubectl top or an HPA reporting that metrics are unavailable or unknown is simply that metrics-server was never deployed, has crashed, or can't reach the kubelets it's supposed to poll — confirming its Deployment is Running and its own logs are clean is the first troubleshooting step, well ahead of assuming anything is wrong with the workload being measured. Because metrics-server calls each kubelet directly over HTTP, a network policy, firewall rule, or certificate-trust problem that blocks that specific path breaks the pipeline in a way that looks, from kubectl top's point of view, identical to metrics-server being entirely absent. If per-Pod metrics are missing for just one workload while every other workload reports fine, checking whether that workload's nodes run a container runtime lacking CRI Container Metrics support is worth ruling out, since that's a narrower and easier-to-miss failure mode than metrics-server being down cluster-wide. Because the whole pipeline still carries a beta feature-state designation, an occasional transient gap in reported numbers is expected rather than alarming, though a sustained failure to report anything at all should still be chased down through the steps above rather than dismissed.

### Beyond CPU and memory: monitoring node health signals directly

Resource metrics answer 'how much CPU and memory is currently being used,' but a node can be unhealthy in ways that number never reveals — disk pressure, kernel-level faults, a corrupted filesystem, an unresponsive container runtime — which is exactly why cluster troubleshooting guidance also points at Node Problem Detector, a daemon built specifically to watch for these lower-level node-health symptoms and surface them as ordinary node conditions and events rather than as CPU or memory figures. kubectl describe node's Conditions block is where any such detected problem eventually becomes visible to an operator, the very same block that MemoryPressure, DiskPressure, and PIDPressure already appear in from the kubelet's own reporting, so a monitoring workflow doesn't need two separate places to look for kubelet-native conditions versus problem-detector-native ones. Taken together, resource-usage monitoring — metrics-server and kubectl top feeding HPA and VPA decisions — and node-health monitoring — conditions, events, and Node Problem Detector — cover two distinct failure classes: one says a workload needs more or fewer replicas, the other says a node itself is degrading in a way that no amount of rescheduling fixes until the underlying host problem is addressed.

## Manage and evaluate container output streams

### stdout/stderr as the baseline, and kubectl logs as the way to read it

The simplest and most universal way a container reports what it's doing is by writing plain text to its own stdout and stderr — the two standard streams every process already has — and every container runtime Kubernetes supports captures both of them without any extra configuration required from the application itself. kubectl logs `<pod>` [-c `<container>`] retrieves whatever that container has written so far; the -c flag only matters once a Pod has more than one container, since a single-container Pod's logs are unambiguous without it. kubectl logs `<pod>` --previous instead retrieves output from the container's last run rather than its current one, which is the standard way to see why a container crashed right before it restarted, since the current instance's own logs won't contain anything written before it started. Because this whole mechanism depends on nothing more than a runtime capturing two ordinary streams, it works identically no matter which language or logging library an application uses — the tradeoff is that Kubernetes has no opinion at all about log format or structure, leaving that entirely to whatever reads the output downstream.

### Log rotation, and why kubectl logs can’t always show everything

The kubelet, not the container runtime or the application itself, owns rotating each container's logs and organizing the on-disk directory structure they live in, coordinating with the runtime over CRI so the actual log-writing follows a format every runtime implements the same way. Two kubelet settings bound that behavior directly: containerLogMaxSize (10Mi by default) caps how large a single log file gets before it's rotated, and containerLogMaxFiles (5 by default) caps how many rotated files are kept per container; two further settings, containerLogMaxWorkers and containerLogMonitorInterval, tune how many rotations can run concurrently and how often the kubelet checks whether one is needed, which matters on nodes generating a heavy volume of log output. The practical consequence: kubectl logs only ever reads the current, unrotated log file, so a container that's written well past the containerLogMaxSize threshold will only show its most recent slice of output through kubectl logs — older, already-rotated content isn't retrievable that way at all, even though it briefly existed on the node's disk. This is exactly why log data that needs to survive longer than a node's local rotation window, or needs querying across many Pods at once, has to be shipped somewhere else entirely — kubectl logs is a live tail, not an archive.

### How nodes actually store logs: journald, flat files, and static Pods

On a Linux node running systemd, the kubelet and the container runtime write their own operational logs to journald by default, read back with something like journalctl -u kubelet; on a node without systemd, both instead write plain .log files under /var/log, and a helper tool called kube-log-runner can redirect the kubelet's own output elsewhere if the default location isn't wanted. Container logs are a separate matter from those component logs entirely: by default the kubelet directs the runtime to write every container's logs under /var/log/pods, organized into per-namespace, per-Pod directories, a path that can be repointed through the kubelet's podLogsDir setting — though the guidance is explicit that changing it should be done cautiously, since a long history of tooling assumes that default location, and the new location still has to live on the very same disk /var itself is on, or the kubelet won't track how much space it's using at all. Control-plane components that run as static Pods — the API server, scheduler, controller-manager, and usually etcd — write their logs the same Pod-log way rather than to the systemd journal, worth remembering when a control-plane node's journalctl output looks unexpectedly quiet about one of them. Because Kubernetes performs no log rotation at all for anything written outside this container-log mechanism — a static Pod's logs shared onto a node-level directory through a volume, say — whatever handles rotation for that directory elsewhere on the host still has to be relied on or configured separately.

### Cluster-level logging patterns: node agent, sidecar, and direct push

Kubernetes deliberately ships no built-in destination for logs to live in permanently or be queried centrally — cluster-level logging always means layering one of a small number of documented patterns on top of the basic stdout/stderr mechanism. Running a logging agent as a DaemonSet, one per node, is the most common approach: it needs no changes to any application, reads whatever containers already write to stdout and stderr from the node's own log directory, and forwards it to a backend, at the cost of losing any distinction between differently-formatted log streams unless the agent is specifically told how to tell them apart. A streaming sidecar container instead has each sidecar tail one particular file, socket, or journald source inside the Pod and re-emit it to its own stdout, which keeps kubectl logs usable per stream — since the kubelet and any node agent still see ordinary container output — and suits an application that writes several differently-formatted files rather than one unified stream, though it roughly doubles the node storage the Pod's logging needs. Running a fully separate logging agent inside a sidecar, rather than a per-node DaemonSet, offers the most control over formatting and destination but costs the most resources and, notably, makes those logs invisible to kubectl logs entirely, since they never pass through the kubelet's own log path at all.

### Splitting stdout from stderr on the wire (alpha)

As an alpha capability gated behind the PodLogsQuerySplitStreams feature gate, off by default, the kubelet can expose a container's stdout and stderr as two independently queryable log streams instead of one interleaved one. With the gate enabled, a client holding read access to a Pod's log subresource can request just one stream by adding a stream query parameter set to Stdout or Stderr against the Pod's log API path, rather than getting kubectl logs' usual all-in-one output. This suits an application that deliberately separates informational output from error output and wants a consumer — a log-shipping pipeline, or a person chasing one specific failure — to pull just the error stream without filtering it back out of a merged log by hand. Being alpha, it's not something to rely on for an exam-relevant workflow yet, but it points at a direction: today, kubectl logs and the underlying log API treat a container's output as a single combined stream, and this feature is what would eventually let those streams be evaluated separately at the API level instead of only through client-side filtering.

### The log-directory structure kubectl logs and rotation both rely on

Every container's captured stdout and stderr ultimately lands in a predictable per-namespace, per-Pod, per-container path under /var/log/pods on the node, and that shared structure is exactly what both kubectl logs (through the kubelet) and the kubelet's own rotation logic are reading from and rotating in place — understanding it explains why rotation settings and kubectl logs behavior are two sides of one mechanism rather than unrelated features. Because the CRI logging format standardizes how a runtime hands log lines to the kubelet regardless of which runtime is running, this entire path — directory structure, rotation, and kubectl logs — behaves identically whether a node runs containerd, CRI-O, or any other CRI-compliant runtime. A Pod evicted from a node takes its containers' logs with it in the sense that actually matters operationally: once eviction happens, that log data is gone from the node's local disk along with everything else about the terminated containers, which is one more reason cluster-level log shipping exists — anything not already forwarded off-node before an eviction is simply unrecoverable afterward.

## Troubleshoot services and networking

### Step zero: does the Service even exist?

It sounds trivial, but the single most common reason a Service 'doesn't work' is that it was never actually created — kubectl get svc `<name>` returning a not-found error is the very first thing worth checking before looking anywhere else. Trying to reach a nonexistent Service by name from inside a Pod produces a DNS failure that looks identical to a genuinely broken DNS setup, along the lines of 'Name or service not known,' which is exactly why confirming the Service object directly, rather than trusting a symptom that could have several unrelated causes, comes first in any real walkthrough. Once its existence is confirmed, checking early for any NetworkPolicy objects whose ingress rules target the Service's backing Pods is worth doing too, since a perfectly correct Service can still look broken if a policy is silently dropping the very connections being tested against it.

### Working through DNS resolution for a Service, one suffix at a time

Starting from any other Pod sitting in that same namespace, a lookup of just the Service's bare name should resolve; if that fails but the namespace-qualified form (name.namespace) works, the caller and the Service live in different namespaces and the app needs that qualified name, or needs moving into the same namespace as the Service. If only the fully-qualified form (name.namespace.svc.cluster.local) resolves, the problem sits somewhere upstream of the shorter forms rather than with the Service itself. A Pod's own resolver configuration is what makes the short forms work at all: its nameserver has to point at the cluster's DNS Service address (set on the kubelet through --cluster-dns), its search list has to include the namespace-local, all-namespaces, and cluster-wide suffixes in order (set through --cluster-domain), and its ndots option has to be high enough — 5 by default — that an unqualified name is actually tried against those search suffixes rather than treated as already complete. If even the cluster's own built-in kubernetes Service fails to resolve from inside a Pod, the problem isn't specific to whatever Service is under investigation at all — it's the cluster's DNS Service, and by extension kube-proxy, that needs debugging instead.

### Checking that a Service's own spec actually matches its Pods

Reading a Service back with kubectl get service `<name>` -o yaml (or -o json) is the way to double-check details that are easy to get wrong writing one by hand: whether spec.ports[].port is actually the port callers are trying to reach, whether targetPort correctly names or numbers the port the Pods listen on, and whether a targetPort meant to be numeric got accidentally quoted as a string, or a named port doesn't match any port name the Pods actually expose. A mismatched protocol — TCP against a Pod actually listening on UDP, or vice versa — is another easy-to-miss cause of a Service that looks entirely correctly defined yet still refuses every connection. Getting these fields right matters more than it might seem, because none of the deeper checks further down the chain — EndpointSlices, kube-proxy's own dataplane — will ever reveal a simple port or protocol typo; a Service can be wired up to exactly the right Pods and still forward nothing usable if the port mapping itself is wrong.

### Proving the Service actually selected the Pods it should have

kubectl get endpointslices -l kubernetes.io/service-name=`<service>` shows the addresses the EndpointSlice controller has actually resolved for that Service's selector, and the count and addresses shown there should line up with the Pods expected to be backing it. An EndpointSlice with no addresses at all almost always traces back to a selector mismatch — the Service's spec.selector labels simply don't match the labels on any running Pod, a mistake that's easy to introduce by hand, the classic example being a Service selecting app=hostnames while the workload's own Pods carry run=hostnames instead, a labeling convention an older kubectl run used to apply automatically. Listing Pods with the exact selector the Service itself uses (kubectl get pods --selector=`<key>`=`<value>`,...) is the direct way to confirm what a human reading raw YAML might miss, since it shows precisely which Pods Kubernetes considers a match rather than which Pods a person assumes should match. Once endpoints are present but something still seems off, checking those same Pods' age and restart counts is worth a look too, since a crash-looping Pod behind an otherwise-correctly-wired Service still shows up as a valid endpoint yet produces inconsistent responses.

### Verifying kube-proxy is actually programming the dataplane

Confirming kube-proxy is running on a node (a plain process check for it) and that its logs show it setting endpoints for the Service in question, rather than errors reaching the API server, is the next layer down once DNS, the Service's own spec, and its EndpointSlices have all already checked out. kube-proxy's logs reveal which backend mode it's using — most commonly iptables or IPVS — and each mode has its own way to confirm the rules are actually in place: an iptables rule dump filtered for the Service's name should show one entry in a KUBE-SERVICES chain pointing at a per-Service KUBE-SVC chain, which in turn fans out to one KUBE-SEP chain per backing Pod, while an IPVS listing should instead show a virtual server for the Service's address with one weighted real server per Pod endpoint. If those rules exist but a direct connection to the Service's ClusterIP from a node still fails, restarting kube-proxy with a higher log verbosity and re-reading its output is the documented next step, since that usually surfaces whatever specific condition it's stuck on.

### The hairpin edge case: a Pod that can't reach itself through its own Service

A Pod occasionally needs to reach itself through the same Service VIP that fronts its whole Deployment, and when that one specific case fails while everything else about the Service works fine, the cause is almost always hairpin traffic not being enabled on the node — a setting that lets a Service's own backend loop traffic back to itself through the proxy instead of only ever forwarding outward to other endpoints. This shows up specifically with kube-proxy running in iptables mode alongside bridge-based Pod networking, and the kubelet's own hairpin-mode flag has to be set to one of two specific values for it to work at all; both the flag's configured value and its actual effective value — visible in the kubelet's own logs, since compatibility fallbacks can make the two differ — are worth checking. Confirming it's genuinely active on the node depends on which mode is effective: one mode is confirmed by checking a hairpin flag on the node's virtual network interfaces, the other by checking that the relevant bridge interface reports promiscuous mode when inspected. This is a narrow, specific failure worth checking only after DNS, the Service definition, EndpointSlices, and kube-proxy's general operation have already been ruled out, since it explains exactly one symptom — a Pod failing to reach its own Service address — rather than Services being broken in general.
