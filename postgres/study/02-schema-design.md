## Relational Modeling Foundations

### Tables as Relations

A relational table models a set of facts about one kind of thing. Because it is modeled as a set, no row order is guaranteed, and a duplicate row carries no additional meaning — though SQL itself does permit two completely identical rows, so it takes a primary key or unique constraint to actually rule them out. Because each row has the same named attributes, a column means the same thing in every row. This is why a query has to state its own ORDER BY to get a stable order, and why a table that mixes two kinds of things — orders and the customers who placed them — starts causing trouble immediately: attributes that describe only the customer end up repeated on every order line, and the table no longer describes a single kind of fact.

### Redundancy and the Three Anomalies

When one fact is stored in more than one place, the copies can disagree. Three failure modes follow. An update anomaly happens when a change reaches some copies and not others, leaving the table self-contradictory. An insertion anomaly happens when a fact cannot be recorded because unrelated data is missing — you cannot register a customer who has not yet placed an order, if customers only exist as columns on order rows. A deletion anomaly is the mirror image: removing the last order for a customer also erases the customer. These three anomalies, not elegance, are the practical reason to split tables apart.

### Functional Dependencies

A functional dependency A -> B holds when each value of A is associated with exactly one value of B: no two rows may agree on A while disagreeing on B. Dependencies are statements about the real world the data models, not about the rows that happen to be present, so they are decided from the domain rather than discovered by querying. They matter because they locate redundancy precisely. A dependency whose left side is a whole candidate key is fine — that is what a key means. A dependency on anything else means the table is recording a fact about something other than its own subject, and that fact will be repeated on every row that shares the value.

### One Fact in One Place

The design goal that falls out of the anomalies is simple to state: each fact should be recorded exactly once, in the table whose subject that fact is about. A customer's address is a fact about the customer, so it belongs on a customer row and is referenced from orders rather than copied into them. This principle is what the normal forms formalize — each successive form rules out another way a table can end up storing a fact about something other than its own key. Working out the grain of a table first, before writing any DDL, usually settles most design questions before they become arguments.

## Keys and Identity

### Candidate Keys, Primary Keys, and Composite Keys

A candidate key is any minimal attribute set that uniquely identifies a row — minimal because dropping any one attribute from the set would let two rows collide. A table can hold several candidate keys at once: an employees table might identify a row equally well by employee_id or by a unique badge_number, and both qualify. Exactly one candidate is designated the primary key; the others remain merely unique. Some candidate keys are composite, spanning more than one column, as with an order_lines table keyed on (order_id, line_number) — neither column alone is unique, but the pair always is. Which candidate becomes primary is not purely cosmetic: the primary key is the candidate that is also forced NOT NULL, and it is the default target for foreign keys pointing at the table. The remaining candidates still need their own UNIQUE constraints — plus an explicit NOT NULL if they are meant to be true identifiers, since UNIQUE on its own permits any number of nulls.

### Natural Versus Surrogate Keys

A natural key is drawn from data the row would carry anyway — an email address, a national ID, a product SKU — so it carries meaning outside the database and is recognizable on sight. That meaning is also its liability: natural keys can change, and can turn out not to be unique once some edge case appears, which is a bad thing to discover in a primary key. A surrogate key, typically a generated integer or UUID, has no meaning at all — it exists only to be stable and compact, which makes it cheap to reference from other tables. Choosing a surrogate does not excuse the natural key from being constrained: it still needs its own UNIQUE constraint, since the surrogate only replaces its role as identifier, not its need to actually be unique.

### Identity Columns and serial

An identity column asks PostgreSQL to generate a value from a hidden sequence rather than requiring the application to supply one. GENERATED ALWAYS AS IDENTITY rejects an explicit value on insert unless the statement adds OVERRIDING SYSTEM VALUE, making an accidental override visible instead of silent; GENERATED BY DEFAULT AS IDENTITY instead lets a supplied value take precedence, behaving more like an ordinary column default. The older serial pseudo-type is shorthand for the same mechanism — a sequence plus a default expression — and identity columns are now the documented, standards-based replacement. Neither approach guarantees uniqueness on its own: a sequence can be reset, and a BY DEFAULT column can still receive a duplicate value supplied by hand, so uniqueness still has to come from a PRIMARY KEY or UNIQUE constraint layered on top.

### UNIQUE Versus PRIMARY KEY

UNIQUE and PRIMARY KEY both stop two rows from sharing the same value in the constrained columns, but they diverge on null handling and cardinality. A UNIQUE constraint permits any number of rows with a null in the constrained column, because by default two nulls are never considered equal to each other — nulls represent unknown values, and two unknowns cannot be shown to collide. PRIMARY KEY carries that same uniqueness rule but adds NOT NULL on top of it, so a primary key column can never hold a null at all. A table may declare as many UNIQUE constraints as it needs — one per alternate identifier — but only one of them can be named the primary key, since that designation marks the columns a foreign key in another table lands on when it names no target columns at all, and the identifier most tooling assumes.

## Constraints and Referential Integrity

### CHECK and NOT NULL: Validating a Row Against Itself

A CHECK constraint attaches a boolean expression to a table, and PostgreSQL evaluates it against every row being inserted or updated: the constraint is satisfied whenever the expression evaluates to true or to null, and only rejects the row when it evaluates to false outright. That null-passes rule matters — a CHECK referencing a nullable column will not, by itself, stop that column from being null, since an expression with a null operand usually evaluates to null rather than false. Because keeping a column non-null is such a common requirement, PostgreSQL gives it a dedicated NOT NULL constraint rather than requiring CHECK (column IS NOT NULL) to be spelled out by hand; the two are functionally equivalent, but the dedicated form is documented as more efficient and is what most schemas should reach for first.

### Declaring a Foreign Key

A foreign key ties a column or column set in one table to a column or column set in another, and PostgreSQL enforces that every non-null value on the referencing side has a match on the referenced side. That guarantee only works if the referenced columns are themselves guaranteed unique, so a foreign key must point at a non-deferrable primary key or unique constraint, or a non-partial unique index, on the target table — pointing at an arbitrary, unconstrained column is rejected outright, since there would be nothing to guarantee a single match. Nothing in that requirement says the two sides need matching names: a foreign key like FOREIGN KEY (b, c) REFERENCES other_table (c1, c2) is perfectly legal, because what actually has to agree is the number and type of the columns on each side, not what they are called. Nor must the two tables even be different ones: a foreign key may reference the same table it is declared on, a self-referential foreign key, and the referenced column still needs that same primary key or unique constraint behind it, exactly as it would if the two tables were distinct. The natural use is a hierarchy kept in a single table, such as an employee row whose manager_id references another row's id in that same employees table. A referencing row with a null in any of its foreign-key columns is exempt from the check by default, on the same logic that makes null incomparable to anything.

The practical effect is a table that cannot record a reference to something that does not exist — though the guarantee is lopsided in one respect: because the referenced columns come from a primary key or unique constraint, they already have an index behind them, but declaring the foreign key creates no matching index on the referencing columns, since not every foreign key needs one and there are too many reasonable ways to index it for PostgreSQL to pick automatically. That gap is usually worth closing anyway, since deleting a referenced row or updating a referenced column forces a scan of the whole referencing table for rows still pointing at the old value, and without an index there, that scan has nothing to speed it up.

### Referential Actions

When a referenced row is deleted or its key is updated, PostgreSQL has to decide what happens to the rows still pointing at it, and ON DELETE and ON UPDATE each accept one of five actions. CASCADE propagates the change, deleting or updating the referencing rows along with it. SET NULL clears the referencing column to null, and SET DEFAULT resets it to the column default — though if that default would itself violate the constraint, the operation still fails, since referential actions never bypass the constraints they interact with. RESTRICT and NO ACTION both reject an operation that would leave a referencing row pointing at nothing, and NO ACTION is the default whenever no clause is written. Picking the wrong action here silently produces either orphaned data or an unwanted cascade of deletes.

### NO ACTION Versus RESTRICT

NO ACTION and RESTRICT look interchangeable at first glance — both refuse a delete or update that would strand a referencing row — but they differ in more than when PostgreSQL checks. RESTRICT is the stricter of the two: it fires the instant a matching referencing row is found and rejects the operation outright, even when the state left behind would still satisfy the foreign key — which is why ON UPDATE RESTRICT also blocks updating a referenced value to one that is merely distinct but compares as equal — and the check can never be deferred. NO ACTION is looser in both respects: it lets the statement run and checks the foreign key against the resulting state, so an operation that leaves no dangling reference succeeds where RESTRICT would have refused it outright, and, when the constraint is declared deferrable, NO ACTION also lets that check wait until the end of the transaction, which gives later statements in that same transaction room to fix the situation — inserting the row that will make a foreign key valid, for instance — before the check finally runs. Because NO ACTION is also the unwritten default, most foreign keys behave this way without anyone choosing it explicitly, and RESTRICT only earns its place when a schema specifically needs the check to fire immediately and without exception.

### Deferrable Constraints

By default every constraint in PostgreSQL is NOT DEFERRABLE, meaning it is checked immediately after the statement that could violate it, with no chance for a later statement in the same transaction to fix things first. Marking a UNIQUE, PRIMARY KEY, EXCLUDE, or foreign-key constraint DEFERRABLE INITIALLY DEFERRED changes that: the check is postponed until the transaction commits, so intermediate states within the transaction are allowed to look inconsistent as long as everything lines up by the end. This is what makes otherwise-impossible operations tractable — inserting two rows that reference each other, or swapping the unique values held by two existing rows without a moment where either would collide with the other. SET CONSTRAINTS can also flip a deferred constraint back to immediate within the current transaction, if a particular statement needs that check enforced right away.

### MATCH FULL Versus MATCH SIMPLE

A composite foreign key inherits the same null-exemption rule as a single-column one, but with several columns the exemption turns ambiguous: does the whole row need every column filled before a match is required, or does one null column let it skip the check entirely? Left unqualified, a foreign key uses MATCH SIMPLE by default, under which a row is exempt from the constraint the moment any one of its referencing columns is null, even when the rest are populated and would, on their own, need a matching row on the referenced side. MATCH FULL replaces that with an all-or-nothing rule: a row escapes the constraint only when every referencing column is null, so a row mixing null and non-null values across its foreign-key columns is guaranteed to fail rather than slip through unenforced. The two modes agree on a row that is fully populated or fully null; only a partially-null composite reference tells them apart, and under the default that row silently escapes the very constraint it was meant to satisfy — almost never what the modeler intended.

### Adding Constraints to a Live Table

Adding a CHECK, foreign-key, or NOT NULL constraint to a table that already holds data normally means scanning every row to confirm none of them violate it, which on a large table can mean a long-held lock blocking other activity. NOT VALID skips that scan: the constraint is added and immediately applies to every future insert or update, but PostgreSQL makes no claim that existing rows already satisfy it. Running VALIDATE CONSTRAINT afterward performs the deferred scan, and because concurrent sessions are already enforcing the constraint on any row they touch, the scan only needs to check pre-existing rows — which lets it take a SHARE UPDATE EXCLUSIVE lock rather than the heavier lock a plain, scanning ADD CONSTRAINT would need. Splitting the operation this way is the standard technique for rolling out a constraint on a busy table without an extended outage.

## Normalization and Relationships

### First Normal Form

The running example starts as a single wide table: one row per order, with order_id, order_date, customer_name, customer_email, and a products column holding something like 'Widget x2, Gadget x1' — a list crammed into one field. That products column breaks first normal form, which requires every cell to hold a single value with no repeating groups or embedded lists. That rule comes from the relational model, not from PostgreSQL — the array and jsonb types covered in the architecture domain deliberately depart from it — so the practical test is whether the elements have to be filtered, joined, aggregated, or constrained individually, which is exactly what a delimited string like this makes impossible. The fix is to give each order-product pairing its own row: order_id, order_date, customer_name, customer_email, product_id, product_name, product_price, and quantity, with one row per product on an order rather than one row per order. Every cell now holds exactly one value, and the table is in 1NF — though, as the next topic shows, giving up the wide layout has just traded one problem for a subtler one.

### Second Normal Form

The 1NF version of the order table now has a composite primary key, (order_id, product_id), since neither column alone identifies a row. But order_date, customer_name, and customer_email depend only on order_id — the same order_date repeats on every product line of the same order — and product_name and product_price depend only on product_id, repeating on every order that includes that product. Both are partial dependencies: attributes depending on part of the key rather than the whole thing, which is exactly what second normal form forbids. The fix splits the table three ways: orders (order_id, order_date, customer_name, customer_email), products (product_id, product_name, product_price), and order_items (order_id, product_id, quantity) linking them, so every non-key attribute now depends on its own table's entire key.

### Third Normal Form

The orders table produced by the 2NF split still has a problem once a customer places more than one order: customer_name and customer_email repeat on every order row for that customer, and if the email changes, every one of that customer's past orders has to be updated to match or the table contradicts itself. The dependency is transitive — order_id determines customer_email, and customer_email in turn determines customer_name, so the name depends on the key only through another non-key attribute rather than directly. Third normal form forbids exactly this chain. The fix extracts a customers table, assigning it a new customer_id as its key alongside customer_name and customer_email, and leaves orders holding only customer_id as a reference in place of the two repeating columns, so a customer's contact details live in one row regardless of how many orders they have placed.

### Boyce-Codd Normal Form

Suppose order_items — still (order_id, product_id, quantity) from the 2NF split — grows a discount_code column, and every order-product line is required to carry one, because a given discount code is always good for exactly one product: discount_code determines product_id. Order_items (order_id, product_id, quantity, discount_code) now has two candidate keys, (order_id, product_id) and (order_id, discount_code) — the second exists only because every line is required to carry a discount code, exactly the premise just established; drop that premise and the pair could no longer stand in for every row, so it would stop being a candidate key at all. Because product_id is part of a candidate key, discount_code -> product_id does not violate third normal form, which excuses a dependency landing on a prime attribute; BCNF removes that excuse, requiring every determinant to be a candidate key outright, and discount_code alone is not one. The correct fix moves the dependency out whole: discount_codes (discount_code, product_id) holds it on its own, and order_items becomes (order_id, discount_code, quantity) — product_id has to leave, since keeping it would leave discount_code -> product_id inside a table where discount_code still is not a superkey, with the same code-to-product pair still repeated on every line that uses the code and free to contradict the discount_codes row. That works cleanly only because every line here has a code; a line without one would have no way left to name its product once product_id is gone. Real order systems usually can't promise that, so most schemas keep product_id on order_items alongside discount_code, accept that the table stays in 3NF rather than BCNF — discount_code -> product_id still holds there, still on a non-superkey — and enforce agreement with a composite foreign key on (discount_code, product_id) referencing discount_codes (discount_code, product_id). That composite reference only works because discount_codes also carries an explicit UNIQUE (discount_code, product_id) constraint alongside its primary key on discount_code, since a foreign key can only point at a primary key, a unique constraint, or a non-partial unique index, and the primary key on discount_code alone doesn't cover the pair. That is a deliberate trade of the stricter normal form for a table that keeps working when a line carries no code, not a BCNF fix.

### Modeling Relationships

The schema that falls out of these refinements — customers, orders, products, order_items, and discount_codes — also demonstrates how relationships are modeled once tables are separated by subject. Customers and orders are one-to-many: one customer places many orders, so the foreign key lives on the many side, with orders.customer_id referencing customers.customer_id, and no separate linking table is needed. Orders and products are many-to-many instead — one order can include many products, and one product can appear on many orders — which a single foreign key cannot express in either direction. order_items is the junction table that resolves it: its primary key is the pair of foreign keys, (order_id, product_id), so each order-product combination appears at most once while quantity and discount_code hang off that combination as its own attributes. discount_code is itself a foreign key into discount_codes, another one-to-many since many order_items rows can share a code, and the composite foreign key on (discount_code, product_id) is what keeps that route to a product agreeing with order_items' own, the price of leaving order_items in 3NF rather than BCNF — a reference discount_codes can only accept because it also carries a UNIQUE (discount_code, product_id) constraint alongside its primary key on discount_code.

## Design Tradeoffs in PostgreSQL

### Denormalizing Deliberately

Normalization optimizes for write integrity — each fact in one place, updated once — at a direct cost to read performance, since reconstructing a full order means joining across orders, customers, products, and order_items every time. Denormalizing means deliberately storing a derived or duplicated value to avoid that join, such as caching a customer name directly on the order row for a reporting query that runs constantly and cannot tolerate the join cost. The trade is real, not free: every copy of a fact is a new place for it to drift out of sync with the source, and something — application code, a trigger, a scheduled job — now owns keeping the copies aligned. It is worth doing against a measured query pattern, not as a default starting position or a hedge against a problem that has not actually been observed.

### Generated Columns

A generated column computes its value from other columns in the same row rather than accepting one supplied directly, and PostgreSQL offers two kinds: VIRTUAL, which recomputes the expression on every read and stores nothing, and STORED, which computes the value at write time and stores that result physically, the same as an ordinary column would. VIRTUAL is the default whenever a generated column is declared without either keyword, so STORED has to be spelled out explicitly to get the write-time, on-disk behavior this topic focuses on. Because the expression can only see the current row, an order line total needs the price on the line itself — order_items carrying its own unit_price snapshot copied from products at order time, exactly the deliberate denormalization of the previous topic. Declaring order_items.line_total as GENERATED ALWAYS AS (quantity * unit_price) STORED then keeps the total consistent with its inputs, because the column cannot be written to directly — an INSERT or UPDATE that tries to supply its own value is rejected outright, with only the keyword DEFAULT accepted in its place. The generation expression is restricted to immutable functions, cannot reference another generated column, and cannot contain a subquery, which keeps its value fully determined by the row itself. This makes a generated column the right tool for derived data the database should maintain, rather than trusting every application code path to recompute the same formula consistently.

### Domains and Composite Types

A domain is a base type plus a set of constraints — CREATE DOMAIN email AS text CHECK (VALUE ~ '@') — used as a column type anywhere the same rule applies, on both customers.email and a separate contacts table, without repeating the CHECK expression in every CREATE TABLE. A composite type instead groups several fields into one named bundle, similar to a struct, and PostgreSQL automatically creates one behind every table to represent its row type. Composite types carry no constraints of their own, though — a NOT NULL written inside CREATE TYPE is rejected — so a composite column is usually the wrong tool where what is actually needed is a related entity with its own identity and foreign-key references: a table, not a bundle of fields glued into one column.

### Inheritance Versus Declarative Partitioning

Table inheritance lets a child table like archived_orders inherit all the columns of orders and add its own, and by default querying orders also sweeps in every row from its children unless the query is restricted with ONLY. CHECK and NOT NULL constraints inherit down to children automatically, but UNIQUE, PRIMARY KEY, and FOREIGN KEY constraints do not — a primary key on orders does nothing to stop archived_orders from holding a duplicate order_id, since indexes and foreign keys in PostgreSQL apply only to a single table, never across a whole inheritance hierarchy. Declarative partitioning closes part of that gap: a foreign key declared on the parent covers every partition automatically, and a UNIQUE or PRIMARY KEY constraint on the parent can be enforced across the whole partition set too — but only when its columns include every column of the partition key. That condition is not a nicety: PostgreSQL refuses outright to create a unique or primary key constraint on a partitioned table that omits a partition-key column, because an index on a single partition can only enforce uniqueness within that partition, never against a matching row sitting in a sibling one, so the partition boundaries themselves have to do the rest of the work. This is why a partitioned table's key so often has to widen to include the partitioning column, and why partitioning, not legacy inheritance, is the documented tool for splitting one logical table by a key like order_date.
