## Index Types & When to Use Each

### B-Tree: The Default, General-Purpose Index

CREATE INDEX builds a B-tree unless another access method is named, and that default choice fits the widest range of situations. A B-tree can be used whenever a query compares an indexed column with <, <=, =, >=, or >, and it also backs constructs built out of those operators, such as BETWEEN, IN, and an IS NULL or IS NOT NULL test. It can even support LIKE and ~ pattern matching, but only when the pattern is a fixed constant anchored to the start of the string, like 'foo%' or '^foo' — a trailing wildcard such as '%bar' gets no help from an ordinary B-tree, and outside the C locale this pattern-matching support requires creating the index with a special operator class. Beyond lookups, a B-tree can also hand back rows already in sorted order to satisfy an ORDER BY, which isn't always faster than a plain scan-then-sort but often is.

### Hash Indexes: Equality-Only, by Design

A Hash index stores a 32-bit hash derived from the indexed value, so it can only ever help with a plain equality comparison — no ranges, no ordering, nothing an ORDER BY could lean on. Since PostgreSQL 10, Hash index changes are written to WAL, which makes them crash-safe and lets them replicate to standbys the same way B-tree, GiST, GIN, and BRIN indexes always have — closing what used to be a real gap. What Hash still doesn't offer is a multi-column index; only B-tree and the other tree-structured or summary access methods support indexing more than one column together. In practice, a B-tree already handles equality lookups efficiently while also remaining useful for ranges and sorting, so Hash rarely wins out as a deliberate choice over the default.

### GiST: A Template for Many Different Indexing Strategies

GiST isn't one algorithm but a balanced-tree infrastructure — a Generalized Search Tree — into which very different indexing strategies can be plugged. Which operators a particular GiST index supports depends entirely on the operator class chosen for it: the core distribution ships GiST support for two-dimensional geometric types, network-address containment, range and multirange types, and tsvector/tsquery full-text matching, and contrib modules like btree_gist and pg_trgm extend that set further. Because an implementer only has to define the semantics specific to their data type, GiST lets an expert in that domain build a working access method without having to understand PostgreSQL's internal locking and logging machinery. A capability unique to GiST among the built-in index types is the ordered, 'nearest-neighbor' scan driven by a distance operator such as <->, which lets a query ask for the ten closest points to a target rather than merely testing equality or containment. Range-typed EXCLUDE constraints — the tool for rejecting overlapping bookings or overlapping validity periods — are typically backed by a GiST index for exactly this reason.

### GIN: Inverted Indexes for Composite Values

GIN, a Generalized Inverted Index, targets columns whose values are composite rather than atomic — arrays, jsonb documents, and tsvector full-text documents are the built-in examples. Instead of one index entry per row, GIN keeps one entry per distinct component key, each pointing to a posting list of every row that contains it; a key that recurs across thousands of rows is still only stored once, which is what keeps a GIN index compact even over highly repetitive data. That layout is precisely why GIN is the access method behind efficient containment and existence queries — @>, <@, the jsonb ? family, and tsvector's @@ match — since testing 'does this key appear anywhere' is exactly what an inverted index is built to answer quickly. The tradeoff shows up on writes: touching one row can mean inserting many keys, which is inherently costlier than a B-tree's single per-row update. GIN's fastupdate mechanism softens this by parking new entries in an unsorted pending list and flushing them in bulk during VACUUM, autoanalyze, or once gin_pending_list_limit is crossed, at the cost of searches also having to scan whatever is still sitting in that pending list.

### BRIN: Tiny, Lossy Summaries for Naturally-Ordered Data

BRIN — Block Range Index — takes a fundamentally different approach: rather than indexing individual rows, it summarizes each contiguous block of table pages, with the size of that block controlled by the pages_per_range storage parameter. For an ordinary linearly-sortable type the summary is just the minimum and maximum value seen in the range (other operator classes, like bloom and minmax-multi, summarize differently), so a single tiny index tuple can stand in for tens of thousands of rows, which is why a BRIN index is often a small fraction of the size of the table it covers and barely adds overhead when scanned. The payoff — skipping whole page ranges the summary proves can't contain a match — only materializes when the indexed column is genuinely correlated with its physical position in the table, such as a mostly-append-only timestamp column; a column whose values are scattered unpredictably across pages gains little. BRIN scans are lossy by design: the executor still has to recheck each candidate row, since the summary only rules ranges out, it never confirms an individual row matches. New page ranges also aren't summarized the moment data lands in them — they stay unsummarized until the next VACUUM, an explicit brin_summarize_new_values() call, or, if the index's autosummarize option is turned on, the next autovacuum pass.

### Comparing Operator Support Across Index Types

Picking an index type starts with asking which operators the query actually needs. B-tree covers the complete family of ordering comparisons — less-than through greater-than — plus anchored pattern matching and sorted retrieval, which is exactly why it's the default and remains the right first choice for most columns. Hash supports only the equals operator and nothing else, a strictly narrower guarantee than what a B-tree already provides for free while also handling ranges. GIN and GiST both offer containment-style operators such as @> and <@, but for different reasons: GIN is the specialist for inverted-index workloads where the same component keys recur across many rows — arrays, jsonb, full text — while GiST's supported operators are far more heterogeneous, spanning geometric overlap, range overlap, and nearest-neighbor distance, because GiST is a general template rather than one fixed algorithm. BRIN's operator support is the narrowest and, for linearly-ordered types, mirrors B-tree's comparison operators applied against a block range's stored minimum and maximum rather than against exact per-row values — a deliberate loss of precision traded for an index that's a tiny fraction of the table's size.

## Targeted Indexing: Partial & Expression Indexes

### Partial Indexes: Indexing Only a Subset of Rows

A partial index is built over only the rows that satisfy a predicate written directly into the CREATE INDEX statement, rather than over the whole table — rows that don't satisfy it simply get no entry at all. A classic reason to do this is excluding an extremely common value: a query for a value that accounts for a large share of the table won't benefit from an index anyway, so there's no point paying to keep those rows indexed, and leaving them out shrinks the index while also speeding up any write that has to maintain it. Indexing an access log's client-IP column only for addresses outside an organization's own subnet is a concrete version of this idea — if the searches that matter are mostly for outside traffic, there's little reason to index the far more common internal addresses at all.

### A Partial Index's Predicate Must Be Implied at Plan Time

A partial index can only help a query if the planner can establish, while planning, that the query's WHERE condition logically implies the index's predicate — and PostgreSQL deliberately doesn't attempt a full general-purpose proof engine for this, since building one would be both very hard and too slow to be worth using. What it can recognize are simple inequality implications, such as x < 1 implying x < 2; beyond that narrow case, the predicate essentially needs to match part of the query's condition close to verbatim, or the partial index won't be considered a candidate at all. Because this check happens against the literal text of the condition at plan time rather than against runtime values, a parameterized clause can never satisfy it: a placeholder comparison like x < $1 has no fixed value the planner can test against a predicate such as x < 2, so partial indexes quietly stop helping once a query is rewritten to use bind parameters instead of literal constants.

### Partial Unique Indexes as a Constraint, Not Just an Optimization

A partial index doesn't have to exist for query speed at all — a unique partial index is also how PostgreSQL enforces uniqueness over only some of a table's rows, leaving the rest unconstrained. Wanting exactly one successful outcome recorded per subject-and-target pair, while allowing any number of unsuccessful ones, is naturally expressed as a unique index on (subject, target) restricted to WHERE success, something an ordinary table-wide UNIQUE constraint simply has no syntax for. The same trick, applied with an IS NULL predicate instead, is the standard way to allow at most one null in a column: an ordinary unique constraint never rejects a second null, because it treats every null as distinct from every other null and so two nulls never count as a conflict.

### Don't Reach for Partial Indexes as a Substitute for Partitioning

One tempting but counterproductive pattern is carving up a table into a large family of non-overlapping partial indexes — one per category value, each restricted to WHERE category = N — instead of a single ordinary composite index on (category, data). The single combined index almost always wins: descending a couple of extra levels of one larger B-tree is cheap, but the planner has to individually weigh every one of the N partial indexes to work out which, if any, applies to a given query, and that per-index evaluation cost typically dwarfs whatever the split was meant to save. When a table is genuinely large enough that this kind of category-based split matters, real table partitioning is the intended tool, because it lets the system understand structurally that the pieces don't overlap instead of having to re-derive that fact index by index at plan time.

### Expression Indexes: Indexing a Computed Value Instead of a Raw Column

An indexed column doesn't have to be a literal column of the table — it's allowed to be any deterministic function or expression built from the table's columns, which is what turns a query like WHERE lower(col1) = 'value' into something indexable: CREATE INDEX ... ON test1 (lower(col1)) builds an index keyed on the function's output, and from the planner's perspective the query now reduces to an ordinary equality test against an indexed value. The same idea extends to multi-column expressions, such as indexing the concatenation of first and last name to accelerate full-name lookups; CREATE INDEX syntax requires the expression to be parenthesized unless it's a bare function call. Declaring an expression index UNIQUE has a useful side effect beyond speed — it can enforce a rule an ordinary column-level UNIQUE constraint has no way to express, such as rejecting rows whose values differ only in letter case.

### The Shared Trade-Off: Write Cost Now for Read Selectivity Later

Partial and expression indexes are really the same bet made along two different axes: both shrink or specialize an otherwise ordinary index rather than switching to a different access method entirely, and both spend extra effort at write time to buy cheaper, more targeted reads later. An expression index has to recompute its underlying expression on every row insert and every non-HOT update, which is genuine, recurring overhead — but that value is never recomputed at search time, since the already-derived result sits directly in the index, so a lookup against it runs exactly as fast as against any other simple indexed column. A partial index pays a smaller, mostly one-time version of the same trade: because only a slice of the table's rows are indexed at all, both the ongoing maintenance cost and the on-disk footprint shrink, in exchange for the index only being usable by the specific slice of queries whose condition matches, or is implied by, its predicate. Both techniques earn their keep only when a specific, well-understood read pattern matters enough to justify that extra write-side cost.

## Reading Query Plans: EXPLAIN & the Cost Model

### EXPLAIN Basics: Plan Trees and cost=startup..total

EXPLAIN renders the plan the optimizer chose as a tree of nodes: the bottom-level nodes are scans that pull raw rows out of a table — sequential, index, or bitmap — and the nodes above them handle joins, aggregation, sorting, and similar operations on those rows. Each node's summary line reports cost=startup..total rows=N width=W. Startup cost is the estimated work needed before the node can produce its very first output row, which matters for something like an EXISTS subquery that only ever needs one row and so cares more about getting started quickly than about running to completion; total cost assumes the node is run all the way through. rows is the number of rows the node is estimated to emit, not the number it has to examine internally — a sequential scan with a restrictive filter can examine far more rows than it ever outputs — and width is the estimated average size of each output row in bytes. All of these costs live on an arbitrary scale, conventionally anchored so that one sequential page fetch costs 1.0; a total cost of 445 isn't 445 of any real-world unit, it's only meaningful next to another candidate plan's cost for that same query.

### From Seq Scan to Bitmap Scan to Index Scan

The same table and the same kind of WHERE clause can produce noticeably different scan strategies depending purely on how selective the condition turns out to be, and EXPLAIN makes each crossover visible. A query with little or no filtering gets a plain sequential scan, since visiting every page in physical order is cheap even when a Filter step throws most of the rows away afterward. Once a condition narrows the matching rows enough, the planner tends to switch to a two-step bitmap plan: a Bitmap Index Scan builds an in-memory map of matching row locations and sorts them into physical page order, and a Bitmap Heap Scan above it fetches only those pages — cheaper than a full sequential pass while still reading in a more cache-friendly order than jumping straight through an index tuple by tuple. When a condition is selective enough that only a handful of rows can possibly match, the planner instead goes straight to a plain Index Scan, fetching rows one at a time directly in index order; this is the shape typically seen for single-row point lookups, and it's also useful when the index's natural order already satisfies an ORDER BY, since no separate explicit Sort step is then required.

### EXPLAIN ANALYZE Actually Executes the Statement — Important Nuance

Plain EXPLAIN only produces a plan and never runs the statement, but adding ANALYZE changes that entirely: EXPLAIN ANALYZE genuinely executes the statement so it can report true elapsed time and true row counts next to the planner's original estimates, shown per node as actual time=startup..total rows=N loops=M — loops matters for any node re-run once per outer row — for instance, a nested-loop join's inner side — and has to be multiplied back in to get that node's real total time contribution. Because the statement is genuinely executed, every real side effect it would normally have still happens; EXPLAIN only ever suppresses the result rows a SELECT would have sent back to the client, it never undoes any underlying change. For an INSERT, UPDATE, DELETE, or MERGE this matters concretely: EXPLAIN ANALYZE will really modify the stored data, even though the phrase used to describe this behavior — that the statement's output is 'discarded' — only refers to hiding the returned rows, not to reverting the write itself. The documented way to inspect a data-modifying statement's plan without keeping its effects is to run it inside an explicit transaction and roll that transaction back afterward: BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;.

### Where Row Estimates Come From: pg_statistic and ANALYZE

The planner's row-count guesses trace back to two different sources of statistics. Coarse, table-wide numbers — overall row count and page count — sit in pg_class's reltuples and relpages columns; refreshing those on every single write would be far too costly, so they're only updated by VACUUM, ANALYZE, and a handful of DDL commands such as CREATE INDEX, and the planner compensates for the resulting staleness by scaling whatever it finds there against the table's current physical size. Finer, per-column detail — the most common values, a histogram summarizing everything else, an estimated count of distinct values, and a null fraction — lives in pg_statistic, populated by ANALYZE (run manually or triggered by autovacuum) and normally inspected through the more approachable pg_stats view rather than pg_statistic directly. How much detail gets collected per column is governed by default_statistics_target, or a per-column override set with ALTER TABLE ... SET STATISTICS; raising it can sharpen estimates for columns with irregular distributions, at the cost of a slower ANALYZE. Because single-column statistics are gathered independently per column, the planner's default assumption is that separate WHERE conditions are independent of one another — an assumption CREATE STATISTICS extended-statistics objects exist to correct for columns that are actually correlated, by explicitly recording functional dependencies, multi-column distinct counts, or multi-column most-common-value lists.

### The Cost Constants: seq_page_cost, random_page_cost, and cpu_*_cost

The numbers EXPLAIN prints are assembled from a handful of tunable planner settings. seq_page_cost, defaulting to 1.0, is the reference unit for a page fetched as part of a sequential read; random_page_cost, defaulting to 4.0, estimates a non-sequential fetch; and cpu_tuple_cost, cpu_index_tuple_cost, and cpu_operator_cost charge small, separate amounts for processing each row, each index entry, and each operator or function call. A bare sequential scan's total cost is built directly from two of these: page count times seq_page_cost, plus row count times cpu_tuple_cost — for a 345-page, 10000-row table that arithmetic is (345 x 1.0) + (10000 x 0.01), which comes out to 445, exactly the total cost such a scan reports. What matters to the optimizer is never any one constant's absolute value, only the ratio between them: scaling every cost constant up or down by the same factor leaves the planner's choice of plan completely unchanged, since it only ever compares the summed cost of competing plans for the same query against each other.

## Performance Pitfalls & Operational Tuning

### random_page_cost and SSDs — Important Nuance

random_page_cost defaults to 4.0 against seq_page_cost's 1.0, which bakes in the assumption that a non-sequential page fetch costs roughly four times what a sequential one does — a ratio shaped by spinning magnetic disks, where physically seeking the read head to a new location adds real time on top of the transfer itself. Even that 4.0 is already described as a discount rather than the true worst case, since genuinely random access to durable storage is normally far costlier than a 4x multiple would suggest; the lower default is used because most random reads in practice, such as indexed lookups, are assumed to already be sitting in cache. On storage that's entirely flash-based, the physical asymmetry that 4.0 is modeling mostly disappears, since an SSD has no seek arm and random reads cost much closer to what sequential ones do — which means the stock default overstates the real penalty of an index scan on that hardware and nudges the planner toward sequential scans more often than is genuinely optimal for it. Because only the ratio between the cost constants drives planning decisions, never their absolute size, the fix is to lower random_page_cost itself — commonly toward somewhere in the 1.1-to-2 range for all-flash storage, or all the way down to match seq_page_cost when the working set is expected to stay fully cached in memory — rather than adjusting every other constant to compensate.

### Bulk Loading: COPY Beats Row-by-Row INSERT

Loading a large volume of data through a stream of individually auto-committed INSERT statements is a common, avoidable source of slow loads: each separately committed insert pays PostgreSQL's per-transaction overhead on its own, and recovering from a failure partway through means manually cleaning up whatever rows already committed before the failure. Wrapping a batch of inserts in a single explicit transaction removes that repeated per-statement overhead and turns a failure partway through into a clean, automatic rollback of everything attempted so far instead of a half-loaded table. The documented fastest path, though, is neither of those — it's the COPY command, purpose-built for loading many rows in a single operation, which needs no explicit transaction wrapper of its own since it's already just one statement. COPY runs fastest of all when it shares a transaction with the CREATE TABLE or TRUNCATE that created its target table, because a failure in that case can simply discard the newly written files outright rather than needing WAL to reconstruct anything — though that particular shortcut only applies when wal_level is set to minimal.

### Bulk Loading: Indexes, Foreign Keys, and the Trigger Queue

Building an index once, after data is already sitting in the table, is quicker than maintaining that same index incrementally on every single row as it arrives — which is why the fastest sequence for populating a brand-new table is to create it, COPY the data in, and only then create its indexes. Adding a large volume of new rows to a table that already has indexes can benefit from the same idea in reverse: dropping the indexes, loading the data, and recreating the indexes afterward, accepting that other readers temporarily lose whatever benefit those indexes were providing. Foreign key constraints have a sharper version of the same problem: checking a constraint in bulk against millions of rows is far cheaper than checking it one row at a time, but row-by-row checking is exactly the default behavior, since every inserted row fires a trigger that queues a pending check, and loading enough rows can grow that pending-event queue large enough to exhaust available memory or make the load fail outright. In that situation, dropping the foreign key before a very large load and re-adding it afterward isn't merely a nice-to-have optimization — it can be the only practical option short of splitting the load into smaller transactions so the pending-check queue never grows without bound.

### Bulk Loading: maintenance_work_mem and max_wal_size

Two settings are worth raising temporarily around a large load, on top of favoring COPY and deferring index creation. maintenance_work_mem governs how much working memory is available to the sort- and build-heavy operations that a deferred rebuild relies on — building a new index and re-attaching a dropped foreign key both fall into this category — so raising it speeds up precisely the rebuild-indexes-and-constraints step that a well-run bulk load defers to the end — it does nothing for COPY itself, so the benefit only shows up once indexes or foreign keys are actually being rebuilt. max_wal_size caps how much write-ahead log can accumulate before a checkpoint is forced, and loading a large amount of data in a short span tends to trigger checkpoints considerably more often than the configured checkpoint interval alone would call for; since every checkpoint has to flush all dirty pages out to disk, temporarily raising max_wal_size during the load reduces both how many checkpoints happen and how much flushing overhead they add along the way.

### Stale Statistics After a Big Load — Run ANALYZE

A bulk load is precisely the kind of event that invalidates whatever row-count and value-distribution estimates the planner was previously relying on, since it can change a table's size and the shape of its data dramatically in one step; without a fresh ANALYZE afterward, the planner keeps reasoning from statistics that are now stale — or, for a table that's brand new, entirely absent — and it can end up choosing noticeably worse plans as a result. autovacuum will eventually catch up and analyze the table on its own, but leaning on that timing right after a deliberate bulk load leaves a real gap: running ANALYZE, or VACUUM ANALYZE, immediately once the load finishes is the documented step that guarantees the very next query against that data gets planned against statistics that actually reflect what was just loaded. The same point applies to restoring from a pg_dump: a full schema-and-data restore already defers index and foreign-key creation automatically, but re-running ANALYZE once the restore completes is still left for whoever is performing the restore to do by hand.
