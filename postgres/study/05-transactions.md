## MVCC Fundamentals & Snapshots

### Readers Never Block Writers, Writers Never Block Readers

PostgreSQL's approach to concurrency departs from the classic model where every reader and writer contends for the same lock on a row. Instead, an update or delete never overwrites a row in place; it leaves the old version alone and adds a new version alongside it, tagged with the transaction that created it. Because a reader only ever needs to pick out the version of a row that its own snapshot considers visible, it has no need to wait for a writer that is simultaneously producing a different, newer version of that same row, and a writer likewise has no need to block a reader that will only ever see an older version anyway. This is the practical payoff of what the documentation calls Multiversion Concurrency Control: it minimizes the amount of blocking a busy, multi-user workload experiences compared with systems that rely purely on locking, while still giving every session a consistent picture of the data. PostgreSQL keeps this reader/writer non-interference guarantee even at its strictest isolation setting, which is a claim not every database product can make about its own strongest isolation level.

### A Snapshot Is a Frozen View of 'Committed as Of'

The mechanism underlying MVCC is the snapshot: at some defined instant, a SQL statement (or, at higher isolation levels, an entire transaction) captures which other transactions' changes count as already committed and which don't, and from then on every row visibility check for that statement or transaction is judged against that frozen boundary rather than against whatever the table looks like at the exact moment a particular row is examined. A row version becomes visible to a snapshot once the transaction that created it counts as committed as of that snapshot's boundary, and a row version drops out of visibility once the transaction that deleted or superseded it likewise counts as committed by that same boundary; anything still in flight, or that started after the snapshot was taken, is treated as though it doesn't exist yet. This is why a query can run for several seconds against a table other sessions are actively modifying and still return a self-consistent answer — every row it returns reflects the same as-of instant, even though the underlying table has moved on by the time the query finishes.

### Locking Still Has a Role Alongside MVCC

MVCC is the default and generally the better-performing way to manage concurrent access, but PostgreSQL doesn't force every use case to rely on it. Table- and row-level locks remain available for applications that need to explicitly manage a specific point of conflict rather than trusting snapshot semantics to sort it out on their own — a topic worth its own dedicated discussion — and PostgreSQL additionally offers advisory locks, which carry a meaning the application itself defines rather than one tied to protecting a particular row or table from concurrent modification. The general steer is that properly relying on MVCC usually outperforms falling back on explicit locks, but locks remain the right tool whenever the behavior an application actually needs isn't what snapshot isolation naturally provides.

### TRUNCATE and Rewriting ALTER TABLE Break MVCC — Important Nuance

Almost every DDL and DML operation in PostgreSQL respects MVCC snapshots, but there are two documented exceptions: TRUNCATE, and whichever forms of ALTER TABLE rewrite the table's underlying files rather than modifying them in place. Once one of these commands commits, the table can appear completely empty to a transaction still running against an older snapshot — not because MVCC decided the rows were logically deleted as of some consistent point in time, but because the command physically replaced the table's storage, leaving no old version of the data behind for that snapshot to fall back on. This surprising outcome can only happen to a transaction that had not gone anywhere near the table prior to the moment the DDL was issued; a transaction that had already read from or written to the table would, by that point, already be sitting on at least an ACCESS SHARE lock, and that existing lock would have forced TRUNCATE or a rewriting ALTER TABLE to sit and wait until the earlier transaction wrapped up before it could even begin. The practical effect is that this gap can never produce inconsistent results across successive queries against the same table — a transaction either blocked the DDL outright or hadn't touched that table yet — but it can produce a visible inconsistency between that table and other tables the same transaction reads, since those other tables continue to be read through ordinary, fully MVCC-safe machinery the whole time.

### Two More Caveats: Hot Standby and System Catalogs

A pair of narrower caveats matter for deployments that go beyond a single primary server. First, hot standby replicas don't yet support the Serializable isolation level; the strictest level a query against a standby can request is Repeatable Read, and although doing every write on the primary inside Serializable transactions keeps the standbys eventually consistent, a Repeatable Read query issued directly against a standby can transiently observe a state that no serial ordering of the primary's transactions would ever have produced. Second, PostgreSQL's own internal lookups against the system catalogs don't go through the calling transaction's isolation level the way ordinary table access does, so a newly created table or other database object becomes visible to a concurrent Repeatable Read or Serializable transaction the moment it's committed, even though the actual rows stored inside that new object stay invisible under that transaction's snapshot until it starts a fresh one. A query that instead reads the catalog tables directly, rather than going through PostgreSQL's internal access path, doesn't get this exception, and sees catalog rows governed by the same isolation-level rules as any ordinary table.

### Serializable as an MVCC Extension, Not a Separate Engine

One easy misconception is imagining that PostgreSQL switches to some entirely different concurrency mechanism once a transaction asks for Serializable isolation. In reality, Serializable is layered on top of the same MVCC snapshot machinery that backs every other isolation level — internally known as Serializable Snapshot Isolation — which is exactly what lets it preserve the same non-blocking reader/writer relationship the rest of MVCC provides, even at its strictest setting. The full mechanics of how it actually detects and reacts to unsafe concurrent patterns deserve their own dedicated treatment, but the framing worth internalizing here is that Serializable isn't a retreat back to traditional locking; it's additional monitoring built on the same versioned-row foundation underneath Read Committed and Repeatable Read.

## Isolation Levels & the SQL Standard

### Four Phenomena the SQL Standard Names

The SQL standard defines transaction isolation in terms of four specific phenomena that a given level either allows or forbids, rather than describing directly what each level actually does. A dirty read means seeing data written by another transaction that hasn't committed yet. A nonrepeatable read means re-reading a row within the same transaction and finding it has changed, because some other transaction committed a modification to it in between. A phantom read means re-running the same qualifying query and getting back a different set of matching rows, because another transaction committed an insert or delete that changed which rows satisfy the condition. A serialization anomaly is the broadest of the four: the end result of a group of committed transactions turns out to be inconsistent with every possible one-at-a-time ordering of those same transactions, even when no single earlier phenomenon can be pointed to as the specific cause. Each of the four standard isolation levels is defined purely by which of these four phenomena it promises will not occur.

### Only Three Levels Actually Exist in PostgreSQL — Important Nuance

The SQL standard names four isolation levels — Read Uncommitted, Read Committed, Repeatable Read, and Serializable — but PostgreSQL only implements three genuinely distinct behaviors internally. Asking for Read Uncommitted doesn't produce a looser level that permits dirty reads; PostgreSQL quietly treats it exactly the same as Read Committed, so a dirty read can never happen in PostgreSQL no matter which of the four levels a session requests. This isn't an oversight so much as a natural consequence of the storage model: since MVCC's versioned-row approach already makes reading another transaction's uncommitted writes essentially impossible by construction, there's nothing left for a genuinely separate Read Uncommitted mode to disable. A second, related subtlety worth remembering is that PostgreSQL's own Repeatable Read is stricter than the SQL standard actually requires that name to be: the standard permits phantom reads at Repeatable Read, but PostgreSQL's implementation rules them out anyway, which the standard explicitly allows, since any database is always free to provide stronger guarantees than the bare minimum a level demands.

### Read Committed: A New Snapshot for Every Statement

Read Committed is the isolation level a new PostgreSQL connection runs under by default, unless a session or transaction explicitly asks for something else. Each individual statement inside a Read Committed transaction takes its own snapshot the moment that statement starts, so a SELECT only ever returns rows that were committed before that particular statement began — never uncommitted data, and never a change some other session commits while the statement is still running — though it does see the effects of the surrounding transaction's own earlier, still-uncommitted statements. Because the snapshot resets on every statement instead of staying fixed for the whole transaction, two SELECTs issued back to back within one Read Committed transaction can legitimately come back with different results if some other transaction committed a change in between them. Read Committed handles narrow, single-row-targeted operations well — moving an amount between two accounts identified by primary key behaves sensibly, because each UPDATE only ever concerns the one row it names — but it can feel inconsistent for broader search conditions, since an UPDATE or DELETE re-checks its WHERE clause against whatever the row looks like at the moment it's actually reached, which may no longer match the row's state as of when the statement started.

### Repeatable Read: One Snapshot for the Whole Transaction

Repeatable Read fixes its snapshot once, at the start of the transaction's first real statement, and every later statement in that same transaction reuses that snapshot instead of taking a fresh one — so, unlike Read Committed, two SELECTs issued later in the same transaction are guaranteed to see identical data even if other transactions have committed changes in between them. That's enough to rule out both nonrepeatable reads and, thanks to PostgreSQL's stricter-than-required implementation, phantom reads as well — but it does not rule out serialization anomalies, which is exactly what separates it from Serializable. If a Repeatable Read transaction tries to update, delete, or lock a row that another transaction has already committed a change to since the Repeatable Read transaction's snapshot was taken, PostgreSQL doesn't quietly apply the change against stale data — it aborts the transaction outright with a serialization-failure error rather than let it proceed against a row it can no longer honestly treat as unmodified. Applications relying on Repeatable Read therefore need to catch that failure and retry the entire transaction from scratch, and only transactions that actually write need to worry about it, since a purely read-only transaction at this level can never hit a conflict of this kind.

### Serializable: Guaranteeing an Equivalent Serial Order

Serializable is defined by one strong guarantee rather than a list of forbidden phenomena: whichever group of Serializable transactions actually ends up committing, executing that same group sequentially, one after another in some order, would necessarily have produced an identical outcome. A useful illustration of why this is genuinely stronger than Repeatable Read: two transactions, each summing one category of values in a table and then inserting that sum as a new row filed under the other category, running concurrently — under Repeatable Read both are allowed to commit even though the two sums each transaction computed could never both have been correct had the transactions actually run one after another; Serializable instead recognizes that impossible combination and forces one of the two to fail with a serialization error instead of letting both commit. This category of problem — sometimes called write skew — is exactly the gap Repeatable Read leaves open despite handing every statement a stable, unchanging view of the data: a stable view isn't the same guarantee as a result consistent with some genuine one-at-a-time execution order. Because Serializable is built directly on top of Repeatable Read's snapshot behavior and layers this extra guarantee over it, transactions running at Serializable must be prepared to retry after a serialization failure in exactly the same way Repeatable Read transactions already need to be.

## Locking Mechanics: Table, Row & Advisory

### Eight Table-Level Lock Modes, One Conflict Rule

PostgreSQL defines eight table-level lock modes, and despite several of them having the word row baked into their names — ROW SHARE and ROW EXCLUSIVE among them — every one of the eight is, mechanically, a lock on the entire table; the naming simply reflects the kind of statement that typically acquires each mode. What actually distinguishes one mode from another comes down to nothing more than which other modes it conflicts with: two transactions can never simultaneously hold conflicting modes on the same table, though a transaction never conflicts with itself, while non-conflicting modes can be held concurrently by any number of sessions at once. Ordinary reads take the weakest mode, ACCESS SHARE, which conflicts with nothing except the strongest mode; row-modifying statements such as INSERT, UPDATE, and DELETE take ROW EXCLUSIVE; and commands that need genuine exclusivity — DROP TABLE, TRUNCATE, VACUUM FULL, and several ALTER TABLE forms among them — take ACCESS EXCLUSIVE, which conflicts with every other mode, including itself. A handy shortcut for reasoning about blocking: only an ACCESS EXCLUSIVE lock is strong enough to block a plain SELECT, which explains why so many schema-changing operations feel disruptive to run against a live table — they're specifically the ones that need that top mode.

### Row-Level Locking: SELECT FOR UPDATE and Its Weaker Siblings

SELECT ... FOR UPDATE lets a query lock the specific rows it retrieves as though it were about to update them, blocking any other transaction from updating, deleting, or similarly locking those same rows until the current transaction ends; if another transaction already holds a conflicting lock on one of the target rows, FOR UPDATE simply waits for it to finish and then re-fetches whatever the row looks like once it's free. Three progressively weaker row-lock modes sit alongside it: FOR NO KEY UPDATE, which is what an ordinary UPDATE that leaves key columns untouched acquires automatically, and which — unlike FOR UPDATE — does not block a concurrent FOR KEY SHARE; FOR SHARE, a shared lock that blocks concurrent writers but still allows other readers to take their own FOR SHARE or FOR KEY SHARE locks alongside it; and FOR KEY SHARE, the weakest of the four, which exists mainly so a foreign-key check against a referenced row doesn't need to block a full FOR NO KEY UPDATE on that same row. One detail that trips up anyone coming from Read Committed: inside a Repeatable Read or Serializable transaction, FOR UPDATE doesn't quietly wait and retry against a row that changed since the snapshot was taken, the way it does under Read Committed — it raises an error instead, because those stricter levels can't legitimately keep pretending the row was never touched.

### Advisory Locks: Session-Scoped vs Transaction-Scoped

Advisory locks are locks whose meaning PostgreSQL doesn't enforce or even inspect — they're simply an arbitrary numeric key an application agrees to coordinate around, useful for locking scenarios that don't map cleanly onto locking one specific row or table. They come in two lifetimes: a session-level advisory lock, acquired with a function such as pg_advisory_lock, stays held until it's explicitly released or the session disconnects, and notably doesn't follow ordinary transaction semantics at all — rolling back the transaction that acquired it does not release it, and an unlock call still succeeds even inside a transaction that later fails. A transaction-level advisory lock, acquired with the xact-suffixed variant such as pg_advisory_xact_lock, behaves instead like a regular lock: it's automatically dropped once the transaction ends, with no explicit unlock call needed or even available. Both scopes come in exclusive and shared flavors, and both offer a non-blocking try_ variant that returns immediately with a boolean rather than waiting, which matters for something like an application-level mutex that should skip its work instead of queuing behind whatever process already holds the same key. Because a session that already holds a given advisory lock can always reacquire it, and because session-level and transaction-level requests for the same key do block one another, mixing the two scopes for what's meant to be a single logical lock is something worth doing deliberately rather than by accident.

### pg_locks: Seeing What Is Actually Held

The pg_locks system view exposes every currently active lock in the server, with one row per combination of lockable object, requested mode, and holding or waiting process — so a single table or row can show up multiple times if several sessions are holding or waiting on it, while an object nobody currently has any claim on doesn't appear in the view at all. Its locktype column distinguishes what category of thing is actually being locked: whole relations, individual pages, individual tuples, transaction IDs, general catalog objects, and — relevant here — advisory locks. The same view is also where Serializable's machinery becomes visible operationally: the predicate locks backing its conflict detection show up in pg_locks tagged with a mode of SIReadLock, which is worth searching for specifically when diagnosing why a Serializable workload is producing more serialization failures than expected. Because pg_locks reports both held and awaited locks for every process, it's the standard starting point for untangling a session that appears stuck: cross-referencing its pid column against the running-query information in pg_stat_activity shows which session is actually executing versus which one is simply queued up behind someone else's lock.

### Advisory Lock Pitfalls: Evaluation Order and Shared Table Limits

A documented trap with advisory locks involves combining them with LIMIT and an ordering clause inside the same SELECT: SQL doesn't guarantee that LIMIT gets applied before a function sitting in the select list is evaluated, so a query that calls pg_advisory_lock(id) against a broad WHERE condition capped with LIMIT 100 can end up acquiring far more locks than the 100 rows the query ultimately returns, because the locking function may be evaluated against every row the WHERE clause matches before the LIMIT ever trims the output down. The documented fix is to push the filtering and limiting into a subquery first, and only call the advisory-lock function against that already-limited result from the enclosing query, so the function runs exactly once per row that's genuinely meant to be locked. Separately, advisory locks share the same underlying shared-memory lock table that ordinary table and row locks depend on, sized according to max_locks_per_transaction and max_connections, so a workload minting an enormous number of distinct advisory-lock keys can, in principle, exhaust that shared pool in much the same way a transaction that locks an unusually large number of ordinary tables could.

## Deadlocks & Serializable Failure Handling

### Anatomy of a Deadlock

A deadlock happens when two or more transactions are each waiting on a lock that another one of them is holding, so none of them can ever proceed — the classic shape is transaction A holding a lock on object X while it waits for a lock on object Y, at the same moment transaction B holds a lock on Y while it waits for a lock on X. This doesn't require explicit LOCK TABLE statements to occur; ordinary row-level locking can produce exactly the same cycle. Two transactions that each update two of the same rows, but in opposite order, are a common real-world example: the first transaction locks one row and then tries to lock a second, while the second transaction has already locked that second row and is now trying to lock the first — each one ends up stuck waiting on a lock the other refuses to release until it, in turn, gets the lock it's waiting on. PostgreSQL doesn't leave a deadlock hanging forever: it detects the cycle and forcibly aborts one of the participating transactions, letting the rest proceed normally. Exactly which transaction gets picked as the victim is intentionally left unspecified and shouldn't be relied on or designed around.

### deadlock_timeout: Why Detection Is Not Instant

Checking for a deadlock cycle is a relatively costly operation, so PostgreSQL doesn't run that check the instant a session starts waiting on a lock — it optimistically assumes deadlocks are the exception rather than the rule, and only bothers checking once a session has been waiting for deadlock_timeout, one second by default. Raising deadlock_timeout means fewer wasted deadlock checks fired against ordinary lock waits that were always going to resolve on their own, at the cost of a genuine deadlock taking longer to get reported and cleared once one actually happens; the documented guidance is to set it comfortably above how long a typical transaction is expected to hold its locks, so ordinary waits have a good chance of resolving before the expensive check ever triggers. The same setting doubles as the threshold for log_lock_waits, which, once enabled, logs a message any time a session has been waiting on a lock for longer than deadlock_timeout — a useful diagnostic even for contention that never actually escalates into a true deadlock.

### Preventing Deadlocks: Consistent Lock Ordering

Because a deadlock is fundamentally a cycle of transactions waiting on each other, the most reliable prevention is structural: make sure every transaction that touches more than one lockable object always acquires those objects' locks in the same relative order across the whole application, so a cycle simply can't form in the first place. In the two-row-update example, had both transactions touched the two rows in matching sequence instead of reversed sequence, neither one would have ended up stuck waiting on something the other was holding while itself holding what the other needed. A second piece of guidance is to take the strongest lock mode a transaction will eventually need on a given object as the very first lock it requests on that object, rather than escalating from a weaker mode partway through, since escalation is a common way deadlock-prone patterns creep into an application unnoticed. When a consistent order genuinely can't be guaranteed in advance — because it depends on data supplied at runtime, say — the fallback is to catch deadlock failures and retry the whole transaction, which is safe precisely because PostgreSQL always resolves a genuine deadlock rather than letting every participant hang forever; a transaction that isn't part of a deadlock, by contrast, will keep waiting on a lock indefinitely, which is exactly why holding a transaction open while waiting on something slow, like user input, is generally a poor idea.

### SERIALIZABLE Detects, It Does Not Block — Important Nuance

A natural but mistaken assumption is that Serializable isolation works by taking out heavier locks than Read Committed or Repeatable Read to physically prevent unsafe interleavings from happening at all. It doesn't. Serializable is implemented through predicate locking, tracked internally as SIReadLock entries visible in pg_locks, and those predicate locks exist purely so PostgreSQL can recognize, as transactions read and write data, when a particular combination of concurrent reads and writes could not be consistent with any one-at-a-time ordering of those same transactions. Critically, predicate locks never block anything by themselves and so can never become part of an actual deadlock; underneath, a Serializable transaction runs with essentially the same blocking behavior as Repeatable Read, and the extra cost is bookkeeping overhead to track dependencies rather than additional waiting during normal operation. When that bookkeeping does detect a dangerous pattern, PostgreSQL's response isn't to block one of the transactions and make it wait — it's to abort one of them outright with a serialization failure once the danger becomes clear. This is a meaningfully different failure mode from an explicit SELECT FOR UPDATE or an outright table lock, both of which genuinely block and, unlike predicate locks, can become part of an ordinary deadlock cycle.

### Retryable Errors: SQLSTATE 40001 and 40P01

Both Repeatable Read and Serializable transactions can fail with a serialization_failure error, always reported under SQLSTATE 40001, whenever PostgreSQL determines that letting the transaction proceed could produce a result inconsistent with any valid one-at-a-time ordering; deadlock victims are reported separately, under deadlock_detected, SQLSTATE 40P01. Applications running at these isolation levels are expected to catch both codes and retry — not merely resend the one statement that failed, but re-run the entire transaction from its beginning, including whatever application logic decided which values or which SQL to issue, since PostgreSQL deliberately provides no built-in automatic-retry facility that could safely do that substitution on the application's behalf. A retry isn't guaranteed to succeed on the very next attempt either; under heavy contention a transaction might need several tries before it finally commits, and if it happens to be blocked behind a still-open prepared transaction specifically, no amount of retrying helps until that prepared transaction is resolved one way or the other. It's occasionally also worth retrying a unique-violation (23505) or exclusion-violation (23P01) error encountered under Serializable, since those can sometimes be the visible symptom of an underlying serialization conflict the server wasn't able to attribute directly to 40001 — though those two codes can just as easily signal a genuine, persistent constraint violation, so retrying them without any further care is considerably riskier than retrying a 40001 unconditionally.

### Two Application-Level Strategies for Consistency Checks

When an application needs a multi-statement operation to see a consistent, tamper-proof view of the data it's checking — the classic example being confirming that total credits equal total debits across two tables that are both being actively updated — PostgreSQL supports two workable strategies rather than just one. The first is to run everything that needs this guarantee under Serializable isolation and lean entirely on its automatic conflict detection; done consistently, this needs no other special handling, though it works best paired with an automatic-retry layer somewhere in the application framework, so a serialization failure never has to surface as a user-visible error. The second is to fall back to Read Committed and take out explicit blocking locks instead — SELECT FOR UPDATE or FOR SHARE to pin down specific rows, or LOCK TABLE at SHARE mode or higher to guarantee no uncommitted changes exist anywhere else in an entire table — before performing the check. The two approaches aren't casually interchangeable: leaning on Serializable for this kind of guarantee doesn't currently extend to hot standby replicas or logical replication targets, so a deployment that reads from standbys for a check like this may still need to fall back to the explicit-locking approach on the primary.
