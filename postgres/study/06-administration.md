## Access Control: Roles, Privileges & Predefined Roles

### Roles Are the Only Kind of Principal — Important Nuance

Older releases of PostgreSQL, before version 8.1, kept users and groups as two separate kinds of catalog entities; today there is exactly one kind, the role, and whether a given role behaves like an individual login, a group other roles belong to, or both, is purely a matter of which attributes and memberships it happens to have. CREATE USER is not a distinct feature with its own logic underneath — it is the very same CREATE ROLE command under a second spelling, and the only thing that spelling changes is a single default: a bare CREATE ROLE leaves the new role unable to log in (NOLOGIN) unless you name LOGIN explicitly, whereas invoking the command as CREATE USER flips that one default so the role can log in unless you explicitly say NOLOGIN. Nothing else differs — password handling, connection limits, membership options, and how later ALTER ROLE or DROP ROLE commands treat the object are all identical either way. In practice this means a script that says CREATE USER app_owner PASSWORD 'x' and one that says CREATE ROLE app_owner LOGIN PASSWORD 'x' leave the cluster in exactly the same state, and any exam or interview question that treats 'user' and 'role' as separate concepts in PostgreSQL is really just asking whether you know that a user is nothing more than a role with LOGIN turned on.

### Role Attributes Control Capability, Not Object Access

A role carries a small set of cluster-level attributes that are set with CREATE ROLE or later changed with ALTER ROLE: SUPERUSER overrides every access check in the system and should be handed out sparingly; CREATEDB and CREATEROLE let a role mint new databases or new roles respectively (CREATEROLE also brings the ability to alter, drop, comment on, or set a security label on other non-superuser roles); LOGIN determines whether the role can be the identity a client connects as; REPLICATION governs whether it can open a physical or logical replication connection or manage replication slots; BYPASSRLS lets it skip row-level security policies entirely; and CONNECTION LIMIT caps how many concurrent sessions it may open. These are fundamentally different from the object-level privileges granted with GRANT: attributes describe what the role itself is allowed to do to the cluster, while privileges describe what it may do to a specific table, schema, or other object it doesn't own. A subtlety worth remembering is that attributes never flow through membership the way ordinary privileges can — belonging to a role that has CREATEDB, even with full inheritance enabled on that membership, does not let a member role create databases; the member would have to explicitly SET ROLE to the CREATEDB-bearing role first and issue the CREATE DATABASE from inside that session.

### Role Membership: GRANT role TO role, and Its Three Independent Options

Membership is how PostgreSQL builds group-like structures out of roles: GRANT some_role TO another_role makes the second role a member of the first, and that single grant can carry up to three separate yes/no options that each control something distinct. The ADMIN option decides whether the member can itself grant or revoke membership in the parent role to others — without it, an ordinary member has no say over who else joins; it defaults to false. The INHERIT option decides whether the member automatically picks up the parent role's object privileges just by being a member, with no further action needed — when unset it falls back to the new member's own INHERIT/NOINHERIT attribute at grant time. The SET option, which defaults to true, decides whether the member is even allowed to run SET ROLE to fully become the parent role for the rest of the session; reaching a role through several layers of membership only works via SET ROLE if every grant in that chain has SET enabled. PUBLIC functions as an implicit pseudo-role that every role is automatically a member of, which is why granting something to PUBLIC hands it to the entire cluster, present and future roles alike, without needing an explicit membership grant.

### The Privilege Model: Ownership, GRANT/REVOKE, and Defaults to PUBLIC

Creating an object makes the creating role its owner, and ownership itself carries an implicit right to alter or drop the object that can never be granted away or revoked from anyone else — the closest you can get to transferring it is reassigning ownership outright with an ALTER ... OWNER TO command, or granting membership in the owning role so someone else can SET ROLE into it. Everyone besides the owner starts with nothing and has to be handed privileges explicitly through GRANT, naming one of the specific privilege kinds — SELECT, INSERT, UPDATE, or DELETE for reading and changing rows; TRUNCATE for wiping a table wholesale; REFERENCES for building a foreign key against it; TRIGGER for attaching trigger definitions; CREATE, CONNECT, and TEMPORARY at the database, schema, or tablespace level; EXECUTE for calling functions and procedures; USAGE for schemas, sequences, types, and languages; SET or ALTER SYSTEM for touching configuration parameters; and MAINTAIN for VACUUM-style housekeeping commands — or writing ALL to cover whichever of those apply to the object's type; REVOKE takes a privilege back, and if it was originally granted WITH GRANT OPTION, revoking that option cascades to strip the privilege from everyone who received it downstream through that grantee. Because the owner is always treated as implicitly holding every grant option on their own objects, an owner can revoke and later re-grant their own privileges freely, which is a documented trick for briefly making a table read-only to yourself as well as everyone else. It's a common misconception that nothing is ever handed to PUBLIC by default — in reality PostgreSQL does auto-grant a few narrow defaults, such as CONNECT and TEMPORARY on newly created databases, EXECUTE on newly created functions and procedures, and USAGE on languages and data types, even though tables, columns, sequences, schemas, and tablespaces get nothing by default; ALTER DEFAULT PRIVILEGES can override any of this going forward.

### Predefined Roles: Delegating Slices of Superuser Capability

Rather than forcing an administrator to choose between handing out full SUPERUSER and leaving a helper role with almost nothing, PostgreSQL ships a set of predefined roles that bundle narrow, commonly needed privileged capabilities, which are simply granted like any other role membership, for example GRANT pg_monitor TO ops_dashboard. pg_read_all_data and pg_write_all_data act as though the grantee held SELECT, or INSERT/UPDATE/DELETE, plus schema USAGE, across every table, view, and sequence in the database, without bypassing row-level security policies. pg_monitor is really a convenience wrapper around three narrower roles bundled into one grant: it folds in the ability to read every configuration setting that pg_read_all_settings alone would unlock, the statistics-view access that pg_read_all_stats grants on its own, and the long-running scan functions pg_stat_scan_tables permits, so a single GRANT pg_monitor covers configuration values, statistics views, and those scan functions in one step rather than three. pg_signal_backend lets a role cancel a query or terminate another session's backend (though not one owned by a superuser), pg_checkpoint allows issuing CHECKPOINT, and pg_maintain covers a cluster of maintenance commands — VACUUM and ANALYZE for space and statistics upkeep, CLUSTER together with REFRESH MATERIALIZED VIEW for data rewrites, REINDEX for rebuilding indexes, and finally LOCK TABLE — across relations the grantee doesn't own individually. A handful of these predefined roles bypass ordinary database-level permission checks entirely: pg_execute_server_program can run programs as the operating-system account PostgreSQL runs under, pg_read_server_files can read any file that same account can see, and pg_write_server_files can write to any file location that account can reach, which in effect makes any of the three equivalent to superuser access and warrants the same caution before granting them out.

## Routine Maintenance: VACUUM, Autovacuum & Storage Reclamation

### Why MVCC Makes VACUUM Necessary

Because PostgreSQL implements multiversion concurrency control, an UPDATE or DELETE never immediately erases the row version it's replacing — the old version has to stick around as long as some other in-flight transaction might still legitimately need to see it, and only once no transaction could possibly need it anymore does that space become genuinely reclaimable. VACUUM is the mechanism that finds and reclaims that dead-tuple space, but reclaiming disk space is really just one of four jobs it performs on a regular basis: it also refreshes the planner's statistics (through ANALYZE, which can run on its own or as part of a combined VACUUM ANALYZE), it maintains a visibility map that records which pages hold only tuples every current and future transaction is guaranteed to be able to see, and it protects against transaction ID wraparound by periodically freezing sufficiently old rows. That visibility map earns its keep beyond just letting plain VACUUM skip pages with nothing to clean up — it also lets an index-only scan answer a query straight from the index without ever touching the underlying table, as long as every row on the relevant heap page is already known-visible, which matters most on large tables where skipping heap fetches saves real I/O.

### Plain VACUUM Never Shrinks the File; Only VACUUM FULL Does — Important Nuance

Standard VACUUM frees up the space taken by dead tuples so it can be reused by future inserts and updates in that same table, but it essentially never hands that space back to the operating system — the single exception is when one or more pages sitting at the very end of the table turn out to be completely empty and VACUUM can briefly grab an exclusive lock to truncate them off (a behavior that can be turned off per-table or cluster-wide via the vacuum_truncate setting if that brief lock is undesirable). Shrinking a table's actual on-disk footprint requires VACUUM FULL instead, which physically rewrites the entire table into a brand-new file containing no wasted space at all and then swaps that file in, at the cost of needing an ACCESS EXCLUSIVE lock for the whole operation and roughly double the disk space until the rewrite finishes. Just as importantly, autovacuum will never issue a VACUUM FULL on its own, under any configuration — its entire design goal is to run plain VACUUM often enough that a table settles into a steady-state size instead of ever needing a disruptive full rewrite, so a bloated table only gets shrunk back down when a human administrator deliberately runs VACUUM FULL (or an equivalent table-rewriting operation like CLUSTER) by hand.

### Freezing and the Transaction ID Wraparound Deadline

Every transaction gets a 32-bit transaction ID, and because that ID space is compared cyclically rather than linearly, a table that goes unvacuumed for roughly two billion transactions risks wraparound — old, perfectly valid rows would suddenly start looking like they were written in the future and effectively disappear from view, which is why PostgreSQL treats the approach of that limit as an emergency. VACUUM heads this off by freezing rows once they're old enough (governed by vacuum_freeze_min_age), marking them so they're always treated as being safely in the past regardless of how the XID counter eventually wraps; a full, aggressive vacuum sweeps every not-yet-frozen page in a table and is forced periodically based on vacuum_freeze_table_age. Crucially, autovacuum_freeze_max_age forces autovacuum to run an anti-wraparound vacuum against a table whose oldest unfrozen row has crossed that age threshold even when autovacuum has otherwise been disabled at the configuration level — this specific trigger cannot be turned off. If a table's oldest transaction IDs are still allowed to get dangerously close to the wraparound point, PostgreSQL starts logging warnings, and if those go unheeded it will eventually refuse to hand out new transaction IDs in that database entirely, at which point only a manual VACUUM run by a superuser (needed because ordinary roles can't vacuum system catalogs) restores normal write activity.

### Autovacuum’s Trigger Formula: A Fixed Threshold Plus a Percentage — Important Nuance

Autovacuum doesn't fire against a table on a fixed schedule; it decides per table by comparing the number of dead tuples accumulated since the last vacuum against a computed threshold, and that threshold is a formula: autovacuum_vacuum_threshold, which defaults to 50 rows, plus autovacuum_vacuum_scale_factor, which defaults to 0.2 (20 percent), multiplied by the table's estimated row count as recorded in pg_class.reltuples (with autovacuum_vacuum_max_threshold acting as an overall cap on that computed number, and a parallel formula using insert-specific parameters separately governing when insert-heavy tables get vacuumed). Because the scale-factor term scales with table size, a table with hundreds of millions of rows needs a correspondingly enormous number of dead tuples to accumulate — tens of millions, at the default 20 percent — before it crosses the threshold and autovacuum even considers touching it. That means a large, high-churn table left on default settings can quietly build up a large amount of bloat and go far longer between autovacuum passes than a smaller table would, which is exactly why experienced administrators lower autovacuum_vacuum_scale_factor (or set a hard cap via autovacuum_vacuum_max_threshold, or override thresholds per table through storage parameters) specifically for their biggest, busiest tables rather than leaving the cluster-wide defaults in place for everything.

### Tuning the Daemon and the Manual VACUUM Command’s Options

The autovacuum machinery is actually two kinds of processes: a single long-lived launcher that decides when to start work, spacing new workers roughly autovacuum_naptime seconds apart per database, and a pool of up to autovacuum_max_workers worker processes that actually run the VACUUM and ANALYZE commands, throttled by autovacuum_vacuum_cost_delay and autovacuum_vacuum_cost_limit so background maintenance doesn't overwhelm foreground I/O. Running VACUUM manually exposes several options worth knowing beyond FULL: FREEZE is shorthand for zeroing out vacuum_freeze_min_age for that one run, paired with a matching zero on vacuum_freeze_table_age, so the run forces aggressive freezing immediately; PARALLEL lets index processing use multiple background workers (and can be disabled outright with PARALLEL 0); and INDEX_CLEANUP, which defaults to AUTO, can be forced to ON to guarantee thorough index cleanup or OFF to skip index vacuuming entirely, which is sometimes used to race through a table as fast as possible when wraparound is imminent, though the vacuum_failsafe_age failsafe mechanism is generally the preferred way to handle that specific emergency. Nearly all of the autovacuum-related settings, from the thresholds to the cost delay, can also be overridden per table through storage parameters set on that table alone, which is the standard way to tune one especially hot table without touching cluster-wide defaults that affect everything else.

## Backup, Restore & Point-in-Time Recovery

### Three Backup Strategies, Three Different Trade-offs

PostgreSQL documentation describes three fundamentally different ways to protect a cluster's data, and each fits a different operational need rather than one simply being an upgrade of another. SQL dump — pg_dump for a single database, pg_dumpall for the whole cluster — produces a logical, portable export that can be replayed with psql or pg_restore, works across PostgreSQL versions and even different machine architectures, but reconstructs the data by re-executing SQL rather than copying bytes, so restoring a very large database can take considerably longer than the original load did. File-system-level backup means copying the underlying data directory directly — typically while the server is shut down, or through a storage snapshot capability that guarantees a consistent point-in-time image — and it restores quickly but only ever restores the entire cluster, never a single database or table, and its portability across architectures and PostgreSQL versions is far more limited than a logical dump's. Continuous archiving, covered in depth below, layers a stream of archived WAL segments on top of an occasional file-system-level base backup, trading extra operational complexity for the ability to recover to any specific moment in time rather than just the instant the backup was taken. A dump from pg_dump or pg_dumpall is purely logical output and cannot be combined with WAL replay — it isn't a valid input to the continuous-archiving recovery process at all.

### pg_dump: A Consistent Snapshot of One Database

pg_dump exports the contents of a single database as of a single consistent snapshot, taken without blocking any other session's reads or writes while it runs. It can write either a plain-text script of SQL commands that psql can replay directly, or one of the archive formats — custom or directory being the most flexible, tar being more limited — that must instead be fed to pg_restore, which can selectively restore just some of the archived objects, reorder them, or in the case of the directory format specifically, restore (and even dump) using multiple parallel jobs. Restoring from a plain SQL script versus an archive format is a meaningful choice: script dumps are the most portable and human-readable, while archive formats give an administrator far more control over exactly what gets loaded back and in what order. A --role option is available to have pg_dump issue a SET ROLE immediately after connecting, useful when the login role lacks the privileges pg_dump needs but can switch into a role that has them. The important nuance to hold onto is scope: pg_dump only ever touches one database, and by design it does not capture roles, tablespaces, or privilege grants on cluster-wide configuration parameters, because none of those things belong to any single database — a pg_dump backup, however carefully taken, silently leaves all of that cluster-wide state out.

### pg_dumpall: The Only Tool That Captures Cluster-Wide Objects — Important Nuance

pg_dumpall dumps an entire cluster into one script by connecting to each database in turn and internally calling pg_dump for it, then adding exactly the pieces pg_dump leaves out: database roles, tablespaces, and privilege grants on configuration parameters, since those objects live at the cluster level rather than inside any one database. Passing -g or --globals-only limits the run to just that cluster-wide layer without touching any individual database's data at all, which is the standard pairing for administrators who want the flexibility of pg_dump's archive formats and pg_restore's selective, parallel restore for their per-database data, while still using pg_dumpall --globals-only separately to preserve roles, tablespaces, and configuration-parameter grants. Because it needs to connect to every database in the cluster to do its job, pg_dumpall generally requires superuser access to produce a genuinely complete dump, and loading its output back typically needs elevated privileges too, since the script includes commands to create roles and databases. Skipping pg_dumpall entirely and relying only on per-database pg_dump backups is a common and easy way to lose track of exactly which roles existed, what they were permitted to do, and how tablespaces were laid out, since none of that state is reconstructed by replaying pg_dump output alone.

### pg_basebackup: Physical, Whole-Cluster Backups Over the Replication Protocol

pg_basebackup takes a physical copy of an entire running database cluster's data directory and any tablespaces, without blocking other clients, by connecting over the replication protocol rather than as an ordinary SQL client — the connecting role needs the REPLICATION attribute (or superuser) and the server needs max_wal_senders configured high enough to spare a wal sender for the backup. Unlike pg_dump, it never operates on anything smaller than the whole cluster; there is no option to back up a single database or a single table with pg_basebackup, and selective backups of that kind require pg_dump instead. It can produce either a full backup — an exact copy of every file — or, given the manifest from a prior backup, an incremental backup containing only the blocks that changed since that reference point, which then has to be merged back together with pg_combinebackup before it's usable on its own. pg_basebackup output commonly serves two purposes: as the base copy that a stream of archived WAL segments gets replayed against for point-in-time recovery, and as the starting point for a new streaming-replication standby server, a use case the -R flag streamlines directly by writing a standby.signal file and the necessary connection settings into the backup's output automatically.

### WAL Archiving and Point-in-Time Recovery

PostgreSQL continuously writes a record of every change to a write-ahead log, physically divided into fixed-size segment files that the server would ordinarily just recycle once their contents are no longer needed for crash recovery. Continuous archiving intercepts that recycling: with wal_level set to replica or higher, archive_mode turned on, and either an archive_command shell command or an archive_library configured, PostgreSQL hands each completed segment off to be copied somewhere durable before it would otherwise be reused. The payoff is that a single base backup, combined with an unbroken sequence of archived WAL segments covering the time since that backup was taken, lets recovery replay forward to any specific moment the administrator chooses within that window, rather than being stuck restoring to the exact instant the base backup finished — this is what point-in-time recovery actually means. A useful side effect is that the base backup itself doesn't need to be perfectly internally consistent, since WAL replay corrects any inconsistency the same way ordinary crash recovery does, which is also exactly the mechanism a warm-standby server relies on when it's fed the same continuous stream of WAL segments in near-real time. As with the file-system-level strategy, this technique only ever restores an entire cluster, and pg_dump or pg_dumpall output — being logical rather than physical — cannot be substituted into any part of this WAL-replay process.

## Server Configuration, Extensions & Partitioning

### Four Layers for Setting a Parameter

postgresql.conf is the base layer: one parameter assignment per line, with the last occurrence of a repeated entry winning, and it's re-read whenever the postmaster gets a SIGHUP — most conveniently triggered with pg_ctl reload or by calling pg_reload_conf() from SQL — though a subset of parameters only ever take effect at a fresh server start no matter how the file changes. Layered on top sits postgresql.auto.conf, a second file with the same syntax that ALTER SYSTEM writes to automatically rather than being hand-edited, which is why manually editing it while the server is running is discouraged unless allow_alter_system has been turned off to prevent a concurrent ALTER SYSTEM from clobbering the manual change. Above the file-based layer come two SQL commands that set defaults scoped more narrowly than the whole cluster — ALTER DATABASE overrides a parameter for every session that connects to one particular database, and ALTER ROLE overrides it for every session a particular role opens — though both of these only take effect for sessions that start after the change, never for ones already connected. Finally, within an already-open session, SET (and the equivalent set_config() function) changes the value for just that session or, with SET LOCAL, just the current transaction, and SHOW (or current_setting()) reads back whatever value is currently in effect after all four layers have been applied.

### Parameter Categories: Orienting Yourself in runtime-config

The server configuration reference organizes its hundreds of parameters into named categories, and recognizing which bucket a setting falls into is often the fastest way to guess how disruptive changing it will be. Connections and Authentication covers things like max_connections and SSL settings; Resource Consumption spans memory sizing (shared_buffers, work_mem), disk usage, background-writer behavior, and worker-process limits; Write-Ahead Log has its own subcategories for general WAL settings, checkpoints, archiving, and recovery; Replication covers sending servers, the primary, standbys, and subscribers separately; Query Planning holds the planner-method switches and cost constants that shape execution plans; Error Reporting and Logging and Run-time Statistics control observability; Vacuuming holds the autovacuum family of parameters; and Lock Management governs things like deadlock_timeout. As a rule of thumb, parameters that affect shared memory layout or fundamental process structure — most of Connections, Resource Consumption, and WAL — tend to require a full server restart, parameters that don't change memory layout can usually take effect on a plain reload, and many Query Planning and logging parameters can even be set per session with an ordinary SET, so knowing a parameter's category is a quick way to predict which of those three you're in for before you go looking up the exact context value.

### Extensions: Bundling Related SQL Objects Behind One Command

An extension packages everything a piece of add-on functionality needs — new functions, operators, data types, index support methods, whatever the feature requires — behind a control file describing the extension's name, its default version, whether installing it needs superuser privileges (or is marked trusted so any role with plain CREATE privilege on the database can install it), and whether its objects can be relocated to a different schema after the fact, plus one or more SQL script files that actually create those objects. Running CREATE EXTENSION executes the relevant script and, just as importantly, records exactly which catalog objects belong to that extension, which is what makes DROP EXTENSION able to remove the entire bundle in one command instead of requiring a hand-maintained uninstall script. pg_dump cooperates with this bookkeeping: rather than dumping every individual object an extension created, it just emits the CREATE EXTENSION call itself (along with whatever GRANT and REVOKE statements are needed to restore privileges recorded in pg_init_privs), which is a large part of why moving an extension to a newer version is far simpler than migrating a pile of loose, hand-created objects — ALTER EXTENSION UPDATE handles that version bump using an update script the extension author supplies, and CREATE EXTENSION ... CASCADE will pull in and install any extensions the requested one depends on automatically.

### Declarative Partitioning: Range, List, and Hash

A partitioned table is a virtual construct with no storage of its own — every row that gets inserted into it is actually routed, based on the value of its partition key columns, into one of several ordinary child tables called partitions that do hold the real data, and PostgreSQL supports three built-in ways to decide that routing. Range partitioning assigns each partition a span of values with the lower bound inclusive and the upper bound exclusive, commonly used for date-based partitioning; list partitioning assigns each partition an explicit, enumerated set of key values; and hash partitioning splits rows across a fixed number of partitions by computing a hash of the partition key modulo some chosen number and assigning each partition one or more of the resulting remainders. The appeal of built-in partitioning over older workarounds like table inheritance or UNION ALL views is threefold: query performance improves when a query can be satisfied by scanning only the partitions that could possibly contain matching rows, bulk loading or purging old data becomes as cheap as attaching or dropping a whole partition instead of inserting or deleting rows one at a time (which also sidesteps the VACUUM overhead a row-by-row bulk delete would generate), and old partitions can be migrated onto cheaper, slower storage once they're rarely queried.

### Attaching and Detaching Partitions Without Locking Out the Whole Table

Creating a partition directly with CREATE TABLE ... PARTITION OF locks the whole parent at ACCESS EXCLUSIVE for as long as the command runs, which can be disruptive on a table that's actively being queried. The more concurrency-friendly alternative is to build the new table as a completely ordinary, standalone table first — loading and validating its data at leisure — and only then run ALTER TABLE ... ATTACH PARTITION, which needs just a SHARE UPDATE EXCLUSIVE lock on the parent rather than an ACCESS EXCLUSIVE one. Attaching does still scan the incoming table under an ACCESS EXCLUSIVE lock on that table specifically, in order to verify its data actually satisfies the partition's bounds, unless a matching CHECK constraint enforcing those same bounds already exists on the table beforehand, in which case the scan is skipped entirely and the now-redundant CHECK constraint can simply be dropped once the attach completes. The reverse operation is symmetric: ALTER TABLE ... DETACH PARTITION ordinarily needs ACCESS EXCLUSIVE on the parent, but adding the CONCURRENTLY qualifier drops that requirement down to SHARE UPDATE EXCLUSIVE, at the cost of some added restrictions on the command, and turns the detached table back into an ordinary standalone table — useful when the plan is to back it up, transform it, or otherwise inspect it further before eventually dropping it for good.

### Partition Pruning: Skipping Partitions the Query Could Never Match

Partition pruning is the optimization that keeps declarative partitioning fast: rather than scanning every partition of a partitioned table and filtering out the ones a WHERE clause excludes, the planner examines each partition's declared bounds and, whenever it can prove a partition couldn't possibly hold any row matching the query, removes that partition from the plan before execution ever begins. This pruning happens purely based on the partition key constraints implicit in how the table was declared, not based on whatever indexes exist, so it works even on partitions with no indexes at all, though indexing decisions on the partitions that do survive pruning still matter in the usual way. Because not every value needed to prune is known at planning time — a value coming from a subquery, a parameter bound through PREPARE, or a value fed in from the inner side of a parameterized nested-loop join — pruning can also happen during execution itself, either once during plan initialization (pruned partitions here simply never appear in EXPLAIN output, though they are still briefly locked at the start of execution) or repeatedly during the run as parameter values change (visible in EXPLAIN ANALYZE output as a reduced loops count, or as subplans marked never executed). The whole mechanism is controlled by the enable_partition_pruning setting, on by default, and turning it off is mainly useful as a diagnostic to compare an unpruned plan against a pruned one.
