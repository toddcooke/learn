## Physical (Streaming) Replication Fundamentals

### Log Shipping and the Primary/Standby Relationship

PostgreSQL's built-in high-availability story starts from continuous archiving: instead of the primary hoarding its write-ahead log for crash recovery alone, a standby server continuously consumes that same log and replays it against its own copy of the data files. The server whose writes it's replaying is called the primary (or read/write server); the server doing nothing but replay is a standby. Because WAL can be handed over either as complete, filled 16MB segment files copied through an archive_command, or incrementally as records are generated, this technique has two flavors: file-based log shipping, and the finer-grained streaming replication layered on top of it. Either way, a standby only enters this mode because a standby.signal file is present in its data directory at startup, and it keeps retrying — first the archive, then any WAL already sitting in its own pg_wal, then a live connection to the primary — in a loop that continues until it's either stopped or promoted.

### Turning File-Based Shipping into Streaming Replication

A plain log-shipping standby only gets a new segment's worth of changes once that segment fills up, which is why streaming replication exists: pointing the standby's primary_conninfo setting at the primary opens a live connection over which WAL records arrive as they're generated, rather than in 16MB batches. That one setting is really the only thing that upgrades a file-based standby into a streaming one; everything else about setting up the standby stays the same. The primary needs listen_addresses and pg_hba.conf configured to accept the connection, and the connecting role needs either the REPLICATION attribute or superuser status, since the WAL stream can leak sensitive data to anyone able to read it. A successful connection shows up as a walreceiver process on the standby paired with a walsender process on the primary, and max_wal_senders on the primary caps how many such connections — from standbys or from tools like pg_basebackup — can exist at once.

### Replication Slots: Automated WAL Retention

A standby that falls behind is only safe if the WAL it still needs hasn't already been recycled by the primary. Before slots existed, the only defense was wal_keep_size, a blunt setting that reserves a fixed cushion of old segments regardless of whether any standby actually needs them. A replication slot instead lets a standby register itself with the primary so the primary tracks, per slot, exactly how far behind that consumer is and refuses to remove or recycle WAL the slot still depends on — retaining only what's genuinely required rather than an arbitrary buffer. The same mechanism also protects against a subtler problem: a disconnected standby whose slot is still registered keeps the primary from vacuuming away rows that standby's eventual queries would still need to see. The obvious danger is the mirror image of the benefit — a standby that never reconnects can make its slot hold an ever-growing pile of WAL, which is why max_slot_wal_keep_size exists as a cap on how much a slot is allowed to retain before it gets invalidated.

### Asynchronous by Default — What "Synchronous" Actually Guarantees

It's easy to assume streaming replication keeps a standby perfectly in step with the primary, but out of the box it doesn't: replication is asynchronous by default, meaning a transaction is considered committed the moment its WAL record is durable on the primary alone, and the standby catches up moments later — typically under a second, but with no hard guarantee. Turning on synchronous replication is opt-in, done by naming one or more standbys in synchronous_standby_names, and it changes what a commit actually waits for. But being 'synchronous' isn't one fixed guarantee — synchronous_commit controls exactly how far the standby has to get before the primary's commit is allowed to return: remote_write only waits for the standby to hand the record to its own operating system, which could still lose it in an OS crash even though PostgreSQL itself didn't crash; the default on waits for the standby to actually flush the record to durable storage; and remote_apply goes further still, waiting until the standby has replayed the record and the change is genuinely visible to queries running there. Choosing between these levels is really choosing between received, flushed, and applied as the bar a standby has to clear before the primary's client gets an acknowledgment.

### Priority and Quorum Among Multiple Synchronous Standbys

When more than one standby is listed in synchronous_standby_names, the list's syntax decides how they get chosen. A FIRST num_sync (list) entry is priority-based: the num_sync standbys named earliest in the list become the synchronous set, and if one of them drops out, the next-highest-priority name on the list is promoted into that role immediately, with no interruption beyond a brief handoff. An ANY num_sync (list) entry is quorum-based instead: a commit proceeds once any num_sync of the named standbys — not any particular ones — have confirmed, which tolerates a standby dropping out without needing a strict ranking. A newly attached standby doesn't count toward either form right away; it first has to work through a catch-up period until its lag reaches zero, and only after reaching that steady real-time streaming state can it actually serve as a synchronous standby. If the primary itself restarts while commits are still waiting on acknowledgment, those transactions are simply marked committed once the primary comes back, since there's no way to be certain after a crash exactly what every standby had already durably received.

### pg_basebackup: Bootstrapping a New Standby

Setting up any physical standby — warm or hot — starts from a base backup, and pg_basebackup is the tool built for that job. Rather than connecting as an ordinary SQL client, it authenticates over the replication protocol using a role with REPLICATION privilege or superuser status, and it copies the entire cluster's data directory and tablespaces in one pass; there's no option to grab a single database or table this way, which is exactly the gap pg_dump fills instead. It can produce either a full copy of every file or, given the manifest from an earlier backup, an incremental copy of just the blocks changed since that reference point (later merged back together with pg_combinebackup before it's usable). The -R flag is the shortcut aimed squarely at standby setup: it writes a standby.signal file into the backup's output and appends the connection settings needed for streaming replication automatically, so the copied directory can be started up as a working standby with essentially no manual editing. Running pg_basebackup against an already-running standby is also supported, letting a cluster spread the load of taking backups away from the primary entirely.

## Logical Replication: Publish/Subscribe Model

### Decoding Row Changes Instead of Copying Blocks

Where physical (streaming) replication ships raw, byte-identical WAL and requires the standby to be a mirror image of the primary down to page layout, logical replication decodes that same WAL stream back into a sequence of row-level insert, update, and delete operations, tied to each table's replication identity rather than to any physical block address. That decoding step is what makes logical replication so much more flexible: a subscriber can run a different major PostgreSQL version than its publisher, live on a different operating system, and hold only a subset of the publisher's tables or even just a filtered slice of one table's rows, none of which physical replication can do since it needs an identical cluster underneath. A subscriber behaves like any other ordinary PostgreSQL instance otherwise — it can itself publish to further downstream subscribers, and because changes arrive as regular DML, ordinary triggers on the subscriber fire for each incoming row exactly as they would for a local write, which physical replication's replay mechanism never triggers at all.

### Publications: Scoping What a Publisher Sends

A publication, created on the publisher with CREATE PUBLICATION, is nothing more than a named, explicit set of tables — or, using the ALL TABLES form, every table in that one database — whose changes are worth exporting; it exists inside exactly one database and has no bearing on how the underlying tables are otherwise accessed. Membership can be scoped further with a WITH (publish = ...) clause naming which operation kinds actually get sent, drawn from insert, update, delete, and truncate, though that filter only shapes ongoing replication traffic and has no effect on the one-time initial copy a new subscription performs when it first attaches. ALTER PUBLICATION can add or drop individual tables at any point after creation, and because both operations are transactional, a table starts or stops being replicated at a clean, well-defined snapshot boundary rather than mid-transaction. A single table isn't limited to one publication either — it can belong to several at once, each potentially scoped to a different set of operations or a different downstream audience.

### Replica Identity: How a Row Gets Matched for UPDATE and DELETE

INSERT never needs any special row-matching logic, but UPDATE and DELETE do — the subscriber has to know which of its own rows corresponds to the one being changed, and that's what a table's replica identity supplies. Left at its default, that identity is simply the table's primary key; a suitable unique index can be nominated in its place if there's a reason to prefer one. When neither is available, REPLICA IDENTITY FULL is the fallback, treating every column together as the identifying key, but this comes at a real cost: without a matching index on the subscriber to search by, the subscriber may end up scanning the whole target table to locate each incoming change, which gets expensive fast on a large table. A table with no replica identity at all — or one whose designated unique index has since been dropped — can still accept inserts through the publication, but any UPDATE or DELETE reaching it will simply error out on the publisher, since there'd be nothing precise for the subscriber to match against.

### Subscriptions and the Replication Slots Behind Them

A subscription, defined on the downstream side with CREATE SUBSCRIPTION, bundles a connection string pointing back at the publisher together with the list of publications it wants; a single subscriber can hold several subscriptions if needed, though care has to be taken that overlapping ones don't fight over the same table. Each active subscription is fed by exactly one replication slot maintained on the publisher, and PostgreSQL manages the whole lifecycle automatically by default — the slot is created the moment the subscription is, and dropped the moment DROP SUBSCRIPTION removes it. Bringing a fresh table's existing data across at subscription time relies on extra, short-lived synchronization slots that exist only for the duration of that initial copy and disappear on their own once it's done. Because tables aren't matched by any hidden identifier, the publisher and subscriber tables have to share the same fully-qualified name, though column order between the two sides is free to differ, and the subscriber's table is even allowed extra columns of its own, which simply get filled from their declared defaults on every incoming row.

### What Logical Replication Deliberately Leaves Out

Several categories of change never cross a logical replication link at all, and knowing them ahead of time avoids some painful surprises. DDL is the biggest one — schema changes on the publisher are not replicated, so a new column or an altered constraint has to be applied to the subscriber by hand, and if replicated data arrives that no longer fits the subscriber's older schema, replication simply halts with an error until the two are reconciled. Sequences are excluded too: a serial or identity column's current values travel over as ordinary row data, but the underlying sequence object on the subscriber keeps whatever start value it was given, which matters enormously if a subscriber is ever meant to be promoted into a writable role — its sequences need to be caught up manually first, or new inserts will immediately collide with already-replicated keys. Large objects have no logical replication path whatsoever, with no built-in workaround beyond migrating that data into an ordinary table instead. And only genuine tables (plain or partitioned) can be a subscription's target — a view, materialized view, or foreign table is rejected outright as an invalid destination.

## High Availability & Failover

### Ending Standby Mode: pg_ctl promote and pg_promote()

A standby stays a standby only until something tells it to stop replaying and start accepting writes of its own, and that transition — promotion — has to be triggered explicitly: an administrator issues pg_ctl promote at the shell, or an already-connected session calls the pg_promote() SQL function directly against the standby. Right before making that switch, the server finishes replaying whatever WAL is already sitting locally, in its archive or its pg_wal directory, but it makes no further attempt to reach out to the old primary for anything more recent — once promotion begins, that connection is treated as irrelevant going forward. Not every standby needs this at all: a reporting replica that exists purely to soak up read-only analytical queries, with no intention of ever becoming a write target, can simply stay in standby mode indefinitely rather than ever being promoted. Once promotion does happen for an HA-oriented standby, though, it's expected to take over primary duties in full, including archiving and accepting its own new set of standby connections.

### No Built-In Automatic Failover — By Design

It would be easy to assume that a database engine this mature ships some kind of watchdog that notices a dead primary and promotes a standby on its own, but PostgreSQL deliberately does not include that piece. The core distribution has no software for detecting that the primary has actually failed (as opposed to being merely slow, or momentarily unreachable over a flaky link) and no software for automatically deciding which standby, if any, should be promoted in response — both jobs are left entirely to third-party tooling built specifically for that purpose, such as Patroni or repmgr, which layer failure detection, leader election, and orchestrated promotion on top of PostgreSQL's own replication primitives. Whatever tool is used, it also has to solve a second problem beyond simply picking a new primary: once a standby is promoted, the old primary — if it's still running, just unreachable — must be stopped from ever accepting writes again — a safeguard administrators often refer to by its blunt acronym, STONITH, shorthand for forcibly powering down whatever node still refuses to concede it lost primary status. Skipping that step risks a split-brain scenario where two servers both believe they're the primary and diverge, which is a far worse outcome than the original outage.

### The Degenerate State and Rejoining a Cluster

The moment a standby is promoted, the topology described in this domain — one primary feeding one or more standbys — briefly collapses into just a single server doing everything alone, a condition the documentation calls a degenerate state. Getting back to a properly redundant setup means building a new standby again, either by turning the just-recovered old primary into one, or by standing up a fresh machine entirely and repeating the base-backup-plus-WAL-stream setup from scratch. Rebuilding the former primary from a full base backup works but throws away a lot of data the two servers still share; pg_rewind exists specifically to shortcut that, resynchronizing the former primary against the new one by identifying and copying over only the pages that actually diverged after their histories split, rather than recopying the entire cluster. Because switching roles this way is a normal, well-tested procedure rather than an emergency-only maneuver, some teams schedule planned switchovers on a regular cadence — it lets each server take turns for maintenance downtime, and doubles as a live rehearsal that the failover machinery genuinely works.

### A Taxonomy of Replication and HA Approaches

Streaming and logical replication are PostgreSQL's own built-in answers, but they sit within a much broader family of techniques, each trading off performance, granularity, and failure guarantees differently. Shared-disk failover sidesteps synchronization entirely by having every server point at one physical disk array, which trades a single point of storage failure for zero replication overhead. File-system-level (block device) replication, with DRBD being a well-known Linux example, mirrors every disk write to a second machine below the database layer, so it needs no PostgreSQL-specific support but requires writes to land on the mirror in the same order they hit the primary. WAL shipping — this domain's own streaming and file-based replication — only ever works at whole-cluster granularity, never per-table, but can run synchronously or asynchronously as covered earlier. Trigger-based systems and SQL-broadcasting middleware, by contrast, operate per-table or per-query, but each brings its own hazards: trigger-based tools typically batch asynchronously, risking data loss on failover, while middleware that simply rebroadcasts SQL to every server can produce diverging results wherever a query touches something nondeterministic, like random() or CURRENT_TIMESTAMP. Notably, PostgreSQL doesn't ship a synchronous multimaster solution of its own at all — building one is left to application code or middleware, typically leaning on two-phase commit.

### Cascading Replication: Standbys That Relay WAL

A standby isn't limited to only receiving WAL — with the right configuration (max_wal_senders and hot_standby enabled, plus matching host-based authentication) it can also act as a sender to further standbys downstream, a role called a cascading standby. The server closer to the primary in that chain is described as upstream relative to the servers further out, which are downstream; nothing about the mechanism caps how many downstream servers a single cascading standby can feed, or how deep the chain can run, as long as it all eventually traces back to one primary. The main payoff is reducing both the number of direct connections the primary itself has to service and the cross-site bandwidth a geographically spread deployment would otherwise burn shipping the same WAL to every location separately. One limitation worth remembering is that cascading replication is always asynchronous no matter what synchronous_standby_names says on the primary — synchronous replication settings simply don't reach through a cascade. Feedback from hot_standby_feedback does still travel the opposite direction, though, propagating back upstream through however many cascaded hops separate a standby from the primary.

## Read Scaling & Connection Pooling

### Warm Standby vs Hot Standby: Two Genuinely Different Things

These two terms sound like a matter of degree, but they describe a real functional split. A warm standby is a server that's continuously replaying WAL from the primary but cannot be queried at all while it does so — the only thing it can offer is a fast promotion later; trying to connect to one simply fails. A hot standby is the same replay process with one crucial addition: the hot_standby parameter, on by default, lets the server accept ordinary client connections and serve read-only queries while recovery is still actively running in the background. Turning that capability on requires wal_level to have been set to replica or logical back on the primary, since a lower level doesn't log enough information for the standby to reconstruct a consistent snapshot. Reaching that queryable state isn't instantaneous either — the server has to first replay far enough to hit a consistent recovery point, logging its own readiness message once it gets there, and only then does it genuinely function as a read-scaling target rather than just a disaster-recovery placeholder.

### What a Hot Standby Session Can and Cannot Do

Every session opened against a hot standby is permanently read-only — transaction_read_only is locked to true for the whole session and can't be toggled off. Ordinary reads, cursors, session-setting commands, and read-only transaction control all work normally, but anything that would need to write a WAL record of its own is rejected outright: row-modifying DML and any DDL both fail immediately, as does locking a row FOR UPDATE or FOR SHARE, since taking a row lock means writing to the underlying data files. Two-phase commit's prepare step is blocked too, for a subtler reason — even the first phase of a read-only transaction still has to write WAL, which a hot standby session is never allowed to do. Somewhat surprisingly, LISTEN and NOTIFY are also off-limits here, even though both are normally permitted for plain read-only sessions on the primary, making hot standby connections marginally more restricted than an ordinary read-only transaction elsewhere. Because replayed changes take a moment to arrive and apply, a query against the standby can also legitimately return slightly older results than the same query run against the primary at the same instant — the standby is described as eventually consistent rather than perfectly synchronized.

### Recovery Conflicts: When the Standby Has to Cancel a Query

The primary has no visibility into what queries are currently running against any of its standbys, so when it does something like drop a table or let VACUUM clean up rows that are still technically visible to an old standby snapshot, the standby can find itself with an incoming WAL record it's obligated to apply but that directly conflicts with a query still reading the data being removed. Since the standby can't simply refuse to replay — the primary already committed to that change — it instead gives the conflicting query a grace period before forcibly canceling it, governed by one delay setting for WAL arriving live over streaming and a separate one for WAL being caught up from an archive. One escape hatch is hot_standby_feedback, which has the standby tell the primary about its oldest still-needed row versions so the primary's own VACUUM holds off on removing them — this eliminates that particular class of cancellation, but the tradeoff runs in the other direction: rows the primary would otherwise have reclaimed now sit around longer, which can measurably increase table bloat back on the primary itself, especially if the standby disconnects for extended stretches without dropping its feedback.

### No Built-In Pooler: Why an External Layer Is Standard

PostgreSQL hands every client connection its own dedicated backend process rather than multiplexing many client sockets through a shared pool of workers, and max_connections is simply a hard ceiling on how many of those processes can exist at once — nothing in the core server itself sits in front of that limit deciding which client gets a slot when demand spikes past it. That gap is exactly what an external connection pooler fills, and the de facto standard tool for the job is PgBouncer, a small, standalone proxy that presents itself to applications as an ordinary PostgreSQL server while internally maintaining and reusing a much smaller set of actual backend connections behind it. Because PgBouncer is a separate project maintained outside the core PostgreSQL distribution, its behavior — and in particular the different modes it can pool connections in — isn't described anywhere in PostgreSQL's own manual at all, which is exactly why understanding it means turning to PgBouncer's own documentation rather than the server's.

### PgBouncer's pool_mode: Session, Transaction, and Statement

pool_mode is the single setting that decides how aggressively PgBouncer is willing to hand a backend connection to a different client. Its default, session, only releases a server connection back to the shared pool once the client that was using it disconnects entirely — the safest option, since it behaves exactly like a direct connection from the application's point of view, but it also gives the least reuse, since one idle client session still ties up one real backend the whole time. transaction mode releases the server connection as soon as each transaction commits or rolls back, letting far more clients share a small pool of backends, but this comes with a real catch: because two statements in what looks like the same client session can end up executed against two entirely different backend processes, anything that depends on session-scoped state — a SET variable, a prepared statement issued outside PgBouncer's own tracking, an advisory lock, a temporary table — stops behaving reliably, and PgBouncer even skips its usual cleanup query in this mode on the assumption that no session state needs to persist between transactions. statement mode goes one step further still, handing the connection back after every individual query, which pushes reuse to its practical maximum but flatly disallows any transaction spanning more than one statement. Paired with routing read-only traffic to hot standbys, a transaction-pooled PgBouncer layer in front of the whole cluster is the common practical shape of read scaling and connection pooling working together.
