## Monitoring Fundamentals: What and How to Measure

### Latency, Traffic, and Errors: The Three Straightforward Golden Signals

Of the four golden signals the SRE book proposes as the minimum viable set for any user-facing system, three map onto fairly intuitive questions. Latency asks how long a request took to answer, and the book insists on tracking failed-request latency separately from successful-request latency, since a backend that fails fast by returning an error in a few milliseconds can drag a blended average down in a way that hides how damaging a genuinely slow, user-visible failure actually is — a sluggish failure is worse for a user than a quick one. Traffic is simply how much demand the system is absorbing, expressed in whatever unit fits the workload: requests per second for a web tier, concurrent sessions for a streaming service, transactions per second for a key-value store. Errors is the rate of requests that didn't succeed, and the book is careful to note that a success status code isn't proof of success — a response that returns HTTP 200 with the wrong payload, or a request that technically completes but blows past a promised response-time bound, both count as failures that raw protocol codes won't surface on their own, which is why some services need a secondary, service-specific signal layered on top of status codes alone.

### Saturation: Not CPU Percentage, But How Full the System Is

Saturation is the golden signal most often reduced to a single convenient number and just as often measured wrong. The SRE book ties it to whichever resource is currently the tightest constraint on the system — memory in a memory-bound service, disk I/O in an I/O-bound one — rather than to a generic CPU percentage that merely happens to be easy to scrape. That distinction matters because most systems begin degrading well before any one resource reaches full utilization, so a raw usage number without a calibrated target says little about how close the system actually is to trouble. Saturation is also explicitly forward-looking rather than a snapshot of the present: the book's own example is predicting that a database will fill its disk in a few hours, and it points out that a short-window 99th-percentile response time can serve as an early warning of saturation, since queues start backing up and tails start stretching before any utilization graph crosses an obvious line. Services with no dial that changes request complexity can sometimes get away with a single number pulled from a load test, but most real services fall back on indirect proxies like CPU or bandwidth precisely because a true measure of remaining headroom is hard to observe directly.

### Black-Box Monitoring: Testing What a User Would Actually See

Black-box monitoring is often assumed to be a statement about where a check runs — outside the network perimeter, hitting a public-facing address — but the definition that matters is about orientation, not location: it means testing externally visible behavior the way a user would experience it, which makes it inherently symptom-oriented and limited to reporting problems that are already happening rather than ones about to happen. A synthetic probe that logs in, walks through a checkout flow, and times the whole sequence counts as black-box regardless of whether it happens to run from inside the same datacenter as the service under test. Its chief value for paging is the discipline it imposes: because a black-box check can only detect a symptom that's already manifesting, every resulting page corresponds to a real, currently active problem, which keeps false positives down. Its chief weakness is the same restriction working in reverse — a black-box check is blind to anything that hasn't yet become externally visible, so a slowly filling disk or a memory leak creeping toward exhaustion stays invisible until it has already caused a user-facing failure.

### White-Box Monitoring: Reading a System's Own Internals — and Why the Line Moves

White-box monitoring is the complementary half of the pair, built from telemetry a system exposes about itself — logs, in-process counters, an internal-state endpoint — rather than from how the system looks from the outside. Because it can see internal state directly, it can catch trouble before it becomes externally visible, including failures that automatic retries are quietly hiding from users for the moment. What's easy to miss is that the black-box/white-box split isn't really about internal versus external tooling at all; it's about whether a given signal describes a symptom or a cause, and that framing shifts depending on where someone sits in a multilayered system. A database team watching its own read latency treats a slowdown there as the very symptom it's investigating, while a frontend team calling that same database experiences the identical slow reads as the cause behind its own separate symptom — a sluggish website. So white-box telemetry can be symptom-oriented or cause-oriented depending entirely on how informative a particular internal signal happens to be for whoever is looking at it.

### Why Monitor at All? Five Jobs Beyond 'Something Might Be Broken'

It's tempting to reduce monitoring to 'the thing that pages me,' but the SRE book lists alerting as only one of several distinct jobs a monitoring system performs. Long-term trend analysis answers slow-moving questions — how fast a database is growing, how quickly daily active users are climbing — nothing urgent on its own, but exactly the kind of data capacity planning depends on. Comparing behavior across time or across experiment groups answers questions like whether a new storage backend is actually faster, or whether a site has quietly gotten slower than it was last week, by giving two comparable measurements to weigh against each other. Building dashboards is its own job: a dashboard exists to answer a service's basic standing health questions at a glance, and the book recommends anchoring that view to the four golden signals so different teams' dashboards stay legible to people who didn't build them. Ad hoc retrospective analysis — essentially debugging — rounds out the list: when latency suddenly spikes, monitoring data is what lets someone ask what else happened at that same moment. Treating all five as legitimate uses, rather than collapsing everything into 'will this trigger a page,' is part of what keeps a monitoring system from becoming either noisy or blind.

### Metrics and Logs: Two Complementary Sources of Monitoring Data

The workbook draws a practical line between the two main raw materials a monitoring pipeline consumes. Metrics are numerical measurements sampled at regular intervals, and a metrics pipeline trades away some granularity for near-real-time delivery — the property that makes it suitable for the alerts and dashboards an on-call engineer actually watches during an incident. Logs are append-only records of individual events, and structured logs in particular support rich after-the-fact queries, but there's inherent lag between an event happening and it becoming visible in processed log output, since log pipelines tend to be batch-oriented. The practical division of labor that falls out of this is that alerts and dashboards lean on metrics, because a page needs to arrive within minutes, while root-cause investigation leans on logs, since that's usually where the specific, high-cardinality detail a metric never bothered to export actually lives. The workbook even suggests that when a single rare event needs to trigger a page, it's usually better to add a counter metric that increments on that event than to build a separate log-based alerting path, just to keep every alert defined inside one consistent system.

## Alerting Philosophy: Symptoms, Causes, and Playbooks

### What's Broken vs. Why It's Broken: Alerting on Symptoms

The SRE book frames good alerting around a single split: every signal either tells you what's broken (a symptom) or why it's broken (a cause), and the book calls this one of the most important distinctions for writing rules with a high signal-to-noise ratio. Its worked examples make the split concrete — serving HTTP 500s is a symptom, a database refusing new connections underneath is the cause; slow responses are a symptom, an overloaded CPU or a half-severed network cable is the cause; a group of users silently missing content is a symptom, a content-delivery network's IP blocklist is the cause. Because paging a human is expensive in attention and sleep, the guidance is to bias alerting rules toward symptoms — active, currently user-visible failures — and reserve cause-oriented signals mostly for debugging once a human is already looking, rather than as independent page triggers. The underlying intuition is that a symptom answers 'is a user hurting right now' directly, while chasing every possible cause invites both false positives and a rule set whose maintenance burden grows with every new failure mode a team happens to learn about.

### From Time-Series to a Page: How an Alerting Rule Actually Fires

Rule-based alerting on time-series data works by having a monitoring system continuously aggregate a metric — say, the ratio of non-200 responses to total requests across every task in a job — and compare that result to a threshold. When the comparison becomes true, the rule is only pending at first; it has to stay true for a minimum duration, commonly at least two evaluation cycles, before the alert is actually considered to be firing, a delay that exists specifically to stop a metric briefly crossing a line from paging someone over a non-event. Once an alert does fire, it carries a severity label that determines where it goes: genuinely urgent, page-worthy conditions route to an on-call rotation, important-but-not-urgent conditions route to a ticket queue instead, and everything else is left to accumulate as status information on a dashboard rather than interrupting anyone. A central alert-routing layer sits downstream of the raw rule evaluation and can deduplicate alerts fired by redundant monitoring instances, suppress one alert while a related one is already active, and fan alerts in or out based on shared labels — mechanics that matter because, without them, one underlying problem can otherwise generate a flood of nearly identical pages.

### The Alerting Checklist: Questions to Run Through Before Adding a New Page

Beyond the symptom/cause split, the SRE book distills its alerting philosophy into a short set of questions worth asking before wiring up any new page-worthy rule: does this detect an otherwise-undetected condition that's urgent, actionable, and already or imminently visible to users; will there be situations where it's safe to just ignore this alert, and if so, why does that scenario exist in the first place; does it definitely correspond to real user harm, or does it need to filter out things like drained traffic and test deployments that look bad but aren't; can a human take a concrete action in response, and could that action just be automated instead; and is someone already being paged for the same underlying issue, making this one redundant? Alongside those questions sits a blunter set of expectations for what a page itself should be: every page should be actionable, should demand real judgment rather than a rote response, and should represent something novel rather than a repeat of an already-diagnosed issue — because a person can only sustain genuine urgency a handful of times a day before fatigue sets in and even the real pages start getting waved away.

### Playbooks Cut Mean Time to Repair by Roughly 3x

Emergency-response quality is measured in mean time to repair, or MTTR, and the SRE book's introductory chapter makes a specific claim about what moves that number: thinking through best-practice responses ahead of time and writing them into what the book calls a playbook produces roughly a threefold improvement in MTTR compared with an on-call engineer improvising from a blank page. The point isn't that a playbook replaces judgment — the book is explicit that no playbook, however thorough, substitutes for an engineer capable of reasoning through a genuinely novel incident on the fly — but that a prepared responder consistently beats even a talented generalist working from scratch, because a playbook removes the overhead of first having to figure out what to even try. That's also why Google pairs playbooks with rehearsal: exercises that walk a group through recent real incidents build the same kind of familiarity a playbook encodes, well before anyone is actually paged for the equivalent live event.

### Maintaining Playbooks: The Staleness Problem, and When to Automate Instead of Document

A playbook is only as good as its last edit, and the workbook's on-call chapter is candid that playbook entries go out of date at roughly the same pace as the production system they describe — a team shipping changes daily may need to revisit its playbooks just as often. It also surfaces a real disagreement among practitioners about how detailed an entry should be: some argue for keeping entries broad and durable, such as one general entry covering every 'elevated RPC error' alert paired with a current architecture diagram, on the theory that broad guidance ages more slowly; others push for precise, step-by-step instructions specifically to reduce variance between different engineers' responses and drive MTTR down further, accepting that those instructions will demand more frequent upkeep. Rather than settling that tension in the abstract, the workbook's practical suggestion is to agree as a team on some minimal structure every entry must contain, watch for entries that accumulate detail beyond that minimum, and treat that accumulation itself as a signal — if a playbook has hardened into a deterministic list of commands run identically every time one particular alert fires, that's a strong candidate for turning into automation rather than something a human keeps re-reading under pager pressure.

## SLO-Based (Burn-Rate) Alerting

### Burn Rate: Spend Relative to the SLO Window, Not an Absolute Percentage

Burn rate measures how quickly a service is consuming its error budget relative to a sustainable pace defined entirely by the SLO's own compliance window — it is never a standalone, absolute number. A burn rate of exactly 1 means the current error rate, if it held steady, would exhaust the entire budget precisely at the end of that window and no sooner; for a 99.9% SLO measured over 30 days, that works out to a constant 0.1% error rate sustained across the full 30 days. A burn rate of 2 doubles the pace and exhausts that same budget in half the time — 15 days for the same monthly window — and the relationship keeps scaling from there: against that same 99.9% target, a burn rate of 1,000 corresponds to a full outage, which would drain an entire month's budget in well under an hour. Because burn rate is always expressed against the SLO's own window rather than as a bare error-rate cutoff, one identical instantaneous error rate implies a completely different burn rate depending on what the underlying SLO and its time window actually are — which is exactly what makes burn rate a portable building block for alerting logic across services with different targets.

### Why a Naive Error-Rate Threshold Makes a Bad Alert

The workbook walks through several increasingly refined attempts at SLO-based alerting to show why the obvious first approach falls short. Simply paging whenever the error rate over a short window — say ten minutes — crosses the SLO threshold detects a real outage almost instantly, but its precision is poor: a brief blip that only spends a sliver of a monthly budget crosses the exact same line a full outage would, so a service could trigger well over a hundred such pages in a single day without ever actually threatening its SLO. Widening the window to demand a larger, more meaningful chunk of budget consumption before alerting fixes precision but wrecks the opposite property: once triggered by a genuine outage, the alert keeps firing for as long as that wide window still contains the bad data, so a short total outage can leave a page stuck active for well over a day after the underlying problem is already resolved. Layering on a minimum-duration requirement — demanding the condition hold for, say, an hour before paging — filters out short-lived noise, but it decouples how fast the alert fires from how severe the incident actually is: a complete outage and a barely-over-threshold blip both wait the same hour to page, and if the metric so much as dips back under the line for a moment, many implementations reset that duration timer, so a genuinely damaging but fluctuating error rate can end up never paging at all.

### Alerting on Burn Rate Directly: Better, but Still Missing Slow Burns

The workbook's next refinement fixes the tradeoff by alerting on burn rate itself rather than on raw error rate: pick a fixed alert window, decide how much budget consumption over that window counts as significant, and derive the burn-rate multiplier that produces exactly that spend. For a 99.9% SLO over 30 days, deciding that a one-hour window consuming 5% of the monthly budget deserves a page works out to a burn-rate threshold of 36 — meaning the current error rate needs to be 36 times what a sustainable, budget-neutral rate would be. This version keeps both detection time and reset time reasonably short while improving precision, but it opens a new gap: a sustained error rate that sits just under that threshold never crosses the line and so never pages, even though, left running, it would still exhaust the entire monthly budget well within a day. That's a recall problem — a real, budget-threatening incident can slip past a single fixed burn-rate threshold simply by staying just below it, which is what motivates layering on more than one threshold rather than trusting any single cutoff.

### Multiwindow, Multi-Burn-Rate Alerting: Catching Fast and Slow Burns Together

The fix is to stop relying on one threshold and instead evaluate several burn-rate cutoffs at once, each paired with its own window size, so both a fast-moving severe outage and a slower but still dangerous sustained problem have a path to alerting. A short window with a high burn-rate threshold catches severe incidents almost immediately; a longer window with a lower threshold catches slower leaks a short window would otherwise blow right past. To also fix the reset-time problem — a long evaluation window keeps an alert active for a while after the underlying issue has already cleared — the recommended technique pairs each long window with a much shorter confirmation window, roughly one-twelfth its length, and only fires when both windows agree the burn rate is still elevated; that way the alert clears almost as soon as the short window's average drops back under its threshold, instead of waiting out the entire long window. Slower-burning issues that would still eventually exhaust a large share of the budget over several days get routed to a ticket rather than a page, since nothing about them justifies interrupting someone immediately.

### The 99.9% SLO Reference Table: 14.4x/1hr and 6x/6hr to Page, 1x/3day to Ticket

The workbook publishes one concrete set of numbers as a starting point for a 99.9% SLO, built from the multiwindow technique. Page when the burn rate exceeds 14.4x sustained across both a one-hour window and a five-minute confirmation window, which corresponds to burning 2% of the monthly budget within that hour. Also page when the burn rate exceeds 6x sustained across both a six-hour window and a thirty-minute confirmation window, corresponding to a 5% budget spend across six hours. And route to a ticket rather than a page when the burn rate exceeds 1x sustained across both a three-day window and a six-hour confirmation window, representing 10% of the monthly budget spent over three days — real, but not urgent enough to wake anyone at 3 a.m. These particular multipliers are explicitly a starting point tuned to a 99.9% target and one organization's tolerance for how much of a month's budget is worth interrupting someone over; the workbook is clear that the right numbers for a different SLO, or a different team's pager tolerance, need to be derived the same way rather than copied wholesale.

### When Burn-Rate Alerting Breaks: Low-Traffic Services and Extreme Reliability Targets

Multiwindow, multi-burn-rate alerting assumes enough request volume that an error rate is a meaningful statistical signal, and that assumption fails at both ends of the traffic spectrum. A service handling only ten requests an hour turns a single failed request into a 10% hourly error rate, which against a 99.9% SLO works out to roughly a 100x burn rate — far past the 14.4x paging threshold, enough to page immediately, even though it might just be one client hitting a transient, uninteresting failure; the workbook's suggested fixes include generating synthetic traffic to add signal, folding several related low-traffic services into one shared budget, or changing the service so a single failure costs users less. At the opposite extreme, a service with an extremely high availability target has almost no budget to spend at all: at 99.999% availability, a total outage burns an entire month's budget in about 26 seconds, faster than most monitoring pipelines can detect, notify, and get a human to act on — so burn-rate alerting alone cannot defend that level of reliability, and the workbook's answer is to design the system so a total outage is inherently unlikely in the first place, for instance by capping the blast radius of any single rollout with staged, low-percentage traffic shifts.

## Observability Over Time: Dashboards and Time Horizons

### Two Different Clocks: Near-Real-Time Alerting vs. Longer-Term Trend Analysis

Monitoring data serves purposes that pull toward different technical tradeoffs, and the workbook's discussion of choosing a monitoring system treats them almost as separate requirements rather than one. Alerting needs freshness: data more than roughly four to five minutes stale can meaningfully slow how fast a system pages someone, and too much lag between taking an action during an incident and seeing that action reflected on a graph can lead an engineer to misjudge whether a fix actually worked. Longer-term analysis wants the opposite trade — retaining data over months, even if that historical view is coarser summary data rather than every individual point — because a long baseline is what actually reveals a slow-building trend that a five-minute window simply can't show, the kind of question the SRE book raises when it asks how fast a database is growing or how quickly daily active users are climbing. The same underlying design choice that makes long-window rate calculations practical — monotonically increasing counters, computed over windows stretching up to a month — turns out to be the same building block burn-rate SLO alerting relies on, so the near-real-time and long-term sides of a monitoring system are less separate in practice than the different requirements might suggest.

### Dashboards as an Interface, Not a Data Store

A dashboard is a prebuilt, purpose-built view of a service's core metrics, and the workbook treats the choice of visualization as a genuine design decision rather than an afterthought: plain time-series graphs, tables, heatmaps, histograms, and logarithmic-scale graphs each surface a different kind of pattern, and picking the wrong one can bury the exact thing a dashboard was supposed to make obvious — a linear-scale graph, for instance, can hide a small but important service in the shadow of a much larger one plotted on the same axes. The same underlying data often needs more than one dashboard because different audiences want different things from it: an engineer debugging an incident wants to drill into individual request types, binary versions, or datacenters, while someone checking on general service health wants a far higher, more stable summary. The workbook's advice is to keep presentation consistent within an audience — the same categories of data shown the same way across a team's dashboards — because that consistency is exactly what lets someone unfamiliar with a particular service still make sense of its dashboard at a glance, which matters most during an incident, when there's no time to learn an unfamiliar layout.

### Anchoring Dashboards to the Four Golden Signals

Both books converge on the same recommendation for a dashboard's default view: show some form of the four golden signals — latency, traffic, errors, and saturation — because together they answer the handful of questions almost anyone looking at a service's health needs answered first, without requiring deep familiarity with that particular service's internals. The SRE book frames this as a natural consequence of building dashboards around the same signals used for alerting, so someone moving from a page to the dashboard that triggered it lands on data already laid out in a way they recognize. The workbook adds a layer underneath that top-level view: once a dashboard shows that an SLO is being violated, it typically can't explain why on its own, so the practical pattern is to pair the golden-signal SLO summary with secondary panels covering things like a service's own recent binary or configuration changes and the health of its direct dependencies — the same four categories, applied one layer down, to whatever the service depends on.

### From Alert to Root Cause: What Belongs on a Debugging Dashboard

Once an SLO-based alert fires, the SLO dashboard itself typically shows that a violation is happening but not why, so a useful debugging dashboard needs a second layer of metrics purpose-built for diagnosis rather than for alerting. Tracking a service's own recent changes — binary version, command-line flags, the version of any dynamically pushed configuration — turns 'did we do this to ourselves' into a quick glance at a graph instead of a search through separate deployment records. Tracking the request size, response size, latency, and response code of every direct dependency, ideally instrumented once inside a shared client library rather than reimplemented per team, extends the golden-signal framing outward to everything a service relies on, rather than stopping at its own boundary. And because metrics meant for alerting and metrics meant for debugging serve different jobs — an alerting metric should barely move except when something is genuinely wrong, while a debugging metric is expected to fluctuate constantly and just needs to point toward what's fluctuating — mixing the two on one dashboard without distinguishing them tends to confuse whoever is staring at it mid-incident.

### Long-Term Monitoring Decisions: The Bigtable and Gmail Lessons

The SRE book closes its monitoring chapter with two case studies showing why decisions about monitoring need a long time horizon, not just a reaction to today's page. Bigtable's team once measured its SLO against mean latency, and a heavy tail dragged that mean around enough that both email and paging alerts fired constantly; the fix wasn't more alerting sophistication but the opposite — temporarily loosening the target to the 75th percentile and turning off the noisy email alerts entirely, which bought enough breathing room to actually repair the underlying storage-stack problems instead of firefighting them indefinitely. Early Gmail faced a different version of the same tension: alerts fired whenever individual backend tasks were descheduled, which was unmanageable at a scale of many thousands of tasks each representing a sliver of users, and the team debated whether to fully automate a fix or leave a human performing a repetitive, scriptable nudge — a debate the book frames as really being about whether the team trusted itself to build the durable fix once the immediate pain of paging subsided. Both cases make the same point: a page addressed only with today in mind just trades a small amount of immediate relief for a worse monitoring system down the road.
