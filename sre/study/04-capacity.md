## Load Balancing Across the Stack

### DNS Load Balancing and Its 512-Byte Ceiling

The first opportunity to spread traffic comes before a client even opens a connection: resolving a hostname to an address. The simplest version just returns several A or AAAA records and lets the client pick one arbitrarily, which is trivial to implement but gives almost no control — each address ends up attracting roughly equal traffic regardless of how close it actually is to a given user. Making that worse, most users don't talk to an authoritative nameserver directly; a recursive resolver sits in between, caching answers and forwarding them to a whole population of users the authoritative server never actually sees, which means a reply optimized for the resolver's location isn't necessarily optimized for the humans behind it. An extension that lets a resolver forward a hint of the client's subnet helps close that gap, and anycast addressing for the nameservers themselves helps route a lookup to a nearby answer in the first place. But underneath all of that sits a hard architectural ceiling: a DNS answer has to fit inside the 512-byte payload that the original DNS specification allows for a reply, which caps how many server addresses can be listed in one response to a number that's almost certainly smaller than a large service's actual server count. That ceiling is exactly why DNS resolution alone is only ever a first, coarse layer of traffic distribution, meant to be paired with a second layer working beneath it.

### Virtual IPs and the Network Load Balancer

Once a client has an address, a virtual IP (VIP) lets that single address actually be served by a whole pool of machines rather than one physical host, so the pool's size and membership can change — for maintenance, for capacity, for failure recovery — without the client ever noticing. The device sitting in front of that pool, the network load balancer, has to pick a real backend for every incoming packet. Tracking the least-busy backend sounds ideal but requires holding per-connection state; a cheaper stateless alternative hashes fields of the packet and takes the result modulo the number of backends, but that scheme falls apart the moment a backend is added or removed, because changing the backend count shifts almost every hash result to a different machine and resets nearly all existing connections at once. Consistent hashing solves that instability by keeping the vast majority of mappings unchanged when the backend pool resizes, so only a small slice of connections need to move. For actually getting a packet onto the chosen backend, one option rewrites only the destination address at the data-link layer so the reply can go straight back to the sender without passing through the balancer again — cheap, but it forces every balancer and backend onto the same physical broadcast domain, which breaks down once a service outgrows a single facility. Encapsulating the original packet inside another one (with the balancer's own address as the outer destination) removes that constraint, letting the balancer and backend sit on entirely separate networks or continents, at the cost of a slightly larger packet. A backend also needs a clean way to leave rotation: rather than dropping connections abruptly, it can enter a 'lame duck' state that tells clients to stop sending it new work while letting requests already in flight finish normally, which is what makes routine restarts and rolling updates invisible to users.

### Subsetting the Backend Pool: Why Random Assignment Falls Apart

Letting every client task hold an open connection to every backend task doesn't scale — each connection costs some memory and periodic health-check overhead on both ends, and that overhead multiplies badly once a service has hundreds of clients and hundreds of backends. Subsetting caps how many backends a given client actually connects to, typically somewhere between twenty and a hundred, but picking which backends make up that subset turns out to be surprisingly hard to get right. Shuffling the backend list once and handing out the first slice to each client — the obvious naive approach — spreads load far less evenly than intuition suggests: with three hundred clients, three hundred backends, and each client connecting to thirty of them, the least-loaded backend ends up around half the average connection count and the busiest around one and a half times average, and shrinking the subset further only makes the spread worse. Reaching genuinely even load through pure randomness alone would require subset sizes so large — on the order of three-quarters of the whole pool — that the approach stops being practical at any real scale. The fix groups clients into 'rounds' and reshuffles the backend list independently for each round, so that when a handful of backends inside one client's subset fail simultaneously, the load they were carrying spreads across the entire backend pool rather than concentrating on whichever few machines happen to remain in that one narrow subset — the difference between a manageable blip and a self-inflicted local overload.

### Backend Selection Policies: Round Robin, Least-Loaded, and Weighted Round Robin

Once a client has a healthy subset of backends to choose from, it still needs a policy for picking one per request. Plain round robin — cycling through the subset in order — is the simplest option and clearly beats picking randomly, but in practice it can leave roughly a two-to-one gap in CPU usage between the least and most loaded backend, driven by clients that issue requests at different rates, requests whose cost can vary by several orders of magnitude depending on what they actually ask for, machines within the same fleet that aren't quite identical in performance, and transient effects like a newly restarted process needing extra resources to warm up. Least-loaded round robin narrows the field to whichever backends currently have the fewest requests outstanding and round-robins only among those — an improvement, but with a specific and dangerous failure mode: a backend that's badly broken and failing every request almost instantly can look, by this metric, like the least busy machine in the pool, so healthy-looking clients pile new traffic onto it — a pattern worth naming because it inverts the intended effect entirely; counting recent errors as if they were still-active requests closes that gap. Least-loaded round robin also has a blind spot of its own: outstanding-request count says nothing about how much actual CPU a request needs, and each client only sees the slice of a backend's load that it personally generated, not the aggregate from every other client. Weighted round robin closes both gaps by having backends report their own observed utilization and error rate back with every response, so clients can continuously adjust how much traffic each backend deserves — in practice this narrows the spread dramatically compared to either simpler policy.

### A Concrete Stack: Anycast, Maglev, and the Google Front End

Google's own public load balancing product illustrates how the layers above combine in a real system, and deliberately skips DNS-based balancing altogether in favor of anycast: a single virtual address is announced from many points in the network, and standard internet routing carries a client's packets to whichever announcing site is topologically nearest, without needing per-user DNS geolocation logic or the propagation delay DNS caching imposes. Because routing tables occasionally recalculate and can silently redirect an in-progress connection to a different site mid-stream, the software load balancer sitting at the edge — Maglev — adds a stabilizing layer on top of anycast: if a Maglev machine ends up holding a packet meant for a client that's actually closer to a different site, it forwards that packet onward to a Maglev machine at the correct site rather than serving it locally, keeping the TCP stream coherent even as routes shift underneath it. Maglev itself scales by simply adding more machines to the pool that shares incoming traffic, and relies on consistent hashing plus per-machine connection tracking so that most packets belonging to an existing connection can be routed without any state having to be shared across the whole Maglev fleet. Behind Maglev sits the Google Front End, which terminates the client's encrypted connection, reads enough of the request to decide which backend service should handle it, and re-encrypts the request on its way in — while a separate global software layer tracks backend health across every cluster and steers traffic away from ones that are failing, so that a customer's service can keep serving even while individual clusters come and go.

## Forecasting and Provisioning for Demand

### Validating Forecasts Instead of Trusting Them

A demand forecast is only as useful as the discipline applied to checking it: the practice is to keep comparing what a forecast predicted against what actually happened, and to keep doing so until the two consistently agree, rather than treating an initial forecast as settled fact. Persistent divergence between predicted and actual demand is itself a warning sign — it suggests the forecasting method is unreliable, that current provisioning is probably wrong in one direction or the other, and that the service carries real risk of a capacity shortfall precisely because nobody would see it coming from the forecast alone. The companion discipline applies to the other half of the equation: rather than assuming that a cluster of a given size can still handle the same traffic rate it handled months ago, load testing should be used to re-establish that resource-to-capacity ratio on an ongoing basis, since the software, its dependencies, and the mix of requests it receives all tend to drift over time even when the hardware hasn't changed. Both practices are meant to run continuously rather than once at launch — a forecast or a load-test result from a quarter ago is exactly the kind of assumption most likely to have quietly gone stale.

### N+2 Provisioning: Surviving a Planned and an Unplanned Outage at the Same Time

It's easy to assume that redundant capacity means keeping enough spare instances to absorb losing any one of them — an 'N+1' posture, tolerant of a single fault. Google's own capacity-planning guidance sets a noticeably higher bar: provision so the service can still handle peak traffic, even if only in a degraded mode, while its two largest instances are simultaneously unavailable. The extra margin isn't about doubling down on paranoia for its own sake; it's about timing. Planned maintenance — draining a datacenter for upgrades, rotating hardware out of service — happens on a schedule that has nothing to do with when an unplanned failure might strike, and sooner or later those two kinds of events will overlap. A service that's only built to survive one simultaneous loss has nothing left in reserve the moment a scheduled drain collides with a hardware fault or a network partition somewhere else. In practice, this means treating capacity equal to your two largest deployments as headroom that's never counted toward serving steady-state traffic at all, so that even the worst-case overlap of a scheduled outage and a genuine surprise still leaves enough of the fleet standing to absorb what those two instances would otherwise have carried.

### Day-One Load Isn't Steady-State Load

A new feature or product often draws a burst of curiosity-driven traffic that has little to do with how much traffic it will carry once the novelty wears off, and that gap between launch-day demand and steady-state demand can be enormous — some products have seen opening spikes run up to fifteen times higher than what teams had projected going in. A well-known example: Keyhole, the imagery service behind Google Maps and Earth, normally serves a few thousand satellite images per second, but on the Christmas Eve a NORAD Santa-tracking site it powered went live, it absorbed roughly twenty-five times its usual peak — over a million requests per second — driven by nothing more than millions of kids waiting to watch Santa's progress. Because a launch spike is a different traffic mix than steady state, not just a bigger version of it, load-test results gathered against ordinary traffic patterns can be misleading, and rolling a launch out to one region or country at a time is a common way to build confidence before exposing a product to the whole world at once. Capacity planning for a launch also has to fold in the same redundancy math used everywhere else: if three replicated deployments are enough to fully cover peak traffic, the actual plan should run four or five, holding the extra one or two back purely as a buffer — and because datacenter and network resources can take a long time to provision, that buffer has to be requested well ahead of the launch date, not scrambled together once traffic is already climbing.

### The Pokémon GO Case Study: When Real Demand Beat Even the Padded Estimate

Niantic load-tested Pokémon GO's stack against up to five times its most optimistic pre-launch traffic estimate — already a generous safety margin. The actual launch request rate landed near fifty times that same estimate, roughly ten times higher than what the team had already over-built for. The overload cascaded in a specific, traceable sequence: frontend proxies couldn't keep up with the sheer number of inbound connection attempts, and connections refused at that stage never even showed up in the monitoring meant to catch trouble; backends, rather than failing fast, slowed down dramatically, which meant requests started timing out at the load-balancing layer instead of erroring out cleanly; the load balancer retried those timed-out requests, adding still more load onto an already struggling backend; and the mobile app's own retry logic — a single immediate retry followed by a constant backoff — synchronized across huge numbers of users into a 'thundering herd' that spiked global traffic to roughly twenty times its already-elevated peak, which in turn degraded the shared frontend fleet's own capacity by about half worldwide. Recovery involved isolating the frontends serving Pokémon GO from the shared load-balancer pool, growing that isolated pool until it could absorb the (degraded) demand, and finally imposing an administrative cap on how much traffic the load balancers would accept for the app at all, buying Niantic room to stabilize and scale up properly. Afterward, Niantic rebuilt its client retry logic around jittered, truncated exponential backoff instead of synchronized constant backoff, and both companies concluded that the only reliable way to avoid repeating this is to measure demand as close to the actual client as possible — server-side estimates alone had badly understated what was coming.

### Autoscaling: A Provisioning Tool, Not a Substitute for Capacity Planning

Autoscaling can absorb demand that capacity planning didn't fully anticipate, but it has enough sharp edges that it works best as a supplement to planned headroom rather than a replacement for it. Averaging utilization across every instance breaks down if some of those instances aren't actually healthy — a job stuck starting up, or a zombie task that never recovered — because unhealthy instances still count toward the average and mask the fact that scaling is genuinely needed; reading a capacity signal from the load balancer instead, and giving new instances a cooldown period before their metrics count, avoids that trap. Stateful systems don't necessarily benefit from adding instances at all, since traffic tied to a specific backend can't simply be rebalanced by growing the pool — task-level routing that actively redistributes load, rather than just more machines, tends to matter more there. Because scaling up too slowly risks dropped traffic while scaling down too aggressively barely risks anything, autoscalers are usually tuned asymmetrically — quick to add capacity, cautious and slow to remove it — and configuring the service to stay well clear of its actual bottleneck matters because new capacity is never instantaneous. Bounding an autoscaler with explicit minimum and maximum limits, and keeping an easy manual override or kill switch on hand, guards against the scenario where a bug or a stuck dependency causes runaway growth that burns through quota without fixing anything. And because scaling one service up can shove unplanned extra load onto whatever it depends on — sometimes starving sibling services that share the same quota pool — a dependency review before deploying an autoscaler is what keeps a locally sensible scaling decision from becoming somebody else's capacity emergency.

## Surviving Overload: Shedding, Degrading, and Preventing Cascades

### Criticality Levels: Four Tiers for Deciding Whose Requests Survive

Every request flowing through Google's RPC framework carries one of four criticality values, and it's that value — not simply how busy the sender happens to be — that decides who gets sacrificed first once a backend or a customer's quota starts running short. CRITICAL_PLUS is reserved for requests where failure causes serious, unambiguous user-visible harm. CRITICAL is the default for ordinary production traffic: still meaningfully user-visible if it fails, but less catastrophic than CRITICAL_PLUS, and services are expected to provision enough capacity to fully cover both of these tiers under normal conditions. SHEDDABLE_PLUS is the default for batch work that can simply be retried minutes or hours later, where some partial unavailability is already an accepted cost of doing business. SHEDDABLE traffic is expected to see frequent partial and occasional full unavailability without anyone being surprised. Criticality is deliberately independent of latency requirements — a search-suggestions request that appears as someone types is highly sheddable, perfectly fine to simply not show under load, yet still needs to come back quickly on the occasions it is served, so the two axes are tracked separately rather than assumed to move together. Criticality also propagates automatically down a call tree: a backend handling a CRITICAL request that in turn issues its own outgoing requests passes that same CRITICAL label along by default, which is what lets a deeply nested dependency shed load in a way that stays consistent with the priority set all the way up at the original request, rather than each layer inventing its own local notion of what matters.

### Client-Side Adaptive Throttling: A Client-Cooperative Brake, Not a Server-Enforced Wall

Rejecting an overloaded request still costs a backend something — parsing it, running the rejection logic — and if enough of a backend's incoming traffic consists of requests doomed to be rejected anyway, the backend can end up overloaded largely by the cost of saying no. Adaptive throttling addresses this by moving part of the decision out to the client itself, cooperatively rather than by server fiat: each client tracks, over roughly the trailing two minutes, how many requests it attempted versus how many the backend actually accepted. Under healthy conditions those two counts stay close together. As a backend starts rejecting more traffic, the client keeps sending real requests out over the network only until the attempted count grows to some multiple K of the accepted count — once that ratio is crossed, the client begins turning away a growing share of its own new requests locally, before they ever reach the network, with the rejection probability rising smoothly as the gap widens rather than flipping on all at once. This is fundamentally a mechanism the client runs on itself, reacting to what it's observed from the backend, rather than a rule the backend or a load balancer imposes and enforces centrally — the backend never has to know a particular client is throttling itself. The multiplier K is a tunable knob: setting it close to 1 throttles more aggressively and wastes less backend capacity on doomed requests, while a looser default deliberately lets more traffic through than will ultimately be accepted, trading some wasted backend effort for faster detection once the backend actually recovers.

### Retry Budgets and the Retry Amplification Problem

Retrying a failed request makes sense when a single backend task happens to be having a bad moment, but that logic stops holding once a meaningful slice of a whole datacenter is actually overloaded, because every retry just adds more load to the same overloaded pool it's trying to route around. The distinction that matters is scope: if only a small subset of backend tasks are struggling, an immediate retry is likely to land somewhere healthy and succeed; if a large subset of the datacenter is overloaded, retrying only compounds the problem, and the failure should be allowed to propagate straight back to the original caller instead of being quietly retried. Two separate budgets keep retries themselves from spiraling: a per-request budget caps any single logical request at a small, fixed number of attempts — three is a common choice — before giving up rather than trying forever, and a separate per-client budget tracks what fraction of a client's overall outgoing traffic consists of retries, refusing to retry at all once that fraction crosses roughly ten percent, since a client retrying more than that is itself evidence that more than one unlucky task is involved. A related discipline applies to deep call stacks: only the layer sitting immediately above whichever component is doing the rejecting should retry, not every layer above it independently, because retry rates compound multiplicatively as they climb a stack — a handful of retries permitted at each of several layered services can turn a single user action into dozens of attempts hitting the lowest layer, which is exactly the wrong direction to push a component that's already struggling.

### Graceful Degradation vs. Load Shedding: Doing Less, Versus Doing Nothing

The two main responses to overload are related but distinct, and mixing them up in conversation tends to muddy the actual engineering tradeoffs. Load shedding rejects a request outright once a task is judged too busy — a fast, cheap 'no' rather than any attempt at an answer — while graceful degradation instead keeps computing an answer but a cheaper, lower-quality one: searching a smaller slice of an index, falling back to a slightly stale cached copy instead of hitting canonical storage, or dropping an expensive secondary feature while still returning the core result. Shedding usually happens through per-task throttling on signals like CPU, memory, or how deep a request queue has grown, and the shape of that queue matters more than it might seem: a plain first-in-first-out queue keeps working through requests whose callers have quite possibly already given up and retried elsewhere, wasting effort on answers nobody will use, whereas a last-in-first-out ordering (or a similar queue-management scheme) tends to drop exactly the requests least likely to still matter — especially effective when paired with deadlines that propagate down the call stack, so a request whose caller already timed out never gets picked up for processing at all. Because graceful degradation only fires during rare overload events, it's also one of the least-exercised code paths a service has, which is precisely the reason it needs deliberate testing: deliberately pushing a small slice of production near its overload threshold on an ongoing basis, and alerting if too many servers slip into degraded mode too often, is what keeps that rarely-used path from quietly rotting until the day it's actually needed.

### Cascading Failure, Precisely Defined: Positive Feedback, Not Just 'Several Things Broke'

It's tempting to label any incident where multiple components failed together a cascading failure, but the term describes something narrower and worth pinning down precisely: a cascading failure is one that grows over time specifically because of positive feedback, where each individual failure directly raises the odds of the next one — not simply several components failing around the same time from one shared underlying cause. The canonical shape starts small: one replica in a fleet fails under overload, which shifts its share of traffic onto the remaining replicas, which raises their load and therefore their own odds of failing next, which pushes even more traffic onto whoever's left standing — a domino effect capable of taking down an entire fleet within a couple of minutes, often faster than the load-balancing and scheduling systems reacting to it can actually intervene. The same feedback loop shows up inside a single overloaded process before it ever spreads to its neighbors: running short on CPU makes every request slower, which means more requests are in flight simultaneously, which consumes more memory, which — on a garbage-collected runtime — triggers more frequent garbage collection, which eats yet more CPU, a self-reinforcing pattern sometimes called a garbage-collection death spiral. What separates both of these from an ordinary multi-part outage is the causal chain: the failure of one part is literally what causes the next part to fail, rather than two unrelated parts merely failing to fail independently at around the same unlucky moment.

### Breaking the Feedback Loop: Deadlines, Jittered Backoff, and Capacity Headroom

A handful of overlapping defenses, roughly in priority order, keep an overloaded system from tipping into a self-reinforcing cascade. Load testing a component until it actually breaks — and studying how it fails, not only confirming that it eventually does — is the foundation, because it's very hard to predict from first principles which resource will run out first or how ugly the failure mode will look. From there: serve degraded results before failing outright, instrument individual tasks to reject work once they're overloaded rather than trying to serve everything and collapsing, and add rate limiting at higher layers — reverse proxies, load balancers — so that a surge gets contained before a failure has already started spreading downstream. Capacity planning belongs on this list too, in the same N+2 spirit covered elsewhere: if every cluster's actual breaking point is a known quantity and traffic is spread evenly, the number of clusters needed to survive losing the two largest ones at peak follows directly from that arithmetic. None of this eliminates the risk entirely, though — a load-balancing misconfiguration, a network partition, or a sudden shift in where traffic is coming from can still create local pockets of overload no amount of planning fully anticipated. Two more mechanisms specifically target the retry side of the feedback loop: deadline propagation, where a single deadline set high in a call stack shrinks as it passes down through each layer so that no downstream component keeps grinding away on a request its caller has already abandoned, and randomized exponential backoff with jitter on every client retry, since un-jittered retries have a well-documented habit of synchronizing into their own recurring traffic spikes — precisely the mechanism, seen at Niantic-scale in the Pokémon GO launch, where an unchecked retry storm turned a real but survivable overload into a much larger one.

## Designing for Scale: Non-Abstract Large System Design

### What NALSD Is, and Why 'Non-Abstract' Is the Point

Non-Abstract Large System Design, or NALSD, is an iterative methodology for turning a rough system sketch into a concrete, defensible resource proposal, blending capacity planning, deliberate component isolation, and graceful degradation into a single repeatable design habit. The 'non-abstract' half of the name is the whole point: every system eventually has to run on real machines, in real datacenters, over real networks with real physical limits, so the discipline of continually converting an abstract whiteboard idea into actual figures — how many machines, how much memory, how much network bandwidth — is what surfaces a fatal physical constraint while it's still cheap to fix, rather than discovering it after the design is already built. The exercise deliberately drives toward concrete numbers, but the numbers themselves aren't really the point; the value lies in practicing sound, explicit assumptions and being able to defend them, since even imperfect assumptions, combined across several iterations, build a far better understanding of a design's actual shape than staying comfortably abstract ever would. It's a skill SREs are expected to exercise routinely — starting from a basic sketch of a system, reasoning through how it would need to scale and where it could fail, and arriving at a concrete resource estimate — precisely because production systems keep changing shape, and that reasoning muscle atrophies if it's only exercised once at initial design time.

### The Basic Design Phase: Is It Possible? Can We Do Better?

NALSD's first phase asks two deliberately unconstrained questions before worrying about scale at all: is a design even possible in principle, ignoring for the moment whether there's enough RAM, CPU, or network bandwidth to actually run it — and once something plausible exists, can it be made simpler, faster, or cheaper. A worked example from the SRE workbook grounds this: designing a system to report an ad's click-through rate from raw search and click logs starts, in this first pass, with the simplest imaginable answer — a single machine running an indexed database, joining a query log against a click log to compute clicks divided by impressions. Even at this stage the exercise forces real numbers: estimating each query-log entry at roughly two kilobytes and multiplying by hundreds of thousands of queries per second across a full day yields on the order of 100 terabytes of log data daily, which immediately exposes a bottleneck no amount of clever indexing can hide — a single machine's disks simply can't sustain the write rate that volume implies. That calculation is what makes 'can we do better' more than a rhetorical question; and stepping back to evaluate the one-machine design against a basic resilience test — what happens when this single component fails — makes clear that even setting the throughput problem aside, a lone machine is an unacceptable single point of failure for anything meant to stay available. Failing the basic design phase this way isn't wasted effort; it's exactly the signal that the design needs to become distributed before moving forward.

### The Scaling Phase: Feasible? Resilient? Iterate Again.

Once a basic design is sound in principle, NALSD's second phase asks whether it's actually feasible under real-world constraints of money and hardware, and whether it's resilient — can it degrade gracefully, and does it survive the loss of an entire datacenter, not just a single machine. Returning to the click-through-rate example, an initial instinct might be to process the logs with a batch framework that scales horizontally without any real ceiling — but batch processing turns out to fail the feasibility test against the system's own freshness requirement, since splitting logs into small time-boxed batches to hit a tight latency target means a query logged in one batch and its matching click landed in the next batch would never actually get joined together at all. The design that survives this iteration instead keeps a queryable, keyed store of the (larger) query stream and processes the (much smaller) click stream against it on the fly, trading a full log scan for a targeted lookup — which is a smaller, cheaper problem to scale. Distributing that lookup layer across many machines, sharded by a consistent hash of the record's key, spreads the write and lookup load evenly; deliberately writing each shard's data to two separate machines rather than one is what actually answers the resilience question, since losing any single machine no longer means losing the in-flight work it was holding.

### Multidatacenter Resilience: When Scaling Requires Distributed Consensus

Even a design that's been sharded and replicated across many machines within one datacenter still has a glaring single point of failure if that datacenter itself goes dark — a multiday power outage or a severed network link takes the whole system down at once. Surviving that requires replicating the critical shared state across multiple, geographically separated datacenters, and keeping those replicas consistent with each other is a specific, well-known hard problem: distributed consensus, typically solved by keeping three or five copies of the state and requiring the replicas to agree with each other, via an algorithm such as Paxos, before a write is considered durable. That agreement isn't free — because it requires at least one full network round trip between datacenters that might be hundreds of kilometers apart, each individual write operation on a single sequential process is capped at only a few dozen per second, which is a dramatically lower throughput ceiling than a single machine could otherwise sustain. Reasoning through that constraint in concrete terms is exactly the NALSD payoff: dividing the actual required write rate by that per-process ceiling tells you directly how many parallel processes — and from there, how many physical machines — the consensus layer needs, turning an abstract 'make it resilient to datacenter loss' requirement into a specific headcount of machines that can then be checked against the design's original latency and freshness targets.

### NALSD Is a Practiced Skill, Not a One-Time Calculation

The four questions that structure NALSD — is it possible, can we do better, is it feasible, is it resilient — aren't meant to be asked once at the start of a design and then forgotten; they're meant to be revisited at every iteration, because a design that comfortably clears the basic-design phase can still stumble once it's pushed through the scaling phase, sending the whole process back to modify or entirely replace a component rather than starting from a blank page. What makes the exercise worth practicing regularly, rather than treating as a one-off interview trick, is that the specific numbers from any single worked example — click-through-rate dashboards, or anything else — matter far less than the ability to reproduce that same reasoning chain against an unfamiliar system: sketching a rough design on a whiteboard, working through what happens as load and failure domains grow, and landing on a concrete, defensible resource estimate. Google's own experience is that this ability degrades without regular use, which is why NALSD is treated less like a document to consult and more like a muscle SREs are expected to keep exercising throughout their careers, on new problems, with new and imperfect assumptions each time.
