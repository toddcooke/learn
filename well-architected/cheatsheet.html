AWS Well-Architected Framework — Cheat Sheet

6 pillars

The Six Pillars

PillarIs the ability to…
Operational excellencerun workloads effectively, see into their operations, and keep improving
Securityprotect data, systems, and assets using cloud technologies
Reliabilityperform the intended function correctly and consistently, when expected
Performance efficiencyuse resources efficiently, and stay efficient as demand and tech change
Cost optimizationdeliver business value at the lowest price point
Sustainabilitycut energy use and raise efficiency across every component

Trade-offs follow business context — but security and operational excellence are generally not traded off against the others.

General Design Principles

  • Stop guessing capacity — take what you need now, scale automatically
  • Test at production scale — build it on demand, pay for the hours, tear it down
  • Automate for experimentation — cheap to replicate, tracked, auditable, revertible
  • Evolutionary architectures — design to keep changing, not to be settled once
  • Drive architectures with data — measure how each choice behaved
  • Improve through game days — simulate real events; test people and systems

Vocabulary

  • Component — code + config + resources meeting one requirement; the unit of ownership
  • Workload — components delivering business value; the unit a review covers
  • Architecture — how the components work together
  • Milestone — a key change as the architecture evolves (design → go-live → production)
  • Technology portfolio — every workload the business needs to operate
  • Level of effort — High = weeks–months · Medium = days–weeks · Low = hours–days

The Review

  • A conversation, not an audit — blame-free, hours not days
  • Output = prioritized risks and actions, not a score or a certification
  • Review early in design (catch one-way doors) and again before go-live
  • Two-way door = reversible, decide lightly · one-way door = inspect first
  • Better than a formal meeting: the building team reviews continuously as it evolves
  • Across the portfolio, look for themes — fix with a mechanism, not team by team

“Good intentions never work, you need good mechanisms.” Practices raise the bar; mechanisms check it automatically.

Operational Excellence OPS

  • Organize teams around business outcomes
  • Implement observability for actionable insights
  • Safely automate — guardrails: rate control, error thresholds, approvals
  • Frequent, small, reversible changes — smaller blast radius
  • Refine procedures frequently; verify teams know them
  • Anticipate failure — drive scenarios, decide which risks to accept
  • Learn from all operational events and metrics, not just failures
  • Use managed services to cut operational burden

Areas: Organization · Prepare · Operate · Evolve

Security SEC

  • Strong identity foundation — least privilege, separation of duties, no long-term static credentials
  • Maintain traceability — monitor, alert, audit in real time; act automatically
  • Security at all layers — edge, VPC, LB, instance, OS, app, code
  • Automate security best practices — controls as version-controlled code
  • Protect data in transit and at rest — classify first, then encrypt/tokenize
  • Keep people away from data — remove the need for manual handling
  • Prepare for events — policy, process, simulations, automated tooling

Areas: security foundations · IAM · detection · infrastructure protection · data protection · incident response · application security

Reliability REL

  • Automatically recover from failure — trigger on KPIs that measure business value
  • Test recovery procedures — test how it fails, not only that it works
  • Scale horizontally — many small resources, no shared point of failure
  • Stop guessing capacity — saturation is what a DoS is trying to cause
  • Manage change through automation — including changes to the automation

Areas: Foundations (quotas, network topology) · Workload architecture · Change management · Failure management

Performance Efficiency PERF

  • Democratize advanced tech — consume it as a service instead of learning to run it
  • Go global in minutes — multi-Region for latency, at minimal cost
  • Use serverless — no servers to run; often lower transactional cost
  • Experiment more often — virtual resources make A/B of instance, storage, config cheap
  • Mechanical sympathy — let access patterns pick the datastore

Areas: architecture selection · compute and hardware · data management · networking and content delivery · process and culture. Endorsed trade-offs: compression, caching, relaxed consistency.

Cost Optimization COST

  • Implement Cloud Financial Management — a capability to build, like security
  • Adopt a consumption model — dev/test 8h×5 vs 24×7 ≈ 75% saved
  • Measure overall efficiency — business output ÷ cost to deliver it
  • Stop paying for undifferentiated heavy lifting
  • Analyze and attribute expenditure — cost per workload owner, so ROI is visible

Areas: practice CFM · expenditure and usage awareness · cost-effective resources · manage demand and supply · optimize over time. Speed-to-market over cost is a legitimate trade-off; lift-and-shift-then-optimize is too.

Sustainability SUS

  • Understand your impact — include customer use and decommissioning; measure per unit of work
  • Establish goals — per-transaction intensity, so growth cuts impact per unit
  • Maximize utilization — 2 hosts at 30% waste more than 1 at 60% (baseline power)
  • Adopt new efficient offerings — design for flexibility so you can move
  • Use managed services — shared utilization needs less total infrastructure
  • Reduce downstream impact — don't force customers to upgrade devices

Areas: region selection · alignment to demand · software and architecture · data management · hardware and services · process and culture

Beyond the Framework

  • Lenses — domain extensions (ML, analytics, serverless, HPC, IoT, SAP, media, games, hybrid networking, financial services); use with the pillars
